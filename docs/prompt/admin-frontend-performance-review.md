# AisenCore Admin 全面性能审查提示词

> 使用方式：将下方提示词全文交给能够读取本仓库、运行本地构建和浏览器的审查者。本文件是审查指令模板，不是审查结果、整改授权或阶段验收证明。

---

请对当前 AisenCore 项目的正式 Admin 前端进行全面性能审查。目标是发现影响实际管理任务的加载、交互、网络、渲染和资源成本问题，提供可复现证据及最小正确整改建议。本轮先审查，不实施整改。

## 1. 事实、范围与约束

先阅读根目录 `AGENTS.md`、当前 Git 状态和以下直接相关文件：

- `docs/spec/requirements.md`
- `docs/architecture/applications/admin-console.md`
- `docs/architecture/applications/admin-ui-design-system.md`
- `docs/architecture/infrastructure/repository-structure.md`
- `docs/Plans/TODO.md`
- `docs/Plans/aisencore-mvp/00-mvp-master-plan.md`
- `docs/Plans/aisencore-mvp/three-stage-delivery-gates.md`
- `docs/Plans/aisencore-mvp/phase1-delivery-remediation-plan.md`
- `docs/Plans/aisencore-mvp/d3-acceptance-matrix.md`
- `apps/admin/README.md`、根及 Admin 的 `package.json`、锁文件、Vite 配置。

以当前源码、锁定版本、实际运行结果为实现证据；文档中的历史日志和候选预算不能冒充当前事实。发现矛盾时分别列明需求合同、当前实现和验证缺口，不默认沿用旧描述。

已知架构仅供定位，开工时必须核实：

- 正式前端在 `apps/admin/`，使用 Vite + React + TypeScript + React-admin + MUI/Emotion。
- React-admin 已提供 TanStack Query 数据缓存、Resource、列表、表单、路由和通知等能力。不能预设项目“没有缓存”，也不能建议再搭一套 QueryClient、SWR、表格、状态或路由框架。
- 唯一主题入口为 `src/theme.ts`；外壳、页面组合和局部 `sx` 同样可能影响性能。
- 普通数据经 DataProvider、PostgREST/RLS 读取；写入经受保护 RPC；部分能力涉及 Edge Function。Supabase Auth/TOTP MFA 和服务端资格复核属于必须保留的安全边界。
- 项目处于第一阶段、本地隔离合成数据交付期，完整性能验收仍须独立核查。不得接入 AisenLens 实际业务或线上服务。
- 已存在路由懒加载、依赖分包和部分测试；逐一验证实际效果，不能把“存在 lazy/import 或 chunk”直接算作优化完成。

审查全部正式页面及共享路径，以当前 `App.tsx` 的 Resource、CustomRoutes、登录/恢复入口和组件调用关系生成清单，不硬编码旧页面数量。至少涵盖：登录/TOTP/恢复、概览、产品、成员、账号查找与用户详情、权益、批次/码/核销、成员事件、管理员/限制/审计、反馈收件箱/工作台/归档/回收站/详情，以及实际存在的标签、编辑、处理历史、图片预览、导出和通用操作弹窗。静态孤立文件与真实运行入口必须区分。

## 2. 本轮权限和工程纪律

1. 不修改或删除产品源码、现有测试、依赖、锁文件、配置、迁移和现有用户改动；允许新增审查报告与必要诊断产物。不得顺手清理或重构。
2. 只使用已核实的独立本地环境和合成数据。不进行云配置、远程写入、Git 提交/推送或部署。
3. 不删除数据库、不 reset、不重建现有 Auth、不重置长期管理员或 MFA。浏览器冷缓存测试不能清掉正常使用的认证和业务数据；使用独立测试浏览器配置。
4. 运行任何现有脚本前先检查副作用。已有 E2E 可能真实写入、创建和清理对象，不能把它当只读性能工具直接运行。优先现有数据的只读操作；需要新增大规模数据、业务写入或故障写入实验时，先提交具体隔离方案并取得明确授权，继续完成不依赖它们的审查。
5. 不记录 Token、密码、TOTP 秘密、兑换码明文、私有图片内容或完整敏感响应。HAR、trace、截图和日志保存前脱敏；优先保存请求类型、计数、时序、大小和无秘密标识。不得让性能埋点或缓存保存敏感数据。
6. 复用已有工具。确需安装时遵守 `AGENTS.md`：可自定义路径的软件安装到 `D:\APP\Codex\对应软件目录`；缓存放 `E:\AppData\工具名称`，不能混放根目录或主动安装到 C 盘/默认目录。
7. 不为了性能放宽 MFA/RLS、可信 RPC、并发保护、幂等、审计、数据完整性、关键风险提示或无障碍要求。
8. 优先现有框架能力和最小改动；不机械要求新增库、memo、骨架屏、预取、虚拟列表、错误边界或重试层。每项建议必须对应可证明的问题。

## 3. 执行方式：全面覆盖，按风险深入

请实际执行能够安全完成的审查，不只交一份检查清单：

1. 记录时间、Git revision 与工作区差异摘要、依赖版本、浏览器/设备、运行命令、环境和数据规模；禁止覆盖现有服务或并行占用既有验收锁。
2. 对全部入口进行源码和构建依赖审查，并逐页核查生产构建浏览器覆盖。列出 PASS / FAIL / NOT RUN / N/A 及理由；无法运行浏览器时仍完成静态审查，但不作性能通过结论。
3. 用 `pnpm build` 的正式产物和独立端口的 `vite preview` 测性能；开发服务器只辅助定位。记录实际启动方式和服务响应，确认没有测到 Vite 开发产物。需要正确会话的页面使用真实本地 AAL2，不绕过权限。
4. 所有路由完成基本浏览器核查；对登录、概览、典型列表、关联最重详情、反馈列表/详情/导出和共享弹窗做深度 trace。对发现异常的其余页面补深测，禁止以代表页代替全站覆盖。
5. 分开记录首次文档加载、认证完成后加载、SPA 路由切换、同页筛选/分页、弹窗操作，不把不同起点的耗时混成一项。
6. 正常读取与交互优先；慢网、离线和只读 429/503 等使用局部、可撤销的浏览器注入，不影响正常开发服务。记录注入规则、恢复步骤和是否实际触达后端。

## 4. 测量矩阵与指标口径

### 4.1 场景

- 首次访问、静态资源热缓存、应用数据缓存命中/失效、刷新、离开后返回；区分浏览器 HTTP 缓存与 React-admin 查询缓存。
- 桌面正常网络，以及固定参数的受限网络/CPU；记录上下行、RTT、CPU 降速、视口与浏览器版本。限速模拟不等于真机测试。
- 数据库记录规模按可用条件覆盖 100 / 1,000 / 10,000，并记录表、关联基数、数据分布、实际返回行数和总数。不得把数据库总量等同于 DOM 渲染量，也不为压测取消服务端分页。现有数据不足且无造数授权时标 NOT RUN。
- 列表加载、筛选/排序/分页、快速切换产品范围、返回详情、打开/关闭弹窗、反馈编辑及历史分页、图片预览与关闭、导出准备/下载、重复访问后内存变化。
- 无数据、筛选无结果、加载中、读取失败及恢复；已授权的写入实验另测提交反馈、成功刷新、失败和 UNKNOWN，不能混用只读重试策略。

### 4.2 测量要求

- 同条件基准至少重复 5 次，记录所有样本、样本数、异常、失败率和中位数；预热与正式样本分开。需要报告 P95 时增加样本、写清算法及统计局限，不能将少量样本或一次最佳值当作稳定 P95。
- 文档加载记录 TTFB、FCP、LCP、CLS，并说明观测起止、LCP 元素及布局偏移来源。记录有实际交互支持的实验室 INP 观测；无有效交互时为 N/A，不能填 0。
- SPA 切换额外定义“触发导航→目标主要数据可见且关键控件可操作”；筛选定义“提交条件→对应结果稳定显示”。记录网络响应、渲染和等待分别耗时。不能把文档 LCP 直接当作每次 SPA 切页耗时。
- 分别记录输入/点击至下一次绘制与操作至服务端结果显示；后者包含网络等待，不等于 INP。TBT、Lighthouse 分数和 DOMContentLoaded 也不能替代 INP 或任务可用时间。
- LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1 作为公开指标的参考良好阈值；本地实验室结果不能宣称真实用户第 75 百分位达标。现行项目预算与新增候选预算分开，未经批准不宣称已冻结。
- 记录首访和切页的请求数量、串行关键路径、重复请求、传输字节、JS 解压/解析/执行、主线程长任务、布局/绘制、DOM 数量和可用的内存数据。
- 明确传输大小、解压大小、磁盘大小与 gzip 估算的区别；无法采集为 NOT RUN，0 或空字段不能解释成“没有资源成本”。记录工具限制。
- 正式构建用于体验基准；React 开发/Profiling 构建仅用于重渲染归因，单独标注插桩开销。区分 StrictMode 开发重复执行与生产重复请求。
- 本地 preview 结果不代表未来 CDN、真实网络、真实 R2 或生产数据库性能。

## 5. 十个审查维度

### A. 首屏、导航与加载关键路径

追踪 HTML→入口 JS→依赖→认证判断→业务 chunk→查询→主要内容的完整瀑布，区分必要安全依赖和可消除串行等待。检查 Suspense 边界是否导致整个外壳反复消失、路由 chunk 失败后的恢复、已加载资源是否重复下载。不能以预取为由在未授权/MFA 前读取管理数据。

### B. 实际分包与资源成本

检查 App、共享导航/弹窗、资源模块和 Provider 的传递依赖，核实 `lazy` 是否仍被其他静态引用提前带入。核对 Vite/Rolldown 真实输出和 Network：首屏到底下载哪些 chunk，vendor 分组是否拖入当前路由不需要的代码，拆分是否制造串行网络等待。检查依赖重复、图标/日期/编辑器/导出库、字体和静态资产；不能只看最大 chunk、源码 import 写法或构建警告判断问题。

### C. 请求数量、关联查询与分页

追踪 React-admin hooks→DataProvider→PostgREST/RPC 的实际请求。检查同一产品/身份查询是否重复、`ReferenceField/getMany` 是否实际合并、是否发生逐行 N+1、计数查询是否过重、字段和响应是否过量。检查产品范围切换、User360、Dashboard、反馈标签/负责人/历史等关联路径。区分前端调度、网络、RLS/RPC/数据库成本；必要的后端归因限于该前端路径，不扩展成全库审计。诊断 SQL 用只读 EXPLAIN，未经授权不执行会产生写入或重负载的 EXPLAIN ANALYZE。

### D. 缓存、失效与状态一致性

核查现有 QueryClient 默认值和实际配置、query key 的产品/筛选/排序/分页边界、staleTime/gcTime、聚焦/挂载重验、去重及写入后的刷新范围。判断返回页面时是否保留已有数据，区分正常后台重验与整页清空。检查过宽失效、重复 useRefresh 和漏刷；登出、账号变化、401/403/撤权后敏感缓存应正确处理。不得为了少请求跨身份复用缓存、长期缓存权限或持久化码明文。

### E. React 渲染、表格与输入响应

定位真实长任务和慢 commit，检查 Context/useStore 更新传播、昂贵计算、列表 key、桌面/移动两套视图是否同时渲染、表格单元格关联组件和高频输入。没有性能证据时不能把 useState/useEffect、未使用 memo 或几十行分页表格直接定为缺陷；只有可见行渲染确实成为瓶颈且官方能力不能满足时才评估虚拟化，并说明键盘、读屏、选择和打印成本。

### F. 布局稳定性与感知等待

对初始加载、查询重验、空态到有数据、错误恢复、图片到达、字体替换和弹窗展开记录布局偏移。定位源元素和受影响操作，区分用户主动展开与不预期偏移。只有实际需要时建议占位/保留高度，不能普遍硬编码与真实内容等高的巨型空容器，也不能用新增说明文案掩盖等待。

### G. MUI/Emotion、样式、滚动与合成

检查 `theme.ts`、外壳和局部 `sx` 的运行时样式成本、重复样式、布局读写、粘性区域、表格溢出、阴影、透明层和 backdrop-filter。用 trace/绘制或图层证据确认掉帧及重绘；不能仅凭存在模糊或局部 sx 判定性能差，更不能为跑分全面取消视觉设计。

### H. 图片、反馈编辑、导出与资源生命周期

按当前真实实现检查附件尺寸、按需读取、预览首开/复开、私有 URL 有效期、Blob URL 释放、图片解码和列表缩略图。检查编辑草稿、标签字典、处理历史是否无谓全量加载，导出是否阻塞主线程、重复请求、积累 Blob/监听器或过量占用内存。区分浏览器成本、Edge 打包、存储读取和下载等待；仅有本地模拟存储时单列真实 R2 NOT RUN。导出范围以当前合同为准，不擅自扩大条数/体积。

### I. 认证、网络失败与安全写入

检查有效 AAL2 下是否每次导航/查询重复调用 Auth 或 MFA，以及 token 刷新是否形成并发风暴；不能移除必要准入检查。核查只读请求取消、过期响应、快速范围切换竞态、错误边界和局部恢复。检查 Query/SDK/自定义逻辑是否叠加重试；401/403、429、503、断网分别处理，遵守适用的 Retry-After，不普遍加重试。发码、授予、撤销、封禁等敏感命令必须等待可信结果；UNKNOWN 保留原 request_id 先核查，不能建议盲重试、换编号重发或乐观宣称成功。

### J. 长会话、测量工具与维护成本

在固定操作序列下反复切页、切范围、开关弹窗/图片/历史，比较稳定后的堆、DOM、监听器、请求和缓存规模；区分预期缓存增长与持续泄漏，不能凭一次堆快照定论。检查现有性能脚本是否测错开发环境、遗漏异步请求、把数据缺失写成 0，或用固定 sleep 导致虚假稳定。只提出确有重复成本的收敛建议，不将代码审美问题冒充性能缺陷。

## 6. 证据与定级

每个发现必须区分：

- **已证实**：实际可复现，提供浏览器/网络/trace/构建证据及源码因果链。
- **静态风险**：源码可证明风险路径，但尚缺运行证据；不得编造耗时、频率和提升百分比。
- **待验证**：缺数据、环境、权限或工具；列出最小验证步骤，不当成已确认缺陷。

按用户影响、频率、覆盖面和恢复成本定级，独立记录证据置信度：

- P0：可复现的核心任务持续不可用、卡死或性能问题造成严重操作安全后果。
- P1：核心高频路径显著等待/卡顿、重复请求风暴、持续资源增长或关键结果被阻塞。
- P2：局部、可恢复且有可测成本的问题。
- P3：低影响且确有证据的微小成本。

不按“缺少某库”“没有骨架屏/虚拟化”“用了 Hooks”定级，也不把一次指标超参考阈值自动升级为 P0。无收益或未经测量的建议不列为整改事项。

每条发现使用以下格式：

1. 编号、标题、严重度、证据类型与置信度。
2. 影响页面/任务、数据规模、网络/CPU、缓存状态和复现步骤。
3. 当前源码路径、函数/组件与准确行号；相关调用链。
4. 原始证据路径、采样方法、样本数、指标及用户可观察结果。
5. 根因：前端加载/渲染、请求调度、认证、后端查询或存储；尚不能分离的部分明确说明。
6. 最小整改建议、可复用的现有 React-admin/MUI 能力、涉及文件及调用方。
7. 安全/一致性/无障碍约束、实现成本、替代方案是否必要。
8. 修复后同条件验证方法及预期改善方向；没有对照实测就不能写确定提升数值。

## 7. 交付格式与停止条件

允许把报告及脱敏证据放在 `docs/Plans/aisencore-mvp/ui-evidence/` 中独立命名的位置，不覆盖旧证据；报告使用相对链接指向证据与代码，不复制秘密。对外提供可点击的实际文件链接。

报告依次给出：

1. **总体判断**：当前能否支持主要管理任务、最主要的已证实瓶颈、判断局限；不是第一阶段签收。
2. **全站覆盖矩阵**：页面/弹窗、状态、场景、静态与浏览器覆盖、测量状态及证据位置；包括未测项。
3. **性能基线表**：环境、数据与返回行数、缓存、样本数、加载/交互/任务可用时间、请求/字节/长任务/内存；无数据不填零。
4. **发现清单**：P0→P3，先展开最重要的 5～8 项，其余真实问题保留在完整表，不得只查代表页或凑固定数量。
5. **最小整改顺序**：先根因后表象，合并同一共享根因；列明影响面、依赖、成本、验证方法，以及是否需要另行授权的数据或后端实验。不提出整套技术栈迁移。
6. **现有实现有效之处**：仅列已核实能力，避免重复建议已有优化；无需重造轮子的地方说明依据。
7. **未执行检查与剩余缺口**：准确列出命令、结果、失败原因、真机/真实 R2/生产网络/大数据/线上真实用户指标等边界。

有关框架行为和测量方法优先查本地安装版本与官方资料，引用准确来源；避免拿其他技术栈的规则套用本项目。可参考：
