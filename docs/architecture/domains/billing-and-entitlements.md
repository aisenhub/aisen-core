# 统一计费与产品权益专项架构

> 状态：**自有兑换码优先 + 爱发电初期暂定 + 支付宝个体户和 Stripe 后期扩展**；轻量统一计费、四类权益、在线授权原则、**MVP 权益逻辑模型、兑换码默认规则及兑换与成员状态的关系**已确认；具体 DDL、函数与接入均未实施。
>
> 本文是权益、套餐、兑换码与支付渠道**业务规则的唯一权威**；数据库约束见[权益与兑换码数据约束](../database/entitlements-and-redemption-constraints.md)，接口契约见[API 契约与 MVP 验收](../backend/api-contract-and-mvp-acceptance.md)。

## 1. 统一公共能力

- 全平台复用 Supabase 用户身份；按用户及产品确定有效权限。
- 多产品共用必要的授权来源、订单/支付状态、订阅生命周期（续费、取消、退款结果）和可靠的权益同步。
- **每个产品独立套餐、价格、订阅和会员权益**；购买某产品会员不自动授权另一产品。
- 公共计费只管理必要的计费事实与产品级权益关系；不接管各产品业务项目、任务和内容。
- **额度事实的归属**：公共平台可声明套餐 `features/limits`，但实际已使用次数/容量、库存预留与扣减由拥有资源的 SaaS 可信业务库/服务负责；**不在首版提前建设全 SaaS 通用余额表、Redis 配额缓存或 `consume_user_quota` 通用接口**。未来确有平台承担费用的消费型产品时再设计可信定价、原子扣减、请求幂等和账本。Aisenlens AI 分析由用户自带第三方 API Key 直连，不产生 AisenCore 应扣的模型调用额；首版 R2 配置备份只需要 Aisenlens 自身的容量/对象预留与确认。实施安全边界见[RPC 原子配额审查](../../Plans/aisencore-mvp/aisencore-mvp-baas-quota-security-lessons.md)。
- 计费事实来自可信流程，重复或延迟的通知需要可靠处理；避免权益状态与实际订阅长期不一致。
- 首版 Admin 管理**产品、套餐/权益与自有兑换码**；外部订单、订阅与退款管理随支付渠道接入再增加（见[Admin 管理前端](../applications/admin-console.md)）。人工修改他人权益、退款等敏感操作必须经可信服务端，浏览器不持有高权限密钥。

## 2. 权益来源与支付接入顺序（当前有效，唯一权威）

| 顺序 | 机制 | 阶段与定位 |
| --- | --- | --- |
| **1** | **AisenCore 平台自有兑换码** | **优先建设的基础授权入口**；React-admin 创建兑换码，由平台所有者人工分发，用户兑换成功后获取对应产品的会员权益。不是爱发电的内置兑换码，也不依赖任何支付平台 |
| **2** | **爱发电（Afdian）** | 初期**暂定**的外部打赏/收款渠道；用户曾在此前项目简单跑通打赏和回调，本项目尚未集成，需再核实适用规则及可靠的订单匹配 |
| **3** | **支付宝个体工商户支付** | 未来注册个体工商户并满足商户资质后再开发，首期不接入 |
| **4** | **Stripe** | 更后期视商户资格和国际收款需求再评估，首期不接入 |

**统一权益，不统一各渠道内部机制**：兑换码、可信订单或管理员人工授予都只是**授权来源**，统一写成同一种“产品授权记录”（见 §3）；各 SaaS 只读取公共权益结果，更换收款方式不影响产品的 Pro 判定。不为尚未接入的渠道建设多支付插件平台，只保留 `source_type` / `source_ref` 这一精简的来源标识。

**爱发电回调可靠性（阶段 2 接入时适用）**：官方提供 Webhook 与订单查询 API，且提示 Webhook 可能漏推、重复；不能仅凭收到请求或前端成功页面开通 Pro。必须以可信端核对订单真实性与状态、所属方案和产品、对应 AisenCore 用户，再以 `source_type='afdian' + 订单号` 幂等写入授权，并考虑漏推补查。具体关联方式、核验方案、平台规则及订阅/退款支持程度**待正式接入时确认**。

## 3. MVP 权益逻辑模型

| 逻辑实体 | 职责 | 关键规则 |
| --- | --- | --- |
| **套餐 `plans`** | 某产品的一个会员方案，例如 `free` / `pro` | 归属单一产品；`plan_key` 在产品内唯一；包含 `features`（功能开关键集合）与 `limits`（数量、额度、存储配额等数值上限）；可选默认授权时长 |
| **产品授权 `entitlement_grants`** | 某用户在某产品获得某套餐的一段授权事实 | 记录来源（`redeem_code` / `admin`，以后 `afdian` 等）、`starts_at`、`ends_at`（**NULL = 一次性永久的非周期授权**）、`revoked_at`；同一来源引用只能产生一条授权（幂等） |
| **兑换码 `redemption_codes`** | 平台自有兑换码及其可用条件 | 见 §4 |
| **兑换记录 `redemptions`** | 某用户使用某码的事实，并关联生成的授权 | 同一码同一用户最多一次 |

**当前有效权益的计算**：读取该用户、该产品全部**未撤销、`starts_at <= now()` 且 (`ends_at IS NULL` 或 `now() < ends_at`)**的授权，按照授权对应的**不可变套餐版本**求并集——功能开关取并集，同名数值额度取最大值（**不相加**）。不靠审计事件回放。每个产品可维护保留 `plan_key='free'` 的基础套餐；即使无有效付费授权，Free 基础功能/额度也按该套餐返回（未配置时默认为无额外能力、额度为 0）。**Free 不要求创建授权记录**；无成员时仍不能使用需要成员的受保护服务。

**能力（capability）标识**就是套餐 `features` / `limits` 中的键（如 `export.hd`、`templates.max`），由管理员按产品维护；功能键表示布尔可用性，额度键表示非负数值上限，未定义的键默认不可用/上限为 0。一个产品内同名键不得同时充当功能开关与数值额度。**一旦套餐被任何授权记录或已发行兑换码引用，features/limits 等权益字段就不得原地修改**；权益调整新建套餐版本、停用旧版本，既不能改变历史已购权益，也不能暗中改变已分发但尚未兑换的码所承诺的权益。不建设平台级能力注册中心或业务资源级通用策略。

**同一套餐的续期规则（MVP 默认）**：新周期授权的 `starts_at = max(当前可信时间, 同用户同套餐未来最晚的非撤销周期 ends_at)`，`ends_at = starts_at + 固定授权天数`；已到期或撤销的旧记录不延长。用户已有**永久**同套餐授权时，新增周期授权仍独立记录但不扩大有效能力；不同套餐不折算、不共享期限。同用户同套餐的并发续期须串行化，防止都读到相同旧到期时间。

**额度与配额的职责（MVP 口径）**：公共权益**定义并返回上限**；**计数由拥有数据的一方负责**——云端 SaaS 按自身业务库计数，文件/备份配额由持有文件元数据的产品计算，本地使用量的可信度由各产品自行评估。公共侧的用量核销/预留账本推迟到出现跨产品或防篡改的真实需求时再建。

**目标商业模式**：月付订阅、年付订阅、一次性永久购买、免费试用四类仍是平台目标；在 MVP 模型中分别表达为“有 `ends_at` 的授权”“`ends_at` 为空的永久授权”和“来源为试用的短期授权”。它们**不要求**兑换码或爱发电阶段立即具备自动续费、扣费或退款；试用是否绑卡、是否自动转正待定。

**首发 Aisenlens 业务已确认**：Free 是可脱离网络/账号正常使用的本地基础工作流；Pro 增加 AI 分析、无水印导出和配置/模板私有云备份，功能开关与数值额度严格分离（字段名、价格、额度仍待产品确认）。首批 Pro 有 **30 天、365 天、永久**三种授权时长，**首版不自动开试用**。30/365 天是固定天数而非自动续订；永久 Pro 使用 `entitlement_grants.ends_at IS NULL` 表示非周期自然到期的产品级授权，并非特殊登录凭证/不受封禁或撤权。推荐三个不可变权益版本/独立套餐键，实际 key 可随 Aisenlens 实现确认。首批兑换码运营确认为**本人 Admin 人工、小批次、单次兑换、固定时长**；100/批仅是候选上限，未批准为生产硬值。永久 Pro 模型可以先通过受保护的管理员直接永久 grant，是否发永久兑换码仍需明确。

## 4. 自有兑换码 MVP 规则

**默认规则（首版即支持，均为可配置项，不预设所有码必为单次或永久）**：

| 属性 | MVP 规则 |
| --- | --- |
| 授权范围 | 每个码对应**一个产品的一个套餐** |
| 授权时长 | 固定天数，或永久（非周期） |
| 可使用次数 | `max_redemptions`，默认 1；同一用户对同一码最多兑换一次 |
| 码本身有效期 | 可选截止时间，过期后不可再兑换 |
| 批量创建 | 一次管理请求可按相同配置生成多张码（单次数量上限在实施时设定） |
| 撤销 | 撤销码只阻止后续兑换；**已产生的授权不受影响**，如需收回由管理员单独撤销对应授权 |
| 绑定指定用户 | 首版不做，确有需要再加 |

**已发行码与套餐停用**：`plans.is_active=false` 只阻止**新建**该套餐的兑换码或管理员直接发放新授权；在码自身有效、未撤销、尚有次数、所属产品仍 `active` 且用户满足准入的前提下，**已发行码仍可按发行时绑定的不可变套餐版本兑换**。需要停止旧码兑现时，管理员应明确撤销对应码或批次，而不是依赖停用套餐的隐式副作用。历史授权和有效权益计算也不因套餐停用而被撤销。

**最小安全要求**：

- 码由可信服务端以安全随机数生成，**有效熵不低于 128 bit**（例如至少 26 个等概率 Base32 随机字符，扣除校验位后仍应达到阈值），统一大小写/连字符规范再计算哈希；绝不使用可猜测序列号、时间戳或非安全随机数。
- 数据库只保存规范化码的**SHA-256 哈希**（高熵码足够抵御离线猜测）；明文仅在**创建成功的首次响应**中提供管理员当次复制/下载，之后不可再次获取或导出，不写日志、审计、浏览器持久存储或监控事件。首次响应丢失只能撤销旧批次并重新发码，不能恢复明文。
- 兑换 RPC **在数据库内按 `auth.uid()` 限流**：每用户滚动 15 分钟最多 10 次失败尝试；达到限额回复 `RATE_LIMITED` 并给出可重试时间，外层可再配置 IP/WAF 防滥用。对**未兑换过该码的用户**，无效、过期、撤销、用尽统一对外返回 `REDEEM_CODE_INVALID`，不能暴露码状态；对**已兑换过该码的本人**返回 `REDEEM_ALREADY_USED`，该分支优先于码随后用尽、过期或撤销的判定（但不绕过身份、平台账号限制和限流）。**业务拒绝采用带 `code` 的结构化结果而不是抛出数据库异常**，使失败次数即使业务拒绝仍可提交；数据库技术故障仍抛异常使整个事务回滚。成功写入授权、兑换与成员审计必须同事务，绝不能在失败时扣码。
- 兑换结果不明（如超时）时，客户端先查询本人授权/兑换记录再决定是否重试；重复提交同一码由“同一用户同一码一次”的约束保证不重复授权。**批量发码请求必须携带独立 `request_id` 幂等键**；重复请求不能重新生成新码，已丢失的明文不可从数据库恢复，只能受控作废并以新请求重新发码。

## 5. 授权与产品成员状态的关系（唯一权威）

**成员资格与授权事实相互独立**：退出或封禁不自动删除订单、撤销授权、终止订阅或清空 Pro；时效、试用与额度不因退出暂停或重置。重新加入只使用仍有效且未撤销的权益。完整成员规则以[产品成员生命周期](./membership-lifecycle.md)为准。

| 授权来源 | 账号被平台限制 | 尚未加入（无记录） | `active` | `left` | `suspended` |
| --- | --- | --- | --- | --- | --- |
| **用户主动兑换** | 拒绝 | 视为首次合法使用：**同一事务内**创建 `active` 成员（写 `join` 事件）并完成兑换 | 正常兑换 | **拒绝**，提示需先明确重新加入；码不被消耗 | **拒绝**；码不被消耗 |
| **管理员人工授予** | 允许写入授权，但不改变任何访问限制 | 只写授权，不创建成员 | 写入 | 只写授权，不恢复成员 | 只写授权，不解封 |
| **外部支付回调**（阶段 2） | 只写授权 | 只写授权，不创建成员 | 写入 | 只写授权，不恢复成员 | 只写授权，不解封 |

任何授权来源都**绝不能**把 `left` / `suspended` 自动变回 `active`。对已付款但成员已退出或被封禁的用户如何告知、是否退款，随支付渠道接入时确定。退出产品**不等于取消自动续费**，有实际自动续费渠道时须提供独立的取消路径。

## 6. 首期权益类型与在线执行

首期公共权益能力为**功能开关、数量/使用额度、云端存储/备份配额、有效期/订阅到期**；并非每个产品都必须同时使用。**通用桌面离线会员授权首期明确不做**，如有产品确实需要再单独扩展。

| 已确认支持 | 权益能力 | 规则待定 |
| --- | --- | --- |
| 功能开关 | 套餐 `features`，按产品和用户区分 Free / Pro 功能 | 各产品功能列表、是否有其他会员档位 |
| 数量或使用额度 | 套餐 `limits` 定义上限，由产品计数 | 计数来源、周期、重置及本地计数可信度 |
| 云端存储/备份配额 | 套餐 `limits` 定义上限，由持有文件元数据的产品计算 | 配额单位、超限处理、删除后的回收 |
| 有效期与订阅到期 | 授权记录的 `starts_at` / `ends_at` / `revoked_at` | 宽限期、取消与退款处理 |

| 产品方式 | 权益校验职责 |
| --- | --- |
| 云端业务型 | 产品的云端可信后端在受保护操作时查询公共权益并实际校验，不能仅凭前端展示 |
| 本地优先型 | 公共权益为权威；启动联网校验 + 运行中按产品关键操作合理复核，详见[本地优先专项](../applications/local-first.md) |
| 混合型 | 按本地与云端操作的执行位置分别校验 |

## 7. 不做

- 不设计所有产品通用的一份 Pro 会员，不把业务数据迁移到公共计费数据库。
- 不预先设计大型多支付渠道插件、企业多租户计费或**按量收费**系统；本次确认的是**使用量限制**，不是按用量收费。
- 不把爱发电平台内部的兑换码当成 AisenCore 自有兑换码；不因爱发电临时采用就锁定未来渠道。
- 不在当前阶段对接支付宝个体工商户支付或 Stripe；不假设初期渠道支持所有自动扣费与退款行为。
- 不在首期建设公共用量账本、高级统计、综合运营中心或面向产品运营团队的权限平台。
- 不以仅前端的权限判断代替云端受保护操作的服务端校验，不承诺完全防止篡改客户端后的本地复制。

## 8. 数据位置

套餐、授权记录、兑换码与兑换记录**存放于公共 Supabase PostgreSQL**，因为兑换核销与授权写入必须在同一事务内完成。外部渠道的订单/订阅原始事实是否同库，在接入对应渠道时决定。

## 9. 待确认

首发 Aisenlens 的 Free/Pro 功能类别及 30/365/永久授权已定，但实际 feature key、Pro 价格、AI 用户 API Key 费用提示、备份配额具体数字、永久授权未来升级/退款/停止服务承诺仍待确认；运营者人工发码、首批单次固定时长已定，**100/批是候选**，非自动试用首版已确认。爱发电订单关联/核验/补查、支付宝/Stripe 接入、会员限制告知/退款、真实运行期复核与异常体验按产品/阶段验收；码明文仍只允许首发一次提供，不提供历史导出。
