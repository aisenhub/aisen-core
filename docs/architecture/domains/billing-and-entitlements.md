# 统一计费与产品权益专项架构

> 状态（2026-11-02）：自有兑换码优先；有限 Pro 使用已本地安装的信用账本，人工和兑换统一立即入账，永久覆盖冻结有限余额。部分真实 JWT/Admin/Lens 联调已有证据，完整验收仍 OPEN，详见[唯一 TODO](../../Plans/TODO.md)。本轮数据库复核及未修缺陷见[审查](../../reviews/2026-11-02-aisencore-backend-supabase-audit.md)；数据清理不代表上线或正式签收。
>
> 本文是权益、套餐、兑换码与支付渠道**业务规则的唯一权威**；数据库约束见[权益与兑换码数据约束](../database/entitlements-and-redemption-constraints.md)，接口契约见[API 契约与 MVP 验收](../backend/api-contract-and-mvp-acceptance.md)。

## 1. 统一公共能力

- 全平台复用 Supabase 用户身份；按用户及产品确定有效权限。
- 多产品共用必要的授权来源、订单/支付状态、订阅生命周期（续费、取消、退款结果）和可靠的权益同步。
- **每个产品独立定价、订阅和 Pro 资格**；购买某产品会员不自动授权另一产品。
- 公共计费只管理必要的计费事实与产品级权益关系；不接管各产品业务项目、任务和内容。
- **业务功能和额度完全属于 SaaS**：Core 不声明也不返回产品具体 `features/limits`、导出权限、AI 次数、容量配额或用量；各 SaaS 自行配置和计量并在可信产品后端实施。AisenLens 自备 AI Key、R2 私有备份依照原有 SaaS 安全流程，但不以 Core 通用功能引擎管理。
- 计费事实来自可信流程，重复或延迟的通知需要可靠处理；避免权益状态与实际订阅长期不一致。
- 首版 Admin 管理**产品、成员、Pro 资格/期限与自有兑换码**；外部订单、订阅与退款管理随支付渠道接入再增加（见[Admin 管理前端](../applications/admin-console.md)）。人工修改他人权益、退款等敏感操作必须经可信服务端，浏览器不持有高权限密钥。

## 2. 权益来源与支付接入顺序（当前有效，唯一权威）

| 顺序 | 机制 | 阶段与定位 |
| --- | --- | --- |
| **1** | **AisenCore 平台自有兑换码** | **优先建设的基础授权入口**；React-admin 创建兑换码，由平台所有者人工分发，用户兑换成功后获取对应产品的会员权益。不是爱发电的内置兑换码，也不依赖任何支付平台 |
| **2** | **爱发电（Afdian）** | 初期**暂定**的外部打赏/收款渠道；本项目尚未集成，需再核实适用规则及可靠的订单匹配 |
| **3** | **支付宝个体工商户支付** | 未来注册个体工商户并满足商户资质后再开发，首期不接入 |
| **4** | **Stripe** | 更后期视商户资格和国际收款需求再评估，首期不接入 |

**统一权益，不统一各渠道内部机制**：兑换码、可信订单或管理员人工授予都只是**授权来源**，统一写成同一种“产品授权记录”（见 §3）；各 SaaS 只读取公共权益结果，更换收款方式不影响产品的 Pro 判定。不为尚未接入的渠道建设多支付插件平台，只保留 `source_type` / `source_ref` 这一精简的来源标识。

**爱发电回调可靠性（阶段 2 接入时适用）**：官方提供 Webhook 与订单查询 API，且提示 Webhook 可能漏推、重复；不能仅凭收到请求或前端成功页面开通 Pro。必须以可信端核对订单真实性与状态、所属方案和产品、对应 AisenCore 用户，再以 `source_type='afdian' + 订单号` 幂等写入授权，并考虑漏推补查。具体关联方式、核验方案、平台规则及订阅/退款支持程度**待正式接入时确认**。

## 3. MVP 轻量产品会员资格逻辑模型

| 核心实体 | AisenCore 保存的最小事实 | 不保存的产品业务规则 |
| --- | --- | --- |
| `products` / `product_memberships` | 产品运行状态和每产品成员准入 | AI/导出/文件/配额/本地功能开关 |
| `entitlement_grants` | 同用户、同产品的独立入账来源、天数、历史日期、永久及撤销事实、幂等 | 功能快照、业务额度和可用次数 |
| `pro_credit_accounts/pro_credit_entries` | 有限 Pro 的结算时点、入账/消费/撤销/剩余秒数 | SaaS 的次数、容量或按量计费 |
| `redemption_codes` / `redemptions` | 指定产品 Pro 授予期限、批次及核销事实 | 特定 SaaS 的业务能力 |
| 管理员与审计 | AAL2、受控发码/直授/撤权的操作事实 | 产品内部功能配置 |

**Free 与 Pro**：可信摘要按同用户、同产品判断当前有效永久 Pro 或有限剩余信用；有其一才为 `pro`，否则为 `free`。有限信用不能用单笔 Grant 的 ends_at 判定。账号 blocked、产品暂停、成员 left/suspended 独立限制在线访问；不写 users.is_pro，不创建 Free Grant。匿名 AisenLens 本地 Free 不依赖 Core。

**期限不是套餐功能版本**：固定天数和永久是时间参数，不是不同功能套餐。人工与兑换成功时立即计入同一信用账本，一天精确 86400 秒；有限余额按 FIFO 消费，撤销只取消该笔未消费部分，其他余额连续接续。有效永久 Pro 冻结有限剩余额，撤销永久后恢复消费；已有有效永久时拒绝继续人工入账或兑换，不消费码。当前直授只接受固定天数/明确永久，不允许手输预约起止。Grant 是独立事实，当前综合终点只以服务端摘要 effective_ends_at 为准；普通授权撤销保留来源和审计。

**业务归属**：各 SaaS 自行管理 Free/Pro 功能、导出规则与额度计量。AisenCore **不保存** `products.free_features/free_limits` 或 `plans.features/limits`，不按功能键检查 `capability`、不求功能并集与额度最大值，也不为更新产品功能创建公共套餐版本。AisenLens 私有配置 R2 备份属于其专项可信 Edge/存储模块，按已有存储安全流程执行。见[唯一职责边界](./membership-qualification-boundary.md)。

## 4. 自有兑换码 MVP 规则

**现行单次码规则**：

| 属性 | MVP 规则 |
| --- | --- |
| 授权范围 | **首期仅限指定产品的 Pro 资格**；Free 是默认配置，不得发行 Free 兑换码 |
| 授权时长 | 当前发行仅固定天数；永久码发行政策未批准，不默认开放 |
| 可使用次数 | 每码全局最多成功一次；max_redemptions 固定 1，不支持多人复用 |
| 码本身有效期 | 可选截止时间，过期后不可再兑换 |
| 批量创建 | 一次管理请求可按相同配置生成多张码（单次数量上限在实施时设定） |
| 撤销 | 撤销码只阻止后续兑换；**已产生的授权不受影响**，如需收回由管理员单独撤销对应授权 |
| 绑定指定用户 | 首版不做，确有需要再加 |

**已发行码与期限预设**：运营者随后修改/隐藏 30/365 天快捷选项，不能影响已经发行码的产品、Pro 资格或首次保存的 grant_duration_days。旧码自身有效、未撤销、次数未用尽且成员/产品准入符合时按原时长兑换；停止旧码必须明确撤销。既有 Grant 不因功能发布而被重写。

**最小安全要求**：

- 码由可信服务端以安全随机数生成，**有效熵不低于 128 bit**（例如至少 26 个等概率 Base32 随机字符，扣除校验位后仍应达到阈值），统一大小写/连字符规范再计算哈希；绝不使用可猜测序列号、时间戳或非安全随机数。
- 数据库只保存规范化码的**SHA-256 哈希**（高熵码足够抵御离线猜测）；明文仅在**创建成功的首次响应**中提供管理员当次复制/下载，之后不可再次获取或导出，不写日志、审计、浏览器持久存储或监控事件。首次响应丢失只能撤销旧批次并重新发码，不能恢复明文。
- 兑换 RPC **在数据库内按 `auth.uid()` 限流**：每用户滚动 15 分钟最多 10 次失败尝试；达到限额回复 `RATE_LIMITED` 并给出可重试时间，外层可再配置 IP/WAF 防滥用。对**未兑换过该码的用户**，无效、过期、撤销、用尽统一对外返回 `REDEEM_CODE_INVALID`，不能暴露码状态；对**已兑换过该码的本人**返回 `REDEEM_ALREADY_USED`，该分支优先于码随后用尽、过期或撤销的判定（但不绕过身份、平台账号限制和限流）。**业务拒绝采用带 `code` 的结构化结果而不是抛出数据库异常**，使失败次数即使业务拒绝仍可提交；数据库技术故障仍抛异常使整个事务回滚。成功写入授权、兑换与成员审计必须同事务，绝不能在失败时扣码。
- 兑换结果不明（如超时）时，客户端先查询本人授权/兑换记录再决定是否重试；重复提交同一码由“同一用户同一码一次”的约束保证不重复授权。**批量发码请求必须携带独立 `request_id` 幂等键**；重复请求不能重新生成新码，已丢失的明文不可从数据库恢复，只能受控作废并以新请求重新发码。

**兑换与错误隔离（DEC-01 已批准 A）**：正式用户兑换签名为 `redeem_code(product_key, code)`；不可信 product_key 是用户意图，不是鉴权来源。身份/blocked/限流后先核对声明产品及该产品的 `left/suspended` 状态；这些成员状态对任何码一律同样拒绝（且计失败窗口），**不查码表**；成员 none/active 才允许查码，未知/跨产品/撤销/过期/用尽码统一 `REDEEM_CODE_INVALID`。已兑本人判重在声明产品准入之后，成功时才为 none 创建成员。迁移不得留下能按码探测的旧单参入口。保留现行高熵/每用户限流/技术错误全事务回滚合同。

**已有永久 Pro 的保护**：同用户/同产品已有当前有效、未撤销永久 Pro 时，人工和兑换都拒绝重复入账；兑换不耗码、不创建成员/Grant。本人同码已成功重放优先返回 REDEEM_ALREADY_USED，身份、成员和限流门禁仍先执行。当前实现由信用账本迁移统一，相关真实 HTTP 子项见 TODO；不沿用旧“尚未本地安装”的状态描述。

## 5. 授权与产品成员状态的关系（唯一权威）

**成员资格与授权事实相互独立**：退出或封禁不自动删除订单、撤销授权、终止订阅或清空 Pro；时效、试用与额度不因退出暂停或重置。重新加入只使用仍有效且未撤销的权益。完整成员规则以[产品成员生命周期](./membership-lifecycle.md)为准。

2026-11-02当前Lens流程先在邮箱确认/已确认登录/会话恢复时建立Free关联，兑换仅用于后续升级Pro，不是加入产品的前提。下表“无记录时兑换”描述直接受保护API的原子语义，不能据此让客户端等到兑换才关联；查询/反馈自身仍不建成员。

| 授权来源 | 账号被平台限制 | 尚未加入（无记录） | `active` | `left` | `suspended` |
| --- | --- | --- | --- | --- | --- |
| **用户主动兑换** | 拒绝 | 视为首次合法使用：**同一事务内**创建 `active` 成员（写 `join` 事件）并完成兑换 | 正常兑换 | **拒绝**，提示需先明确重新加入；码不被消耗 | **拒绝**；码不被消耗 |
| **管理员人工授予** | 拒绝 | 拒绝；先独立加入产品 | 产品 active 且无有效永久时允许入账 | 拒绝，不隐式恢复 | 拒绝，不隐式解封 |
| **外部支付回调**（阶段 2） | 只写授权 | 只写授权，不创建成员 | 写入 | 只写授权，不恢复成员 | 只写授权，不解封 |

任何授权来源都**绝不能**把 `left` / `suspended` 自动变回 `active`。对已付款但成员已退出或被封禁的用户如何告知、是否退款，随支付渠道接入时确定。退出产品**不等于取消自动续费**，有实际自动续费渠道时须提供独立的取消路径。

## 6. 首期权益类型与在线执行

首期 Core 能力仅是产品级 Pro 资格、授权来源/有效期/撤销、会员状态认证以及兑换码、必要审计；具体功能开关/数量额度/云端存储配额属于 SaaS。

| 已确认支持 | 权益能力 | 规则待定 |
| --- | --- | --- |
| 功能开关 | SaaS 自行定义 Free/Pro 能使用什么；Core 仅回答会员资格 | 实际产品配置归该 SaaS |
| 数量/使用额度 | SaaS 自行保存上限、计数和核销；Core 不返回额度 | 产品可信业务执行端 |
| 云端存储/备份配额 | AisenLens 等产品的业务库/Edge 管理，不在 Core Pro 模型 | 产品属主与对象策略 |
| 有效期与订阅到期 | 当前有限信用/有效永久及综合 effective_ends_at；逐笔来源和撤销另记 | 宽限期、取消与退款处理 |

| 产品方式 | 权益校验职责 |
| --- | --- |
| 云端业务型 | 产品的云端可信后端在受保护操作时查询公共权益并实际校验，不能仅凭前端展示 |
| 本地优先型 | 公共权益为权威；启动联网校验 + 运行中按产品关键操作合理复核，详见[本地优先专项](../applications/local-first.md) |
| 混合型 | 按本地与云端操作的执行位置分别校验 |

## 7. 不做

- 不设计所有产品通用的一份 Pro 会员，不把业务数据迁移到公共计费数据库。
- 不预先设计大型多支付渠道插件、企业多租户计费或**按量收费**系统；本次确认的是**使用量限制**，不是按用量收费。
- 不把爱发电平台内部的兑换码当成 AisenCore 自有兑换码；不因爱发电临时采用就锁定未来渠道。
- 不在当前阶段对接支付宝个体工商户支付或 Stripe；不假设初期渠道支持所有自动扣费与退款行为。
- 不在首期建设公共用量账本、高级统计、综合运营中心或面向产品运营团队的权限平台。
- 不以仅前端的权限判断代替云端受保护操作的服务端校验，不承诺完全防止篡改客户端后的本地复制。

## 8. 数据位置

套餐、授权记录、兑换码与兑换记录**存放于公共 Supabase PostgreSQL**，因为兑换核销与授权写入必须在同一事务内完成。外部渠道的订单/订阅原始事实是否同库，在接入对应渠道时决定。
