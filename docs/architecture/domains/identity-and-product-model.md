# 统一身份、产品目录与成员关系模型

> 状态：逻辑领域模型已确认；字段是架构层候选，公共 API 逻辑已确定；产品/成员表与可信状态变更 RPC 已在本地实现并有 SQL/实际 HTTP 的部分测试证据；完整端到端负例及生产部署尚未验收。

## 1. 目标和身份边界

AisenCore 统一管理多个独立 SaaS 的**公共账号、产品目录、产品成员资格**以及独立的产品级权益；各 SaaS 继续拥有自己的项目、任务、内容、项目协作角色和业务资源权限。公共成员管理不等于统一全部产品业务数据或企业多租户 RBAC。

- **Supabase Auth** 是公共身份、登录、会话的权威来源；首版邮箱和密码。使用稳定 `user_id` 作为跨产品主体标识，邮箱不作为业务主键；统一身份不自动保证跨域无感 SSO。
- **公共产品目录** 是产品存在、产品标识和产品生命周期的权威来源。
- **公共产品成员关系** 是用户是否属于某产品、是否处于退出或限制状态的权威来源。MVP 平台级跨产品访问限制已确定由独立的 `platform_account_restrictions`（仅 `blocked`）控制，不批量重写产品成员状态。
- **公共会员权益** 是某用户对某产品当前 Pro 资格、授权时效/来源/撤销的权威来源，与成员独立；功能开关、使用额度与备份配额由 SaaS 负责，不进入 Core 会员模型。
- **产品业务系统** 决定用户是否能操作具体项目、任务、文件和协作空间。
- 平台管理权既不等于登录，也不等于产品成员资格或 Pro 权益。

对受保护的产品操作应分别判断身份、产品状态、成员状态、相应权益（如有）与产品业务资源权限；不存在“登录了就自动有 Pro”或“有 Pro 就是管理员”的捷径。

## 2. 公共逻辑实体

| 领域实体 | 最小职责与标识 | 决策边界 |
| --- | --- | --- |
| `auth.users`（Supabase Auth） | `user_id`、邮箱与认证/会话资料 | 不自研密码和身份系统 |
| `products` | 内部不可变 `product_id`、唯一稳定 `product_key`、名称、状态、必要时间 | 产品元数据公共管理，不存各 SaaS 业务项目 |
| `product_memberships` | `membership_id`、`user_id`、`product_id`、状态、首次加入及更新时间 | 每个 `user_id + product_id` 最多一条当前关系 |
| `membership_events`（逻辑） | 关键状态变化的主体、操作人、原/新状态、原因与发生时间 | 已确定仅作最小审计；当前成员状态以 `product_memberships` 为权威，不回放事件计算 |
| 平台管理员授权（建议 platform_admins） | 可信 user_id、是否有效及最少授予信息 | 复用现有 Auth 身份，名单由可信管理接口维护；不做复杂 RBAC |
| 用户公共显示资料 | 可选昵称存于 Supabase Auth 用户可编辑资料，跨产品显示 | 不另建资料表/头像/主页；可编辑 metadata 绝不能用于鉴权、管理员或 Pro 判断 |
| `entitlement_grants` / `redemption_code_batches` / `redemption_codes` / `redemptions` | 按产品 Pro 资格、可信授予时段/来源/撤销、兑换码与核销事实 | 无公共业务套餐功能版本、功能开关或额度；具体功能策略属 SaaS，参见[资格边界](./membership-qualification-boundary.md) |
| 各 SaaS 业务数据 | 项目、任务、内容、产品内协作权限和文件元数据 | 归各产品自己管理 |

以上是逻辑实体与推荐字段，已确认采用当前状态表 + 最小事件审计表；首批基础表 DDL/索引已在本地迁移；其余关系、RPC/云端部署与 API 行为尚待实施测试。数据库不变量与事务规则详见[数据库逻辑约束与最小审计模型](../database/database-constraints-and-audit.md)。公共身份、产品与成员核心使用已选择的 Supabase 托管 PostgreSQL；产品业务数据可逻辑隔离或物理隔离，无“一产品一 Supabase Project”强制要求。

## 3. 产品注册与生命周期

产品由本人或少数可信平台管理员注册，不开放第三方开发者自行入驻。建议产品目录包含 `id`、稳定唯一 `product_key`、`name`、可选 `description`、`status` 和创建/更新时间；套餐、价格、R2 位置和具体业务库配置不混入产品目录核心。

产品生命周期：`draft`（尚未开放）↔ `active`（可用）↔ `suspended`（公共受保护服务暂停），具体允许的管理流转需可信接口校验。暂停产品**不**自动删除成员、会员授权、订单和业务数据，也**不**将所有成员改为 suspended；恢复产品也不自动解除个人封禁。产品永久下线/删除、已购权益补偿和运维时效留待专门策略确定。

## 4. 成员创建规则

- 注册平台账号时不自动关联全部 SaaS；首次打开应用或匿名使用免费本地能力也不产生公共成员记录。
- **首次实际使用某产品需要账号的服务时**，认证后由可信公共服务端检查账号、产品可用性、产品身份与当前成员记录；不存在才幂等创建 `active`。
- 已存在 `active` 则沿用；已有 `left` 或 `suspended` 一律不因登录、重试、启动应用、兑换码或支付事件自动恢复。
- 同一用户同一产品只有一条当前成员关系；设备并发、请求超时重试必须防止重复创建与旧状态覆盖新封禁。不能仅靠前端预查询实现原子性。
- 成员授权与会员权益并不等价；兑换后取得的授权事实可在成员退出期间独立保留。

完整状态转换、例外和退出后的复用规则见[成员生命周期](./membership-lifecycle.md)；MVP 首次 SaaS 接入与公共 API 调用边界见[公共 API 专项](../backend/public-api-and-saas-integration.md)。

## 5. 三种产品模式

| 模式 | 加入触发 | 访问与数据边界 |
| --- | --- | --- |
| 本地优先 | 首次使用需要公共登录的服务（如会员或私有配置备份） | 匿名离线免费功能不触发加入；本地视频、项目、AI 密钥和结果不因成员管理上传；Pro 启动在线校验和运行中合理复核 |
| 云端业务 | 首次实际进入需要账号的产品服务 | 可信云端校验成员/产品状态和业务资源权限；具体项目数据由产品拥有 |
| 混合型 | 首次使用需登录的云端/账号能力 | 本地免费与云端受保护能力分别判断，产品数据按本地/云端归属管理 |

公共成员关系不等于各 SaaS 的项目成员角色。产品 A 的 Pro 不授权产品 B 的 Pro，也不授权访问产品 A 内的任意他人资源。
