# 平台管理员权限与公共账号生命周期

> 状态：MVP 统一用户领域的架构结论。**已决定**：首版建设仅含 `blocked` 的平台级账号限制；账号注销请求首版由人工受理；管理员会话必须完成 MFA。数据清理时限、法律保留期限与具体 SQL 仍需上线前确定。平台级账号与产品级成员限制是独立维度。
>
> **现行产品决定**：正式公众注册、**一名实际运营者**做日常 Admin/发码，且**Admin TOTP MFA 已明确纳入 MVP**；有效会话期间不逐次触发额外认证挑战，但每个受保护请求必须校验当前 `aal2` 与管理员资格。主管理员备用恢复方式及真实独立人员/身份仍未落实，须在 Admin 开通前完成恢复演练；当前的长期安全规则与恢复要求见下文 §1/§1.1；[当前待办与未验证项](../../Plans/TODO.md)仅保留批准依据。

## 1. 平台管理员：最小可信机制

首期仅本人或少数可信管理员使用 **React-admin**。采用极简的平台管理员资格记录（逻辑名 `platform_admins`，字段见[数据库约束](../database/database-constraints-and-audit.md#25-platform_admins平台管理员资格)）：没有记录或 `active=false` 即不是管理员。

- **初始所有者**：通过受版本管理的迁移种子或受控 SQL 写入，绝不提供“注册即管理员”的公开入口。
- **后续增减与保底可用性**：只能由现任管理员经管理函数操作，写入 `admin_audit_log`。`RevokeAdmin` 与 `BlockAccount` 共同保证至少保留一名**合格管理员**（`platform_admins.active=true` 且未被平台 `blocked`），不能通过撤销资格或全局封禁变相锁死最后的管理入口；管理员不能绕过当前权限检查修改自身资格。
- **MFA**：管理员账号启用 Supabase Auth 自带的 TOTP MFA；`private.is_platform_admin()` 同时要求当前 JWT 为 `aal2`，未完成第二因素的会话既不能读取管理数据，也不能调用管理函数。不自建 2FA 框架；管理员丢失 MFA 设备必须走预先批准的受控身份恢复流程，不以直接修改 Auth 内部表或绕过 `aal2` 作为普通恢复手段。
- **MVP 必做 + 低打扰边界**：实现 TOTP enroll/challenge/verify、新 `aal2`、正常会话刷新后的等级验证和失设备受控恢复；**每个管理读或管理 RPC 在原请求内查 `aal2` 及实时管理员资格，但不得在正常有效会话内另发 MFA Auth 网络请求或逐操作弹 TOTP**。管理 UI 的 `checkAuth/canAccess` 短期缓存只节流导航；被撤权/blocked 后下一次服务端操作照样拒绝。

MVP **不**建立通用 `roles/permissions/policies` 角色引擎或多级管理员角色；若未来不同管理员需要差异化权限，再从明确用例扩展。React-admin `authProvider` / `canAccess` 只负责 UI 提示，**每个管理函数必须自行复核当前资格**。管理员身份不放在可自行编辑的 `user_metadata`，也不依赖 JWT 中缓存的角色声明；撤销后下一次管理调用立即被拒绝。

### 1.1 单人运营 MFA 恢复控制（A-04）

**“至少一名合格管理员”是数据库状态约束，不等于有人持有可用 TOTP 因子及登录会话。** 公开生产运营前必须确认恢复责任、保管主体和真实演练证据，否则生产恢复准入为 **BLOCKED**。

1. **事前预防**：使用已验证的 Supabase Auth 能力配置两个独立 TOTP 因子/设备，或另行批准等效的离线应急恢复方案；离线隔离保管应急材料，凭据/密钥不得进入 Git、CI、日志或公开工单。
2. **触发与身份核验**：主管理员设备丢失、会话失效或因素遭窃时，必须由事先指定的可信责任人和独立核验手段启动受控恢复；不得设允许 `aal1` 管理操作的应急后门。
3. **受控恢复**：优先验证官方 Supabase Auth 管理 MFA API 对因素撤销、重新注册的实际支持。任何超出官方流程的 SQL/维护操作必须另行审批、备份、隔离执行、审计与具备回滚步骤；不得把直接改写 `auth.mfa_factors` 当作常规恢复方式。
4. **重新加固**：撤销已失控因素并令受影响会话失效，在可信设备重新 enroll/challenge/verify 获得新 `aal2`，再复核当前管理员名册与非 blocked；审计保留主体、时间、目标和动作，**不记录 TOTP 秘钥**。
5. **上线前演练**：在隔离环境验证主设备丢失、全部因素不可用、旧会话拒绝、恢复失败和回滚，并保存可复核证据。**未经演练不得公开生产上线**。

本节仅定义安全控制，**不虚构**已存在的备用人员、设备、SDK 功能或实际通过的恢复测试。普通用户不因此强制 TOTP。

## 2. 最小管理权限矩阵

| 管理操作 | 普通用户 | 平台管理员 | 注意 |
| --- | --- | --- | --- |
| 查询本人身份、产品、成员与权益 | 允许 | 允许 | 不暴露其他用户隐私 |
| 首次加入、本人退出、明确重新加入、兑换 | 允许按规则 | 以本人身份亦可 | 不能跳过 `left/suspended` 规则 |
| 查询跨用户公共成员、权益、必要审计 | 禁止 | 允许 | 不自动访问各 SaaS 私有项目 |
| 注册/发布/暂停/恢复公共产品，维护套餐 | 禁止 | 允许 | 产品暂停不批量修改个人成员 |
| 封禁/解封产品成员 | 禁止 | 允许 | 解封恢复封禁前 `active/left` |
| 发行/撤销兑换码、人工授予/撤销权益 | 禁止 | 允许 | 规则见[计费与权益](./billing-and-entitlements.md) |
| 平台级封禁/解除 | 禁止 | 允许 | 区分产品封禁与平台级限制；不可封禁最后一名合格管理员 |
| 账号注销 | 经人工渠道提出本人请求 | 按人工流程协调 | MVP 不提供自动接口 |
| 读取 SaaS 业务文件/项目 | 按该 SaaS 业务授权 | **不因平台管理员身份自动允许** | 产品数据独立 |

## 3. 三层状态与生效顺序

| 层级 | 当前权威 | 影响范围 |
| --- | --- | --- |
| Supabase Auth 身份/会话 | Supabase Auth | 用户身份验证、登录、重置与会话 |
| 平台级账号访问限制 | `platform_account_restrictions`（仅受限账号有记录） | **所有**产品受保护公共服务 |
| 产品成员 | `product_memberships` | 指定产品成员资格（`active/left/suspended`） |

**MVP 决定**：建设 `platform_account_restrictions`，`kind` 首版只有 `blocked`（字段见[数据库约束](../database/database-constraints-and-audit.md#26-platform_account_restrictions平台级账号限制)）。理由是成本极低（一张小表 + 准入函数里的一次查询），且能覆盖仅靠 Supabase Auth 封禁时“旧 JWT 在到期前仍然可用”的窗口。

- 它不是用户主档：Supabase Auth 仍是身份权威，该表只控制跨 SaaS **业务准入**；普通用户无法读写。
- 所有需登录的公共准入、加入、重新加入和兑换函数**先检查该限制**，再检查产品与成员状态；各独立 SaaS 通过公共准入结果获知阻断。
- 全局阻断不批量改写各产品成员状态、权益、订单或文件；解除后各产品按原成员/权益状态重新计算，不自动把 `left/suspended` 变为 `active`。
- **管理员保护**：`BlockAccount` 若目标是合格管理员，必须在与 `RevokeAdmin` 一致的事务级串行化保护下核验变更后仍有至少一名合格管理员，否则返回 `STATE_CONFLICT`，不施加限制；并发封禁/撤权也不得分别通过检查而共同锁死后台。所有者或仅剩一名管理员的 MFA 设备丢失、Auth 账号实际无法登录属于受控运维恢复场景，不以名单数量假称能保证真实登录可用。
- 需要同时阻止登录时，管理员 Edge Function 可在数据库 `BlockAccount` 通过可信校验后额外调用 Supabase Auth 的用户封禁能力；**不得对合格管理员跳过共同保底检查而单独发起 Auth Admin 封禁**。Auth 用户封禁与数据库事务不能当作跨系统原子动作，应处理部分失败并保留受控恢复入口。**仅禁用登录或登出会话不足以立即废止已签发的 JWT**，所以限制表仍是业务准入的判断依据。严格实时撤权仍受进行中的业务请求、离线本地 Pro 与已签发文件 URL 的边界限制。

## 4. 账号生命周期与删除

1. **注册/待验证**：沿用 Supabase Auth 邮箱密码，并**开启 Supabase 的 Confirm Email**；未确认邮箱的用户拿不到会话，因此无需应用层再做“未验证不可用”检查。产品成员不会在注册时自动创建。
2. **正常用户**：公共 Auth 身份独立于任何产品成员；同一用户可以在 A 产品 `left`、B 产品 `active`、C 产品尚未加入。
3. **产品级限制**：某产品 `suspended` 不影响其他产品；解封恢复封禁前状态。`left` 是用户自愿退出，不等于注销平台。
4. **平台级封禁**：见 §3。
5. **账号注销请求（MVP）**：人工核验、受控清理及必要合法留存例外已定；以专门支持邮箱人工受理为渠道方向，**具体渠道留待上线前确定**，此前不开放可成功提交的申请按钮、不假报已受理。单人运营者核验身份后可先 blocked，再按批准清单清理云数据与必要留存，最后处理 Auth 身份并核验；不建自动删号 RPC，不删除本机项目/配置。天数、法律例外与通知仍需公开前确定，不声明未执行的步骤已完成。
6. 用户仅退出某产品，不进入注销流程。

**公开上线前的人工注销验收**：第三阶段在获授权的隔离测试账号上演练身份核验、限制访问、按批准清单处理反馈/备份对象与必要保留记录、最后处理 Auth 身份并核验。保留逐步执行结果，注入对象清理或 Auth 处理失败后从未完成步骤继续，不重复已完成删除或误报全部完成；核查对象残留、旧会话/短 URL 有效窗口及本机数据不变。渠道、留存清单与执行责任未确定或演练未通过时不能将注销能力标为已验收；隐藏申请按钮不替代该上线门禁，不新增自动删号接口。

**退出 ≠ 注销 ≠ 删除业务数据 ≠ 取消自动续费**。各产品保留窗口、删除时限、备份清理时效和法律保留期限属于正式上线前的独立政策，不在此虚构全局天数。自助注销接口、`deletion_pending` 等受限状态与跨产品自动删除编排，推迟到用户规模或合规要求确实需要时再设计。

## 5. 最少管理审计

- 成员 `suspend` / `restore` 写 `membership_events`；产品状态、套餐、兑换码、人工授权、管理员授予/撤销、平台级封禁/解除写 `admin_audit_log`，均与业务变更**同事务**（[数据库约束](../database/database-constraints-and-audit.md#27-admin_audit_log非成员类管理审计)）。
- 审计记录操作人、目标、动作、精简前后状态、可信时间与必要原因；不复制邮箱等多余个人信息，绝不包含兑换码明文、令牌或密码。
- 成员事件表只记录成员事件，不混入密码重置或登录历史；登录类安全记录沿用 Supabase Auth 自带日志。
