# 平台管理员权限与公共账号生命周期

> 状态：MVP 统一用户领域的架构结论；具体管理员初始名单、数据清理时限、法律保留期限与 API/SQL 实现仍需上线前确定。平台级账号与产品级成员限制是独立维度。

## 1. 平台管理员：最小可信机制

首期仅本人或少数可信管理员使用 **React-admin**。推荐一个极简的**平台管理员注册记录**（逻辑名称 `platform_admins`）：`user_id`（关联 Auth 主键且唯一）、`active`、`created_at`，必要时可记录授予人/时间；普通用户没有记录或 `active=false` 即不是管理员。初始所有者必须通过可信运维/部署引导配置，绝不能以公开“注册即管理员”入口自行授予。后续增减管理员也只能经服务端已经验证的管理员授权流程。

MVP **不**建立通用 `roles/permissions/policies` 角色引擎，也不强制 owner/editor/auditor 多级继承模型。少数高风险动作按服务器端显式权限检查；若未来不同管理员需要差异化权限，再从明确用例扩展。React-admin `authProvider`、`canAccess` 负责 UI 提示，不能代替 Edge Functions 对敏感请求的复核。

管理员本人仍使用 Supabase Auth 登录；管理员身份不放在可自行编辑的 `user_metadata`，也不能仅凭陈旧 JWT claim 决定敏感权限。管理员停用/撤销后，下一次敏感 API 必须检查当前可信状态；对高风险操作可增加重新验证会话有效性/近期登录的条件。

## 2. 最小管理权限矩阵

| 管理操作 | 普通用户 | 平台管理员 | 注意 |
| --- | --- | --- | --- |
| 查询本人身份、产品和成员状态 | 允许 | 允许 | 不暴露其他用户隐私 |
| 首次加入、本人退出、明确重新加入 | 允许按规则 | 以本人身份亦可 | 不能跳过 `left/suspended` 规则 |
| 查询跨用户公共成员、必要审计 | 禁止 | 允许按最小范围 | 不自动访问各 SaaS 私有项目 |
| 注册/暂停/恢复公共产品 | 禁止 | 允许 | 产品暂停不批量修改个人成员 |
| 封禁/解封产品成员 | 禁止 | 允许 | 解封恢复封禁前 `active/left` |
| 发行/撤销兑换码、人工改权益 | 禁止直接写入 | 通过独立可信管理流程 | 计费与权益专项负责业务规则 |
| 全局禁用账号、启动账户注销 | 仅可提交本人合法注销请求 | 可信管理接口按条件操作 | 区分产品封禁与平台级限制 |
| 读取 SaaS 业务文件/项目 | 按该 SaaS 业务授权 | **不因平台管理员身份自动允许** | 产品数据独立 |

## 3. 三层状态与生效顺序

| 层级 | 当前权威 | 影响范围 |
| --- | --- | --- |
| Supabase Auth 身份/会话 | Supabase Auth | 用户身份验证、登录、重置与会话 |
| 平台级账号访问限制 | 公共可信管理的当前限制记录（按需）+ Auth 管理 | **所有**产品受保护公共服务 |
| 产品成员 | `product_memberships` | 指定产品成员资格（`active/left/suspended`） |

建议对于必须实现“全平台下一次关键校验立即拒绝”的账号封禁，引入**一张仅保存受限账号的极小控制表**（逻辑名 `platform_account_restrictions`，`user_id` 唯一、`kind`＝`blocked` 或 `deletion_pending`、必要时间/原因，普通正常账号无记录）。这不是重复用户主档：Supabase Auth 仍是账号身份权威；该表仅控制跨 SaaS **业务准入**。普通用户无法直接修改它。所有需登录的公共授权/加入接口先检查该限制，继而检查产品和成员状态；各独立 SaaS 通过公共授权结果获知阻断。全局阻断不批量改写每个产品的成员状态、Pro、订单或文件。

同时按现有 Supabase Auth 管理能力限制后续登录或刷新会话；**仅禁用/登出会话不足以立即废止所有尚未到期的 JWT**。目前不强制每个小请求再去 Auth 服务做远程会话校验；高度敏感的管理/账号操作可进一步检查当前会话或要求近期重新认证。严格的实时撤权仍受已经开始的业务请求、离线本地 Pro 和已签发文件 URL 的边界限制。

如果首期**并不交付全局账号封禁操作**，可以先不建该异常表、仅实现 Auth 自带会话管理；但在正式提供全局封禁之前必须具备等价的统一可信阻断机制。此表是针对明确跨产品实时阻断需求的最小增量，而非默认维护每用户完整资料。

## 4. 账号生命周期与删除

1. **注册/待验证**：沿用 Supabase Auth 邮箱密码；产品成员不会在公共注册时自动创建。若要求邮件确认，未完成确认前不允许进入正式受保护账号业务。
2. **正常用户**：公共 Auth 身份独立于任何产品的成员；同一用户可以在 A 产品 `left`、B 产品 `active`、C 产品尚未加入。
3. **产品级限制**：某产品 `suspended`，不影响其他产品的正常成员资格；解封恢复封禁前状态。产品 `left` 是用户自愿退出，不等于注销平台。
4. **平台级封禁**：所有需要公共账号的云端受保护操作拒绝，当前各产品成员状态不变；解除全局限制后分别依照各产品原成员/权益状态重新计算，不自动把 `left/suspended` 变 `active`。
5. **账号注销请求**：通过独立、验证本人身份的流程受理，可采用待处理的访问限制，必要时停止新授权；但不自动等同“立即删除所有数据库记录”。
6. **实际注销与清理**：根据产品数据库/R2 私有文件、当前授权、订阅/退款、审计与财务法定留存要求协调处理；确认清理与外键引用策略后，才执行 Auth 身份清理。已完成清理的 SaaS 业务数据不能承诺重新加入后恢复。

**退出 ≠ 注销 ≠ 删除业务数据 ≠ 取消自动续费**。注销时需要明确导出/取消订阅提示与必要用户通知；各产品具体保留窗口、删除请求时限、备份清理时效和法律保留期限属于正式上线前的独立政策，不在此虚构一个全局天数。

## 5. 注销的 MVP 交付形态

不用首版就搭建跨产品自动数据删除编排平台。最小可行是：用户经可信入口提交并验证请求 → 受限状态或处理中的记录防止并发新加入（是否暂停根据法律/产品政策）→ 平台管理员或专门受保护流程按明确清单协调各 SaaS 数据、R2、必要财务数据 → 保留依法必须保存的最少记录 → 最后完成账号删除/匿名化及核验。

对外只声明实际已完成的步骤；受理请求不等于所有产品数据已经删除。若用户仅退出某产品，仍不进入注销清理流程。

## 6. 最少管理审计与风险

- 成员 `suspend` / `restore` 与成员审计同事务；公共产品发布/暂停、管理员授予/撤销、全局账号限制及注销执行需保留相应最小管理操作记录。
- 优先复用可信业务操作日志或一张小型管理审计记录，不强制独立通用审计平台。**成员事件表只记录成员事件**，不混入密码重置或所有用户登录历史。
- 操作人、目标、动作、前后状态、可信时间、必要原因；避免复制邮箱、令牌、密码等敏感内容。
- 管理员不能在未检查当前权限的情况下修改本人/他人的管理员资格；防止最后一个可恢复管理员被误停用的保护策略留到实际管理接口细化。
- 管理员登录与账户恢复应考虑 Supabase 已支持的 MFA 等安全能力，但不自行实现 2FA 框架；是否首发强制 MFA 与账号恢复流程在上线安全检查时确定。
