# Aisenhubsass 主架构

> 状态：以已确认需求为基础的当前架构讨论稿；未批准实施
> 需求依据：[当前统一需求](../spec/requirements.md)；详细技术选型见 [技术栈专项](./tech-stack.md)

## 1. 平台定位和边界

Aisenhubsass 为多个**相互独立的 SaaS 产品**提供有限且值得复用的公共基础能力。**统一必要的能力，不集中全部业务。** 目标是清晰、简单、可维护，避免无依据的过度抽象与过度防御。

| 范畴 | 当前方向 | 确定性 |
| --- | --- | --- |
| 身份与账号 | **Supabase Auth** 作为当前公共用户与身份管理基础；全平台共用账号 | 已确认 |
| 关系数据库 | **Supabase 托管 PostgreSQL**，保存必要的公共身份关联、产品与权益等结构化信息 | 已确认公共核心数据库；各产品业务库仍独立决定 |
| 可信服务端 | **Supabase Edge Functions**（TypeScript / Deno 兼容运行时）优先承接敏感公共业务逻辑与 API | 技术载体已确认；具体函数接口仍待设计 |
| 产品权益 | 按产品分别判定免费/付费功能与有效权益；A 的会员不能默认用于 B | 已确认 |
| 计费与权益来源 | **平台自有兑换码优先 → 爱发电初期暂定 → 支付宝个体户后期 → Stripe 更后期**；订单与兑换结果统一授予对应产品权益，各产品套餐/价格独立 | 阶段顺序已确认；兑换码规则、爱发电生产接入及支付细节待定 |
| 管理后台 | **React-admin（Marmelab）** 及默认 React / TypeScript / MUI 技术栈；**Cloudflare Pages** 托管 Admin 网站 | 框架、默认技术栈与 Admin 部署平台已确认；具体配置待实施 |
| 代码管理 | **GitHub / Git** 管理源代码与版本；后续可配置 Pages 自动构建与发布 | 技术平台已确认；仓库与发布流程未配置 |
| 产品业务 | 各产品分别管理自己的业务逻辑和结构化数据，尽量不与公共核心耦合 | 已确认独立性原则；物理数据库拓扑未定 |
| 文件对象 | **Cloudflare R2** 用于按产品需要保存云端用户文件及配置备份 | 平台已确定；接入和对象组织未定 |
| 迁移 | Supabase 托管优先，后续按规模评估自部署及可靠迁移 | 方向已确认；范围和验收未定 |

### 第一版公共能力范围（已确认）

第一版按**最小核心**推进：统一用户和账号、产品管理、按产品区分的会员与权益、**优先采用兑换码开通会员，随后按阶段对接外部支付**，以及必要的 Admin 管理功能。首期权益包括**功能开关、数量/使用额度、云端存储或备份配额、有效期/订阅到期**。**桌面端离线会员授权不属于首版必需，保留未来按产品实际需要扩展**。具体额度计算和实现方式按产品再定。

**首版账号**：Supabase Auth 邮箱与密码登录。将来可按实际支持情况添加手机号验证码、邮件验证码、免密链接、Google 或其他（包括需额外适配的微信）登录方式；正式开放注册前要确认邮箱确认、密码找回和邮件发送能力，不提前选定第三方发信/验证提供商。

**公共计费模式与推进顺序**：目标支持月付订阅、年付订阅、一次性永久购买和免费试用；各产品价格、权益独立。**先通过 React-admin 创建并由所有者分发平台自有兑换码开通会员，再暂定接入爱发电打赏与回调；支付宝个体户、Stripe 留待后续阶段开发**。兑换码和可信付款记录最终都映射为公共产品级权益；永久购买不应伪装成自动续费订阅。各渠道支持的具体续费形式、退款与试用规则待定，详见[计费与权益专项](./billing-and-entitlements.md)。

Admin 初期仅服务**本人或少数可信管理员**；仍需保护敏感管理操作，但**不预先建设**面向各 SaaS 运营团队的复杂角色平台。高级审计统计、综合运营系统等不是第一版目标；必要的支付可靠性记录和基础安全审计范围另行明确。

**技术选型概要**：内部 Admin 已确定使用 **React-admin 默认技术栈**，以 **Vite** 构建并部署到 **Cloudflare Pages**；源码使用 **GitHub** 管理。公共后端采用 **Supabase Auth、托管 PostgreSQL 和 Edge Functions**，文件对象使用 **Cloudflare R2**。Admin 敏感操作仍需服务端鉴权，不能暴露高权限密钥。具体依赖、框架默认组件、数据适配、部署关系和待定项集中维护在 [技术栈专项架构](./tech-stack.md)，主架构不重复展开。

**不做**：不采用 Payload；不默认复用已经舍弃的旧后端；除已选定的 React-admin 外，其他领域未确认需求前不选型；未经明确实施授权不安装/接入具体项目；不为假设中的未来需求建立复杂的通用框架。

## 2. 公共和产品专属能力

```text
                    ┌───────────────────────────┐
                    │   Aisenhubsass 公共能力    │
                    │  统一用户 / 产品级权益    │
                    │  轻量计费 / 公共管理能力   │
                    └─────────────┬─────────────┘
                                  │ 统一身份、按产品授权
                ┌─────────────────┼────────────────┐
                │                 │                │
           本地优先产品        云端业务产品       混合型产品
           本地业务/文件      独立业务数据       本地+云端业务
           可选配置备份       可选 R2 文件       按需存储
                └─────────────────┴────────────────┘
```

- 公共核心只存管理身份、产品权益及履行轻量计费/运营所必需的信息；**逻辑统一不代表所有数据要存入同一个 Supabase Project**。详见[计费与权益专项](./billing-and-entitlements.md)。
- 各产品自己的数据库、文件、本地存储、业务 API 是产品职责范围。统一身份和权益在不同产品中复用，但产品数据**不自动跨产品可见或互通**。
- 如产品有用户上传文件，**结构化业务记录**（任务、项目、文件归属等）与**文件对象**（图片、视频、PDF 等字节内容）可分别存于业务数据库和 R2。是否同库、独立库、单桶或多桶留待真实需求确定。详见[产品业务数据与文件专项](./product-data-and-files.md)。
- Admin 采用 React-admin 管理公共能力，**不是产品业务数据天然汇聚到公共库的理由**；也不要求所有 SaaS 产品必须采用 React/React-admin。

## 3. 不同 SaaS 产品模式及使用时机

| 模式 | 数据与执行在哪里 | 公共底座负责什么 | 需要额外考虑什么 |
| --- | --- | --- | --- |
| **本地优先** | 用户本地进行视频处理、生成、分析等；可直接调用用户选定的第三方 AI 提供商 | 登录、产品级权益、轻量计费；用户自主使用可选云端备份能力 | 启动时在线验证、运行中按产品复核；将来有需要再扩展离线授权；本地数据不经公共后端 |
| **云端业务型** | SaaS 产品自己的云端服务处理用户上传的业务数据，业务数据库按产品管理；文件本体可用 R2 | 同一账号和产品级权益、公共计费与管理 | 产品端数据权限、文件访问、成本、备份和删除 |
| **混合型** | 设备本地处理部分数据，云端产品服务处理用户主动提交的其他数据 | 相同公共身份/权益与计费，按需提供公共能力 | 明确何种数据留本地、何种数据允许上传以及如何同步 |

模式只是**产品接入方式的分类**，不意味着要预先建三套框架或三个 Supabase 项目。各产品只启用自己真正需要的公共能力。

## 4. 会员在线校验与产品自主复核

本地优先产品的核心付费操作发生在用户设备，而不是平台服务器上。因此：

1. **权益权威来源**属于公共身份/权益核心，可按用户和产品区分 Free/Pro、有效期、功能及限额；实现接口待确定。
2. **首版在线授权原则**：需要 Pro 的本地客户端在启动时联网校验，并在运行期间**按具体 SaaS 的实际需要合理复核**。各产品可在进入特定高级功能、关键操作或其他合适时机触发复核；不统一强制每次点击请求后台，不预设一个对所有产品通用的固定校验周期。
3. **离线授权延期**：首版不开发通用的桌面离线 Pro 授权凭据及相关许可系统。对短暂断网、已开始的任务、权益撤销与重新联网后的处理，留到具体产品专项确定；不自动限制与会员无关的 Free 本地功能。
4. **防复制的实际边界**：在线验证能降低用户保存网页后沿用正常付费功能的机会，但网页前端及本地应用代码可以被保存或修改，**只依赖前端检查不能保证防破解或防复制**。如付费功能依赖云端 API/业务数据，云端应在真实受保护操作上**服务端验证权限**；若功能完整运行在用户设备上，需接受不能绝对防复制的现实。
5. 本地权益验证的具体复核点和故障体验，见[本地优先专项](./local-first.md)；其他 SaaS 不必照搬拉片产品的复核方式。

## 5. 本地拉片专题与主架构的关系

本地拉片是本地优先模式的一个实例：视频、剪辑、AI 结果与密钥保留本地；客户端直连第三方模型；用户主动备份时直接上传配置文件至 R2，不通过 Supabase 转发文件内容。配置备份不要求客户端端到端加密，但保持私有。

具体配置恢复、可选分享、会员运行期在线复核及以后可能需要的离线授权均在[本地优先专项](./local-first.md)中维护，不成为其他 SaaS 的强制设计。

## 6. 未确定事项与审查原则

- **业务数据与部署**：各产品业务库是与公共库同库隔离还是独立数据库；是否存在多个 Supabase Project；不因产品独立而默认多项目。
- **权益**：各产品在线复核点及短暂掉线行为、数量/使用额度计数与重置、云端文件/备份配额计算、到期与取消/撤销语义；离线会员授权仅未来出现实际需求时再讨论。
- **云端文件**：R2 的桶/对象路径、权限发放、用户配额、访问记录、恢复与删除策略。
- **计费**：渠道、支付和订单的权威数据位置、管理范围、账单/会员的细节。
- **共享接口与运营**：React-admin 首期具体管理操作与页面、Data Provider / Auth Provider 适配、受保护的管理员 API、跨产品鉴权边界、必要审计与迁移验收指标。
- **选型**：React-admin、Cloudflare Pages、Supabase Auth / 托管 PostgreSQL / Edge Functions、Cloudflare R2、GitHub 已确认；各产品独立业务实现与尚未明确的模块再按需求选型，不提前绑定；不复用已弃用旧后端，除非用户明确指出特定部分可参考。

**所有尚未决定的具体实现机制都是讨论方向，不构成启动开发、创建服务或选择框架的授权。**
