# 统一计费与产品权益专项架构

> 状态：**自有兑换码优先 + 爱发电初期暂定 + 支付宝个体户和 Stripe 后期扩展**；轻量统一计费、四类权益及在线授权原则已确认；具体接入未实施

## 统一公共能力

- 全平台复用 Supabase 用户身份；按用户及产品确定有效权限。
- 多产品共用必要的订单、支付状态、订阅生命周期（续费、取消、退款结果）和可靠的权益同步。
- **每个产品独立套餐、价格、订阅和会员权益**；购买某产品会员不自动授权另一产品。
- 公共计费只管理必要的计费事实与产品级权益关系；不接管各产品业务项目、任务和内容。
- 计费事实来自可信流程，重复或延迟的支付通知需要可靠处理；避免权益状态与实际订阅发生长期不一致。
- Admin 已选择 **React-admin** 管理统一用户、产品、套餐和订阅等公共业务；具体页面与业务接口后续设计。对退款、人工修改他人权益和 Supabase Auth 用户管理等敏感操作，必须通过受保护的服务端管理接口，而非浏览器直接持有高权限密钥。

## 兑换码及支付接入顺序（当前有效）

| 顺序 | 机制 | 阶段与定位 |
| --- | --- | --- |
| **1** | **Aisenhubsass 平台自有兑换码** | **优先建设的基础授权入口**；React-admin 创建兑换码，由平台所有者分发，用户兑换成功后获取对应产品的会员权益。自有兑换码不是爱发电的内置兑换码，也不要求先接支付平台 |
| **2** | **爱发电（Afdian）** | 初期**暂定**的外部打赏/收款渠道；用户曾在此前项目简单跑通打赏和回调，此项目尚未集成，需再核实适用规则及可靠的订单匹配 |
| **3** | **支付宝个体工商户支付** | 未来注册个体工商户并满足相关商户资质后再开发，首期不接入 |
| **4** | **Stripe** | 更后期视商户资格和实际国际收款需求再评估开发，首期不接入 |

**统一权益，不统一各支付渠道的内部机制**：自有兑换码或经可信校验的订单都只负责提供**产品、用户、授权方案及有效范围的依据**；平台公共权益仍为唯一实际授权来源。未来更换收款方式不改变各 SaaS 的 Pro 判定。不要为将来两个尚未接入的渠道提前建设庞大多支付插件平台，必要时仅保留精简的支付来源标识和可扩展边界。

**兑换码最小安全要求**：Admin 发码和用户兑换必须通过可信服务端检查权限、有效性、产品归属和可用条件，可靠防止未授权、重复消费或并发超量兑换。码可使用次数、有效期、是否批量创建、是否绑定某个用户、兑换后的权益期限与撤销规则待实施时讨论，**不预设每码必定单次或永久**。

**爱发电回调可靠性**：官方提供 Webhook 与历史订单查询 API，Webhook 存在漏推送和潜在重复通知的提示；实际接入时不能仅凭收到请求或前端成功页面就开通 Pro。先以可信端核对订单的真实性与状态、所属方案和产品、对应 Aisenhubsass 用户，再幂等更新权益，并考虑漏推补查。具体关联方式、签名/核验方案、支付平台规则及订阅/退款支持程度均**待正式接入时确认**。

## 首期能力和权益类型

**身份首版**：Supabase Auth 邮箱/密码登录；邮件确认、密码找回所需发送服务必须在正式开放注册前落实。手机 OTP、邮箱 OTP/免密链接、Google 与其他适配后可用的提供商留待后续。

**目标购买与权益模式已确定**：月付订阅、年付订阅、一次性永久购买、免费试用；它们是**平台目标业务能力**，不是要求首个兑换码或爱发电阶段同时完成各类自动续费、扣费、退款。永久权益与按期续费是不同授权类型，不能以虚假的永久订阅状态替代；免费试用是否绑卡、是否自动转正待确定。

首期先建设**统一用户、产品管理、会员权益、自有兑换码开通及必要 Admin**，再按阶段连接爱发电和基础支付状态同步；不要求首期完成支付宝或 Stripe 接入。Admin 由本人或少数可信管理员使用，不先设计复杂的多产品运营团队权限体系。

首期公共权益能力为**功能开关、数量/使用额度、云端存储/备份配额、有效期/订阅到期**；并非每个产品都必须同时使用。**通用桌面离线会员授权首期明确不做**，如有产品后来确实需要，再单独扩展。

| 已确认支持 | 权益能力 | 规则待定 |
| --- | --- | --- |
| 功能开关 | 按产品和用户区分 Free / Pro 功能 | 产品的功能列表、是否有其他会员档位 |
| 数量或使用额度 | 限制模板数量、功能使用次数或其他产品专属限额 | 计数来源、周期、重置及本地计数可信度 |
| 云端存储/备份配额 | 限制各产品云端文件或配置备份的空间/数量 | 配额单位、超限处理、删除后的回收 |
| 有效期与订阅到期 | 根据授权有效时间决定权限是否继续生效 | 宽限期、取消与退款处理 |

**在线执行规则**：Pro 功能采用启动时有效在线授权与运行期间合理复核的原则；复核点由产品自行确定（如关键操作或进入付费功能时），不是统一固定频率。云端产品执行受保护操作时还须由**服务端实际校验权限**，不能仅凭前端展示状态。

## 使用方式

| 产品方式 | 权益校验职责 |
| --- | --- |
| 云端业务型 | 产品的云端业务服务校验账号和对应产品权益 |
| 本地优先型 | 公共权益是权威来源；客户端启动时联网校验并在运行中按产品规则合理复核；详见[本地优先专项](./local-first.md) |
| 混合型 | 根据本地与云端操作的执行位置进行相关权益校验 |

## 不做

- 不设计所有产品通用的一份 Pro 会员。
- 不把所有产品的业务数据迁移到公共计费数据库。
- 不预先设计大型多支付渠道插件、企业多租户计费或**按量收费**系统；本次确认的是**使用量限制**，不意味着要求按使用量收费。
- 不把爱发电平台内部的兑换码当成 Aisenhubsass 自有兑换码；不因爱发电临时采用就锁定所有产品未来只能用该平台。
- 不在当前阶段对接支付宝个体工商户支付或 Stripe；不假设初期渠道必然支持所有目标自动扣费与退款行为。
- 不在首期建设复杂的高级统计、综合运营中心或面向不同产品运营团队的权限平台。
- 不在首期建设通用桌面离线会员授权系统，不将“离线许可证”作为所有 SaaS 付费体系的必要基础。
- 不以仅前端进行的权限判断代替云端受保护操作的服务端校验，不承诺完全防止保存网页或篡改客户端后的本地复制。
- 不强制计费数据必须在 Supabase 同库部署；**仅支付接入顺序和爱发电暂定方向已确定**，不预先确定其它尚未选择的支付适配库。
