# 公共 API MVP 与独立 SaaS 首次接入架构

> 状态：公共 API 的逻辑职责、调用边界、首次加入、准入复核和异常原则已确认；示例路径、字段名、HTTP 状态码映射仅是候选契约，尚未批准为最终接口实现。当前只做架构设计，不安装依赖、不建库、不开发、不部署。

## 1. 目标与适用范围

以最少公共能力支持本地优先、云端和混合 SaaS：**Supabase Auth 提供统一身份；AisenCore 统一管理产品目录、产品成员资格及产品级权益；各 SaaS 独立管理业务数据、业务资源权限及实际执行**。保持公共身份、产品运行状态、成员状态、Pro 权益、业务资源权限相互独立。

MVP 优先复用 Supabase Auth、Supabase 托管 PostgreSQL、Edge Functions、PostgreSQL 事务/约束/RLS 与 React-admin，不新增第二套用户认证、产品授权 JWT、通用授权服务器、API 网关、Redis、消息队列、事件总线或跨数据库分布式事务框架。可根据真实规模或新业务需求再扩展。

## 2. 调用参与方与身份可信边界

| 参与方 | 负责什么 | 不能做什么 |
| --- | --- | --- |
| 浏览器 / 桌面 / 移动客户端 | 用户登录、展示本人状态、发起需登录服务/本人退出或重新加入 | 不能携带平台级 secret/service_role，也不能自行修改成员状态 |
| 具有可信后端的 SaaS | 判断合法业务接入触发点；验证用户身份并转发用户 JWT；检查业务资源权限、执行项目任务等 | 不能因为声称 product_key 就获得管理权限，也不能任意替其他用户更改公共成员与权益 |
| AisenCore 公共服务 | 独立验证用户令牌与产品/成员/权益；可信执行成员状态转换，输出公共准入结果 | 不接管各产品项目、团队/项目成员角色及业务资源 |
| React-admin | 复用管理资源界面、筛选和操作入口 | 不代替可信管理接口的服务端授权 |
| Supabase Auth / PostgreSQL | 公共身份权威与公共产品/成员/权益状态权威 | 不替 SaaS 判断具体业务资源归属 |

用户 JWT 只证明当前用户身份，**不证明请求一定由指定 SaaS 后端发出**。对面向公众开放的产品，允许用户持有效公共身份直接自助加入，是 MVP 已接受的信任边界；`joined_at` 只表示成员关系创建时间，不是可信的首次真实业务使用证明。将来有邀请制、审批制、私有产品或严格的后端限定要求，再为这种产品增加明确准入策略和受限服务认证；普通首次加入不预先分配各 SaaS 平台级高权限密钥。

服务端后台任务若确需机器身份，应另行采用受限、可校验调用方身份及产品/操作范围的服务间凭据；不得把 Supabase 平台级 `service_role` / secret key 下发给 SaaS 客户端，亦不默认分发给所有独立 SaaS 后端。跨独立 Supabase Project 的身份、JWT/RLS 也不会天然互通，必须在相应可信边界验证。

## 3. MVP 逻辑接口分组

以下是**逻辑操作名称**，不是最终函数名、路由或部署边界。

| 分组 | 逻辑操作 | 权限及副作用 |
| --- | --- | --- |
| Supabase Auth（直接复用） | 注册、登录、会话刷新、邮箱确认、找回密码 | 不另建公共密码/Token 服务 |
| 普通用户只读 | `GetMyProducts`, `GetProductAccess` | 仅返回本人关联/产品状态；**无副作用**，不隐式加入 |
| 公共准入只读 | `EvaluateProductAccess(subject, product, capability)` | 公共服务验证身份与范围；判断产品、成员及所需权益；不修改记录，不替产品做业务资源授权 |
| 成员变更 | `EnsureMembership`, `LeaveProduct`, `RejoinProduct` | 可信服务端按有限状态转换；用户只能操作本人 |
| 内部 Admin | 产品创建/变更/发布/暂停/恢复，成员查询/暂停/恢复，关键状态事件查看 | 平台可信管理员；需要服务端授权、原子变更与最小审计 |
| 权益与计量（独立领域） | 查询/评估 Pro、配额；可信核销/预留 | 与成员状态分离；只读准入查询不承担额度扣减、支付或兑换 |

普通用户可查看本人必要的成员状态、授权历史、取消订阅/数据请求途径，即使处于 `left`/`suspended`；这些账号管理接口不机械要求 `active`。查询接口和管理接口不得因为登录或读状态而改变成员资格。

建议成功使用 HTTP 标准状态码加简洁 JSON（不强制 `success/data` 包装）；错误优先复用 RFC 9457 Problem Details 并附稳定的业务 `code`。示例中的路径、响应字段和具体码值仍待接口落地前最终校对。

## 4. 首次合法接入触发与两种调用时序

**共同原则**：平台账号注册、单纯登录、查看产品介绍、查询本人状态、打开本地免费功能均**不触发** `EnsureMembership`；只有第一次实际进入某产品需要公共账号的合法业务流程才触发。非法资源请求、支付回调和后台定时任务不应借首次接入流程替用户自动加入。

### 4.1 有独立可信后端的云端 SaaS

1. 用户经公共 Supabase Auth 登录，向目标 SaaS 发起合法的需登录业务请求。
2. SaaS 后端验证用户令牌并完成适当的业务入参/目标资源初检，确认符合自动加入触发条件。
3. SaaS 后端将**现有用户 JWT** 和目标 `product_key` 发往 AisenCore 的普通用户 `EnsureMembership` 能力；不传任意可自选 `user_id`，不需要平台级机器管理密钥。
4. 公共服务**再次独立验证** JWT 及身份，验证产品存在且开放，再在 PostgreSQL 中原子地查询/创建该 `user_id + product_id` 成员。
5. 新成员创建为 `active`；已有 `active` 返回现状；已有 `left` 或 `suspended` 必须拒绝自动恢复。
6. SaaS 收到有效成员结果后，在自身业务数据库幂等地初始化必要的个人业务记录/工作空间，并检查业务资源及如有必要的功能权益后执行。

若公共成员创建成功但 SaaS 独立数据库初始化失败，**不回滚公共成员**；业务初始化可在后续合法请求时安全重试。不预建跨系统分布式事务协调。对高风险业务/额度等，随后仍须按执行时可信权限与计量规则处理。

### 4.2 纯本地优先 SaaS

1. 匿名本地免费操作不进入公共账号和成员流程，也不强制联网。
2. 首次进入真正需登录的本地 Pro 账号服务、主动私有配置备份等能力时，客户端使用 Supabase Auth 登录。
3. 客户端携带**自己的用户 JWT**直接请求同一公共 `EnsureMembership` 接口（不得含 service_role/secret key）。
4. 公共服务用相同的用户/产品/成员规则创建或返回现状；本地客户端在启动时执行 Pro 有效在线校验，并在运行期间按实际关键操作合理复核。
5. 用户本地视频、项目、AI 结果/API Key 等不因成员注册上传公共服务器；与会员无关的离线免费功能不因授权失败而被无故禁用。

混合型产品仅针对其需登录的账号/云端能力应用相应路径，本地业务仍依产品边界。

## 5. EnsureMembership 语义与状态转换

仅保证**当前用户首次加入或继续使用已有 active 成员关系**。输入逻辑上只有已验证身份与目标产品；不接收客户端直接指定任意 `user_id`、套餐、价格、Pro 状态。

| 当前记录/条件 | 行为 |
| --- | --- |
| 产品不存在或处于 draft / suspended | 拒绝普通自动加入，无成员修改 |
| 无成员记录，产品允许加入 | 原子创建 `active`，返回 created=true |
| 已 `active` | 返回已有成员，created=false |
| 已 `left` | 拒绝自动恢复；仅用户主动确认的 `RejoinProduct` 可 `left → active` |
| 已 `suspended` | 拒绝自动恢复；仅管理员可信解封操作 |
| 重复请求、双设备并发、响应超时后重试 | 保持唯一当前成员记录，不能覆盖较新状态 |

管理员解封采用**恢复封禁前状态**：原 `active` → `suspended` → `active`；原 `left` → `suspended` → `left`。暂停前状态必须可靠保存，重复封禁不能覆盖它；恢复不得默认恢复 Pro、撤销退款、删除/恢复业务数据。成员退出与产品业务数据删除、账号注销、订阅取消、退款和原授权有效期相互独立。

## 6. EvaluateProductAccess 与授权检查顺序

建议的逻辑输入：经过可信验证的主体 + 目标 `product_key`/`product_id` + 所需的**公共能力标识**。用户请求中不接收用于冒充他人的 `user_id`。示例能力 `document.generate.pro` 仅说明业务名称，不意味着平台管理产品资源细节。

最小响应建议：产品标识、产品状态、成员状态（未加入可以在响应中表示 `none`，但 `none` 不是持久化成员状态）、`allowed`、稳定 `reason`、可选 `evaluated_at`。该结果是**特定时刻、特定主体/产品/能力的状态判断**，不是长期有效授权 Token 或 SaaS 业务资源访问票据。

对云端受保护操作，逻辑检查为：

1. 验证用户身份、令牌/会话必要有效性；
2. 验证产品存在且允许当前服务；
3. 验证成员为 `active`（首次合法使用时由**独立 ensure 操作**处理，查询不顺便创建）；
4. 按实际功能检查 Pro、使用额度/存储权限等公共权益；
5. 由 SaaS 可信后端验证具体项目、文件、任务等业务资源权限；
6. 涉及额度消费时进入可信原子核销/预留流程，再执行实际业务及结果记录。

逻辑前提不强制每项检查都独立发 HTTP 请求；可先做无敏感信息泄露的业务初检以节约调用。一次可信请求可复用其最近一次合适的判断，但**客户端状态快照不能替代云端关键操作时的服务端验证**。纯本地 Pro 延续启动联网 + 运行期合理复核；不要求每次点击联网。

## 7. 响应、错误与失败重试的 MVP 约定

**接口的唯一详细错误/响应与验收定义**放在[公共 API 契约与 MVP 验收](./api-contract-and-mvp-acceptance.md)；本文件只规定接入过程的关键业务边界：

- `EnsureMembership` 的重复请求不创建重复成员，也不自动恢复 left/suspended；结果未知时先查当前状态，必要时安全重试。
- 无效 JWT/无权限是确定性的拒绝；公共授权服务不可用是“暂时无法验证”，不可当作封禁，也不可对新的云端受保护操作默认放行。
- 购买/兑换、消费额度、支付回调存在独立的幂等与事务约束，不由查询型 `EvaluateProductAccess` 隐式扣减。

## 8. 状态缓存与撤权时效

- 产品静态介绍可缓存；客户端可短暂缓存成员/Pro 状态供**展示**。退出、重新加入、产品切换或已知状态变更后应刷新；不得凭旧的 `allowed=true` 直接执行云端受保护操作。
- 可信 SaaS 后端可在**单次请求处理范围内**复用适当的当前公共授权结果，避免重复远程调用；MVP 不维护长期跨请求的授权权威副本，也不要求每次简单读取都远程校验。
- 已提交的封禁/退出/产品暂停应在下一次必要的可信云端授权检查中体现；进行中的长任务在明确的关键操作点复核，具体中断与撤权生效时效待产品确定。
- 身份 JWT 仍有效**不代表**成员仍为 active；只信任 JWT 中可自改写用户资料或缓存权益状态都不安全。
- 本地客户端无法保证断网后立即获知撤权；不承诺离线正在运行的任务即刻停止，也不无故封锁免费功能。
- 先前签发的临时 R2 访问 URL 可能在自身到期前继续有效；有效期与撤权策略应由文件专项按实际风险设计。
- 新的云端受保护操作若无法可信验证公共准入，不应“故障时自动放行”；但应区分服务不可用与成员被禁止，不误导用户。

## 9. 独立 SaaS 的安全及数据职责

- 对开放型产品，首次用户 JWT 自助加入可接受；仅 `product_key` 不是可信服务身份，服务端代理请求也不应有权替用户转变成员状态。
- 公共接口不提供各 SaaS 业务项目/文件的统一访问控制，不因管理员身份天然开放所有产品私有数据。
- 各 SaaS 不保存可独立修改的第二套公共会员权威状态；可用稳定公共 `user_id` 关联本产品数据库。
- 浏览器、本地客户端及独立 SaaS 不获授整个平台的 `service_role` / secret key；Admin 高权限操作须可信校验、最小审计。
- 无需首版实现复杂 RBAC/ABAC、跨 SaaS 分布式事务、跨请求 Redis 撤权缓存或第二套产品授权 Token。

## 10. 明确尚未定稿的事项

- HTTP 路由、Schema 精确字段、能力标识规范、HTTP 错误码精细映射、接口版本策略；
- 对需要服务身份的后台任务如何限制具体产品与动作；将来邀请制/私有产品准入策略；
- JWT 验证与严格会话撤销的具体实现、API 超时/重试参数、峰值流量优化；
- 权威产品成员/封禁恢复的 PostgreSQL 逻辑约束、最小事件审计字段和 RLS；
- 云端长任务撤权检查点、消费额度事务边界、R2 临时凭据期限与删除/恢复时效；
- 产品暂停、退出/封禁下的新购买行为、自动续费取消入口及补偿规则。

这些是后续需要解决的细节，不能当作当前已授权实施的接口或数据库方案。
