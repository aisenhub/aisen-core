# AisenCore Admin｜统一 Theme 与通用 UI 质量规范

> **定位**：本文件只约束正式 React-admin 前端的全局视觉一致性与质量底线，不定义具体配色方案、页面布局、菜单树、表格行高、候选主题、专用控件或业务功能。业务能力与安全边界以 [Admin 应用架构](./admin-console.md)、[正式需求](../../spec/requirements.md)及各后端/领域合同为准。视觉方案由当前任务的设计与实际用户评审决定。
>
> **状态**：正式 React-admin 的 Theme/页面仍需项目所有者评审；V6 离线原型只作交互参考，不是批准的生产视觉方案。

## 1. 单一视觉来源与 React-admin 优先

- 正式 Admin 使用 React-admin + MUI + TypeScript。优先使用官方布局、Resource、List/Datagrid、Show、Create/Edit、表单、通知、菜单和交互能力。只有存在实际功能缺口时才做最小业务组合或扩展；不另造第二套 UI、路由、缓存或表单框架。
- 全站只有一套由 React-admin/MUI 官方 Theme 入口注入的权威视觉主题，可在 `theme.ts`（或实际项目约定的唯一主题模块）中管理 palette、typography、spacing、shape、components 与必要的亮暗模式。项目尚未选定、冻结任何具体视觉 Token。
- 业务页面优先消费语义颜色、主题间距及既有变体；必要局部布局可以使用最小 `sx` 或相应官方样式机制，但不得建立并行品牌 Token 或散落与主题冲突的重复全局覆写。
- 不从 HTML 原型、第三方模板、旧截图或此前候选方案自动推断某套视觉风格已批准。组件复用是技术与质量原则，不等于 UI 外观必须与某个原型 DOM 1:1 相同。

## 2. 设计自由度与质量底线

- 信息架构、页面分区、导航形式、颜色、字体大小、控件密度、圆角、断点、弹窗样式以及列表列组合，均由当前任务、实际数据、React-admin 能力、可访问性和用户反馈决定；未经明确批准的旧候选不具有强制性。
- 页面用清晰信息层级、标签与操作反馈表达任务，避免重复说明、无用装饰与噪音；但不能为追求极简省略必需的标签、单位、权限限制、危险后果、错误恢复和辅助技术名称。
- 关键状态不得仅通过颜色传达。键盘焦点、表单标签与错误关联、Dialog 焦点管理、中文/英文/长 ID、缩放与窄屏可操作性按相关 WCAG 2.2 AA 原则和真实浏览器结果验证。
- 保留加载、空列表、筛选无结果、权限拒绝、网络失败、冲突、写入结果未知等不同状态的清楚反馈。危险操作显示真实影响范围，不能用前端确认代替服务端鉴权。
- 禁止前端泄露 service_role、MFA 秘密、码哈希、历史兑换码明文和独立 SaaS 私有资料；遵循已有后端/API 安全合同。不能从本文件推导新增业务功能或接口。

## 3. 审核与变更

1. 开始开发前先核对当前需求、业务合同和真实 React-admin/MUI 版本；仅针对本次任务读取相关 [62 条结构化 UX 规则](../../development/frontend/admin-design-rules.json)。
2. 对复杂、不确定或高风险交互，可按 [原型及 AI 开发工作流](../../development/frontend/interaction-benchmark-workflow.md) 先验证；原型本身只作设计候选，不能决定数据库、权限或 RPC。
3. 对已确认的视觉方案，保存可追溯的版本、必要页面与状态示例、用户反馈和验收结论；不强制特定主题数量、具体视口列表、固定页面集合或单一视觉稿载体。
4. 正式代码的可用性、可访问性、设计一致性与权限安全均需真实测试证据；`NOT RUN` 不等于 `PASS`。未通过的视觉或真实系统测试维持 NOT RUN，不能用演示结果代替。
5. 视觉方案变更通常只更新唯一 Theme 与相关设计决议，不再同步维护多套重复 Token 清单。具体视觉变更仍由用户确认；D1 本地开发与 Admin 视觉评审是两个独立阶段。
