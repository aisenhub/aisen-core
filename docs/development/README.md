# 开发指南与参考资料

> 定位：这里只保存**开发阶段如何实现**的规范、参考链接、操作检查点和可复用模板。当前只是整理文档，并未批准实际开发、安装或部署。

## 与其它文档目录的职责

| 目录 | 保存什么 | 不保存什么 |
| --- | --- | --- |
| [`../spec/requirements.md`](../spec/requirements.md) | **唯一当前有效的、已经确定的需求**；另标明尚待确认的需求细节 | 历史需求、修改日志、某第三方 API 的操作教程 |
| [`../architecture/`](../architecture/current-main-architecture.md) | **已确定的总体及专项架构**：模块关系、边界、数据流、关键技术决策；可按领域增加子文件夹 | SDK 调用示例、操作指南、第三方参考链接合集、可复用模板 |
| `../development/` | **开发指南**：开发约束与步骤、官方文档和开源参考、测试规范、模板/资产 | 未经确认的架构选型、产品需求决定、项目变更日志 |

如发现新业务需求，先确认并修改 `spec/requirements.md`；若改变已确定的系统设计，先同步对应 `architecture/`；再更新 `development/` 下的操作指南，避免由一份参考文档反过来决定架构。

## 统一约定

1. **按主题建目录**：每个专题按实际复杂度放独立的 `references.md`（官方文档/开源参考）、`integration-guide.md` 或其它开发规范，以及按需 `templates/`。不强求每个主题都按同样数量创建文件。
2. **参考不是决定**：引用第三方项目、博客或 API 文档，不代表已经选用、安装或授权其许可证；需记录来源和适用场景，重要结论实施前复核。
3. **规范只写已确认的底线**：未决定的 SDK、接口结构、表结构、测试框架、部署步骤明确标为「待实施时确定」，不凭空补出代码模板。
4. **模板不包含秘密**：不在文档或模板中保存真实 API Token、支付密钥、R2/Supabase 高权限密钥或用户资料。
5. **不保留旧版本**：文档直接维护最新有效内容；删除失效的参考、样例与说明，不生成修改历史记录。
