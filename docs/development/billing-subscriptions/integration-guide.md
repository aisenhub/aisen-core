# 兑换码与爱发电接入开发指南

> 性质：按**目前已确定的边界**列出未来实施时的工作步骤和必须满足的可靠性要求。这里**不是可直接照着执行的完整 API 规格或开发授权**。

## 1. 对接边界

- **架构依据**：[统一计费与权益专项](../../architecture/domains/billing-and-entitlements.md)；[当前需求](../../spec/requirements.md)。
- **管理前端**：React-admin 创建/管理平台自有兑换码。管理员不是任意登录用户。
- **可信处理**：优先使用 Supabase Edge Functions + 公共 PostgreSQL 保存必要的兑换结果、可信授权依据与实际产品权益。不能把服务端密钥写进 Cloudflare Pages 前端。
- **用户权益**：不管源头是兑换码、爱发电还是后期支付服务商，最终都由**AisenCore 的产品级权益系统**决定用户可用的 Pro 功能，不在各支付渠道分别复制会员系统。

## 2. 自有兑换码：未来开发步骤

1. **先确定最小兑换规则**：码对应产品和授权范围；是否单次/多次使用、有效期、授权时长、是否限制用户、是否允许撤回、批量发码方式。当前均未最终决定，**不得直接当成数据表字段清单**。
2. **Admin 发码**：由经过可信校验的管理员通过 React-admin 发出创建请求，后台验证操作主体和请求范围；由**平台所有者自行分发**，不要求支付平台参与发码。
3. **用户兑换**：登录用户提交自有兑换码，可信端核对码和其可用条件，将消费记录及相应产品权益更新作为可靠的整体操作，避免两个用户并发重复兑换或同一请求重复增权。
4. **查看结果**：用户以公共权益为准查看是否成功；后台保留必要的发放/兑换记录以支持排错和必要的安全审计。
5. **异常行为**：对无效码、过期码、重复请求和并发争抢做明确处理；具体错误提示、频率限制、风险检测和撤回流程随实际需求设计。

## 3. 爱发电：未来开发步骤

1. **核对官方接口与平台使用规则**，确认打赏订单能用于拟定的付费开通流程，以及当前平台能够获取到哪些订单、赞助者、金额、商品/方案和状态信息。
2. **确定用户与订单的可信关联方式**：应能把爱发电的某笔订单对应到 **AisenCore 用户 + 产品 + 应授予权益**。不能仅凭浏览器提交某个订单号就授予会员。
3. **按官方文档设置 Webhook 接收地址**：由可信服务端接收；外部 Webhook 不提供 Supabase 用户 JWT，服务端必须按照爱发电实际支持的核验机制处理来路与订单真实性，必要时**主动调用订单查询 API 交叉核对**。不要将主动 API 调用签名误写成 Webhook 消息已带有相同签名。
4. **去重、补查、补偿**：相同订单不能多次授予权益；必须处理重复通知、可能漏推的订单以及回调延迟，按实际订单状态安全补查、同步，不依赖前端成功页面。
5. **对账与审计**：需要能够排查收到通知但未成功开通、重复通知及无法匹配用户的记录；不能暴露支付密钥或不必要的用户数据。
6. **由公共权益系统开通**：确认订单与授权事实后，再根据对应产品权益规则开通/延长会员，不让爱发电订单字段成为所有 SaaS 必须直接依赖的会员格式。

**待明确**：实际爱发电接口字段、回调鉴别机制、订单账号绑定方式、金额与套餐映射、是否适用月/年自动订阅、退款或取消后的状态处理。先核对参考文档，不凭先前项目的简单测试推导生产接入已可靠。

## 4. 后期支付宝和 Stripe

本阶段**只保留清晰的支付来源扩展位置**，不建设支付宝/Stripe SDK、接口、模拟实现或大型通用渠道插件系统；等实际有商户资格和接入任务时，再在本专题按需要增设对应指南。

## 5. 最小安全和测试核对

- Admin 创建兑换码与用户兑换都必须有**服务端授权**；普通客户端无权批量生成会员资格。
- 兑换必须防**并发双重消费、重复提交、越权兑换其它产品权益**。
- 爱发电支付开通必须防**伪造/重放通知、重复订单增权、订单错绑用户或产品、漏推未补账**。
- Supabase 高权限密钥、爱发电 API Token 等仅存于可信服务端；**不使用客户端传来的“成功付款”状态作为授权事实**。
- 月付、年付、永久权益、免费试用是平台目标能力，不意味着爱发电初期已具备等价的自动扣款或退款处理。

真正开发时的用例及测试工具归于[测试规范专题](../testing/README.md)；参考 API 与案例见[参考资料](./references.md)。
