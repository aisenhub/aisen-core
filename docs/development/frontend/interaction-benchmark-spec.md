# 交互基准产物规范（UI-G0A Prototype Specification）

> **定位**：规范低成本交互网页应该体现什么、交付前检查什么。流程见 [交互工作流](./interaction-benchmark-workflow.md)，业务规则见 [架构](../../architecture/README.md)，视觉唯一权威是 [Admin UI-G0](../../architecture/applications/admin-ui-design-system.md)，批准与问题写入 [Plans](../../Plans/README.md)。
>
> 方法已选，但当前 **UI-G0A NOT APPROVED**；原型不等于已实现后端或正式开发许可。

## 1. 边界与最小产物

- **交互优先**：约 80% 评审精力关注模块衔接、上下文保留、操作流程、状态和错误恢复；约 20% 关注布局/样式/主题。比例是建议，不替代可访问性与安全底线。
- **默认一场景一个单文件 HTML**：本地打开即可运行，HTML/CSS/模拟 JS 自包含，不依赖 npm、真实认证、生产 API、外部网络、服务端或共享的原型框架。仅用合成数据，显著注明「模拟演示」。
- **只模拟不确定性**：覆盖一条端到端任务旅程、必要相邻模块、一条主路径与当前最重要的异常/危险路径；不要求造完整 Admin、多主题和所有 HTTP 错误。不存在的功能不补造。
- **业务合同不可篡改**：字段、状态、授权、计时、RPC 错误、产品作用域、UNKNOWN 安全行为依据 spec/architecture；无法确认的内容写明「待定」，不靠演示假数据创建新政策。
- **原型是评审手段**：不承诺生产性能、幂等、事务、隐私保护或 WCAG 已通过；不把 HTML CSS/JS 复制为正式 React-admin 组件。

## 2. 业务交互的最低覆盖维度

| 维度 | 原型中应当体现（与当前任务有关时） | 不合格表现 |
| --- | --- | --- |
| 任务与模块关系 | 角色、目标、起点、涉及模块、完成落点和下一步动作 | 孤立页面堆叠，不知道从哪开始 |
| 上下文衔接 | 列表→详情→操作→结果→返回；适用时保持用户/产品/ID、筛选和返回位置 | 跳转后丢失用户和条件，反复复制 UUID |
| 状态转移 | 正常、处理中、成功/拒绝、空数据、禁用/只读；操作之后有可见状态变化 | 全靠成功 Toast，数据毫无变化 |
| 输入与防错 | 必填/非法输入、默认值、联动字段、单位/时区、取消/草稿保留 | 忽略输入，或将硬编码结果称为计算结果 |
| 错误与恢复 | 与场景有关的 401/403/409/429/503、业务拒绝、`UNKNOWN`；明确下一步和安全重试边界 | 错把 UNKNOWN 当失败，盲目重复高危写 |
| 危险操作 | 显示真实影响范围、必要二次确认，永久/撤销/跨产品行为不含糊 | 随便点一下就模拟全局封禁或永久授权 |
| 敏感与权限 | 使用假的敏感信息样本，演示必要的生命周期与受限可见性 | 假装前端禁用等于 RLS 成立、保留真实明文 |
| 可操作性 | 必要导航/返回、关闭弹窗、键盘基本焦点、重置场景、状态切换 | 死按钮、打不开/关不掉弹窗、引导中提不存在按钮 |

**分支选取规则**：每个本次要验证的核心任务至少一条完整主路径 + 一条最重要的异常或高危路径；若场景无风险分支，说明原因。复杂度来自真实业务风险，而不是固定状态数量。

**发码 UNKNOWN 例子**：提交发行→响应丢失→本地保留非秘密 `request_id`→模拟按原请求核验执行状态→若旧批已创建但明文无法取回，提供经确认的作废/新请求路径。原型不得由「超时」直接推断「发行失败」，不得声称真的完成了后端事务审计。

## 3. 必须怎样体现架构中的设计系统

「完整体现」是指**本次场景实际使用到的设计系统类别**有对应表现，而不是要求每个原型设计全站所有主题和 320～1440 的每一种组合。

| 类别 | 原型实现要求 | 权威与限制 |
| --- | --- | --- |
| 主题/颜色 | 在 HTML 顶部用集中 CSS 语义变量对应 page/panel/text/border/primary/status/danger；主次危险按钮、状态区别清晰 | 变量的含义与候选值看 [UI-G0 第 2 节](../../architecture/applications/admin-ui-design-system.md)；Token 未冻结时不冒充正式品牌色 |
| 字体 | 字体族与中文/英文混排、标题/分区/正文/表单标签、数字/UUID 等宽、字号与字重层级一致 | 参照 UI-G0 Typography；不散落随意字号 |
| 全局布局 | 对涉及的业务页统一 AppBar、导航、当前产品上下文、内容区、页面标题与操作位；MFA 登录隔离壳 | 参照 UI-G0 第 3 节与 D3-UI；不凭演示增设多产品状态机 |
| 通用组件 | 表格、输入、表单、弹窗、徽章的高度、间距、圆角、焦点、危险强调和反馈一致 | 按 UI-G0 第 4 节与 [组件模式](./admin-design-components-and-patterns.md)；无需自建正式组件库 |
| 屏幕与滚动 | 当前任务必测桌面与窄屏；按适用性审阅 1440/1280/820/375/320px，表格局部滚动，不让根页面溢出 | CSS 切换宽度仅供原型预览，不等于真实视口/缩放 PASS |
| 可读性与无障碍 | 重要状态不能仅凭颜色，标签、键盘焦点、弹窗关闭和错误恢复信息可见，浏览器可缩放 | 正式 WCAG 2.2 AA 目标与 UI-G3 运行审核另做 |
| 暗色、主题切换、动效 | 只有确为本次讨论重点才增加；否则只演示一套一致的候选主题 | 未批准特性不可因 HTML 做得方便而进入 MVP |

**注意技术边界**：允许在一次性原型中手写 HTML/CSS/少量 JS，因为这不是正式 React-admin 页面；正式页面仍优先 MUI/React-admin 官方组件和唯一 Theme。原型颜色/字体/布局不反向修改 architecture，先由项目所有者确认。

## 4. 「怎么体验」引导是每次交付的必备内容

至少使用一个载体，不要求生成三份重复材料：

- **默认当次对话**：用简短文字说明本次验证目标、打开哪份 HTML、2～5 个真实存在的点击动作、分别观察什么、视觉检查点与直接反馈方式。
- **离开聊天独立操作/多人评审**：HTML 首页显著提供「怎么体验」入口，使用可返回当前任务并保留本地状态的独立页或可收起面板；不把教程塞满日常业务页面。
- **确有交接/归档需求**：同场景短 `guide.md`，不重复抄写业务合同。

引导应包含**主路径 + 最关键异常路径**，清晰标注「仅本地模拟，不会修改真实数据；交互认可≠视觉认可≠正式施工许可」。如有审批复选框必须默认未审，不准预填 `APPROVED`、`PASS`、`WCAG verified` 或自动签名。引导步骤要与网页实际按钮相符，不得给出不存在的入口。

## 5. 交付前的最低核查

在可用浏览器打开 HTML，至少完成**主路径和关键异常路径**一次，核对输入联动、导航/返回、关闭弹窗、模拟状态重置、引导可用、明显浏览器控制台问题、桌面和窄屏、键盘焦点；检查无生产 API/外部请求、无真实秘密。未能实际执行的写 `NOT RUN`，不能声称已测试。

是否需要专用浏览器自动化、何时进入 UI-G3/后端验收，参照 [原型到正式实现与测试规则](./prototype-to-production-rules.md)。观察与决策写在任务的 Plans 记录，不在网页内部建立审批系统。
