# 原型到正式实现：复用规则与分级验证边界

> **目的**：不要把同一份前端写两遍，也不要把轻量原型的演示通过误认为真实后端/浏览器 E2E 通过。业务以 [architecture](../../architecture/README.md) 为准；原型要求见 [产物规范](./interaction-benchmark-spec.md)；Theme 见 [UI-G0](../../architecture/applications/admin-ui-design-system.md)；审批/问题记入 [Plans](../../Plans/README.md)。
>
> **状态**：这是未来开发方法，不代表已部署测试框架；UI-G0A NOT APPROVED、正式业务代码未获施工授权。

## 1. 应复用的是确定的设计，而不是临时 HTML 源码

| 可复用的内容 | 真正来源 | 正式工程中的用法 |
| --- | --- | --- |
| 字段、RPC 参数、权限边界、业务状态和错误语义 | 已批准的 spec/architecture | 原型引用，生产实现仍只以此为权威，不另造字段与规则 |
| 导航/操作顺序、表单联动、确认和异常恢复 | 用户体验认可 + Plans 增量决定 | 使用 React-admin/MUI 正式组件实现，不必重新讨论交互 |
| 语义 Token、已签收的布局和组件表达 | UI-G0 唯一规范 | 由正式全局 Theme 统一映射，不逐页复制 HTML CSS |
| 关键路径的「初始状态→用户动作→预期结果」 | 原型的场景 + Plans 决定 | 转换成 UI-G3 浏览器用例/必要的 RPC 权限负向用例 |
| 已认可的必要标签/风险文案 | 交互决定和业务权威 | 核对当前错误/权限/时区语义后进入真实 UI |

**不复制**：演示用 HTML 字符串模板、`onclick`、手写表格和分页、模拟数据库、假认证/TOTP、硬编码日期/测试账号、演示 JSON、假审计和「成功」Toast、局部视觉魔法值、模拟明文的全局变量。不能把这些混进生产工程或作为安全证明。

**例外**：若有稳定、无副作用的纯格式化/计算逻辑确实必要，可以在生产工程以权威合同重写成最小函数并加单元测试；不为复用此函数而给独立 HTML 和 React 建一套共享构建/包依赖。

## 2. 一条低成本的交接路线

1. **做原型前**：引用相关 spec/architecture/D3-UI，列出这次需要解决的不确定交互，而非复制一份长需求。
2. **体验后**：在现有 Plans 的「决定」处只写差异：原型路径与 Git 版本、已认可的 2～5 个关键行为、未解决的点、交互/视觉/施工各自的授权状态。
3. **实现时**：读取**权威合同 + 已认可行为**，优先 React-admin/MUI List/Show/Form/Confirm/Theme/Provider，按实际 API 实现。无需追求 HTML DOM/JS 完全重用。
4. **测试时**：将已认可的行为作为测试用例输入，不将模拟通过认定为真实 `PASS`；补齐真实权限、事务、数据与可访问性检查。
5. **上线前与后续改动**：以正式应用/测试为运行真相；交互不变的小改动直接改真实代码，不长期同步 HTML 与 React。被 UI-G0 签收引用的原型必须保持版本可追溯，未引用的探索稿按 [产物规则](../../interaction-benchmarks/README.md) 清理。

## 3. 什么时候做测试、测试到什么程度？

| 时点 | 必要检查 | 对通过结果的正确解释 |
| --- | --- | --- |
| **无需新原型的小改动** | 实现后运行受影响组件/回归用例，保留既有安全门槛 | 不必补做一次 HTML 审批 |
| **P0：每次交付原型** | 在浏览器打开；走完**主路径+关键异常/危险路径**；核对状态、输入、返回、重置、引导、窄屏、基本键盘、无真实外部请求 | 证明「模拟可体验」，不证明真实 API、权限、WCAG |
| **P1：跨模块或高风险交互变化** | 根据改变的交互增加状态断言/浏览器自动化；重放相关场景，不无差别测试所有页面 | 发现演示死链、假状态和 UX 错误，仍不证明后端 |
| **UI-G0 真实视觉签收** | 已要求的代表性任务和状态、适用宽度、Token/组件一致性、用户实际审阅与明确签收；未测试写 NOT REVIEWED | 只批准特定交互/视觉基线和范围，不自动解锁施工 |
| **P2：正式实现后，合并前** | 真实浏览器路径、组件/API 行为；涉及 RPC/权限则在隔离环境做事务、幂等、MFA/身份、敏感数据与负向测试 | 由正式运行证据证明实现满足批准合同 |
| **P3：UI-G3 / 发布就绪** | 现有 D3-UI-X/UI-G3/后端安全 E2E 的适用范围；实际 1440/1280/820/375/320、缩放、键盘、错误注入和性能 | 不等于跑了一次 `npm build` 或单张截图 |

**测试边界最重要的区分**：P0/P1 回答「HTML 中交互能不能走通」；人评审回答「设计是否顺手」；P2/P3 回答「真实程序是否正确、安全、可用」。三者可以共享同一场景**描述**，但互相不能借用 `PASS`。

**自动化触发边界**：只有 P0 手动验证不可靠（多分支复杂、需要反复迭代、易回归破坏）或现有浏览器自动化可直接低成本复用时，才做 P1 自动化；不为一个单页原型引入 npm/Playwright 工程。正式安全和权限测试必须完成其真实合同门槛，不能因原型简单而省略。

## 4. 什么时候需要重新设计原型？

- **先模拟**：新增跨模块路径、复杂表单依赖、用户上下文或产品作用域切换、高危/不可逆操作、UNKNOWN/授权错误恢复，或用户明确指出当前流程难以操作。
- **通常跳过**：已确认设计的小幅文案、简单列表列/筛选、局部间距、既定 Token 的视觉微调，或者正式代码里交互未变的普通修复。
- **先改权威再考虑原型**：如果改动涉及新增状态、权限、产品决策、API/RPC 签名，必须先由 spec/architecture 作出明确决定，不能让一个方便演示的 mock 成为新合同。
- **现阶段特殊门槛**：AisenCore 的 UI-G0 尚未批准；按风险跳过某个日常原型，并不等于项目级视觉基线、正式开发许可证已通过。

## 5. Plans 里记录哪些信息就够了？

在当前任务的「决定/验证」位置记一小段，不另建逐步审批单：

- **场景与合同**：例如 `admin-codes-unknown`，关联 D3-UI/RPC。
- **原型引用**：有文件时写 `docs/interaction-benchmarks/admin-codes-unknown/index.html` 与**实际已审阅的 Git commit/内容版本**。
- **交互决定**：认可/需修改/待审，以及关键分支如何处理。
- **视觉决定**：已认可/待确认、Token 与宽度覆盖范围。
- **正式施工许可**：明确授权范围，若未表达则 `NOT AUTHORIZED`。
- **测试状态**：只写本次 P0/P1/P2/P3 的 `NOT RUN / PASS / FAIL` 和必要证据路径，未运行不填 PASS。

代码实现和真实测试完成后，Plans 按其原有完成/删除规则收敛，不保留平行数据源。
