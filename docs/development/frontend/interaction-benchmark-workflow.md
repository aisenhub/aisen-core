# Admin 原型验证与 AI 开发工作流

> **定位**：保留可跨 AisenFlow 等项目复用的「明确问题 → 按需验证 → 用户判断 → 使用成熟框架实现 → 真实验收」流程。此文档不是第二套业务架构、Theme、MVP 功能清单或自动审批系统。当前历史 UI-G0A 未签收、正式施工未授权的状态不因本文改变。

## 1. 按风险选择工作方式

| 任务 | 推荐方式 |
| --- | --- |
| 新的跨模块任务、复杂表单/高风险权限动作、`UNKNOWN` 与并发异常恢复 | 先验证真实任务链及正负状态；选择适合的高质量交互原型 |
| 用户尚未决定的导航、视觉、信息层级或组件方案 | 提供有限、可比较的候选与关键状态，请用户明确反馈；旧色板和布局不自动成为默认 |
| 已确认方案内的普通文字、筛选、列、表单小修复 | 在已获开发授权时直接用 React-admin 组件实施并回归，无须重建全景原型 |
| 业务字段/RPC/权限事实不清或相互冲突 | 回到 spec / architecture 收敛合同，不能让 UI 模拟替代后端决定 |

## 2. 六步闭环

1. **对齐合同**：读取 [需求](../../spec/requirements.md)、[Admin 应用与权限合同](../../architecture/applications/admin-console.md)、后端接口及本任务相关的 [UX 规则](./admin-design-rules.json)，识别必须保护的事实和可重新设计的界面。
2. **确定验证范围**：只列出本次需要回答的交互/视觉问题和关键状态，确定最小足够场景；不硬性规定全景模块、Theme 数量、固定宽度、引导容器或生产页面结构。
3. **制作与验证原型**：按 [产物规范](./interaction-benchmark-spec.md) 使用合成数据，验证实际操作、状态转移、权限范围、异常与恢复、基本可用性；避免静态假成功和无法使用的视觉壳。
4. **用户体验与明确决策**：给出清楚的试用步骤、候选差异和问题，记录具体认可项与未认可项。交互确认、视觉/Token 确认、正式施工授权相互独立；原型内没有自动签收器。
5. **正式工程实现**：在用户授权的范围内使用 React-admin + MUI + TypeScript、单一 Theme、现成 Resource/DataProvider/AuthProvider 和最小必要适配；根据已认可行为选择最佳标准组件，不强制对原型 DOM 进行 1:1 转译。
6. **分级验证与回归**：P0 检查演示的可操作性/关键路径，P1 只在确有复杂状态时加轻量状态回归；P2 在正式代码连接真实 RPC/RLS/Auth 时进行功能和负向安全测试；P3 用真实浏览器测试操作、焦点、窄屏、可访问性与性能。未执行项标记 `NOT RUN`。

## 3. 交付记录与不变量

- 每个任务在现有 Plans/TODO 中简要记录原型路径与版本、实际测试场景、用户决策、开放问题、授权范围和验证证据，不新增独立签收表/重复日志。
- 模拟通过不等于真实 MFA/权限/事务/性能或可访问性通过；安全合同和可信后端决定不允许由前端设计覆盖。
- 只有需求涉及复杂恢复或实际跨模块联动时才使用模拟共享状态；原型辅助控件与正式业务界面应分离，但不强制采用某种实验室外壳。
- UI 风格、导航、模块组织和组件样式应依据当前任务自由设计，最终经用户评审与真实 React-admin 组件验证。历史示例不得以「工业级保真」名义绑死当前 UI。
