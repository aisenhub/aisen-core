# 交互优先的轻量验证与 AI 正式开发工作流（Interaction Benchmark）

> **定位**：AisenCore Admin 的 UI-G0A 设计验证方法；以后可供 AisenFlow 或其他项目复用。这是开发流程，不是产品需求、后端业务合同、Theme 权威或新的自动化系统。
>
> **当前状态（2026-10-22）**：项目所有者选择「交互逻辑优先、视觉辅助、按复杂度决定是否制作原型」。`灵感/` 下现有 HTML 只是候选演示，**UI-G0A NOT APPROVED**；还未完成真实签收，正式 Admin、SQL/云端业务开发未获授权。方法论确认 ≠ 原型签收 ≠ 正式施工许可。
>
> **权威来源**：需求见 `docs/spec/requirements.md`；业务/权限/RPC 见 `docs/architecture/`；Admin 页面行为见 `docs/Plans/aisencore-mvp/aisencore-mvp-d3-ui-admin-uiux-design.md`；视觉与 UI-G0 签收见 `docs/architecture/applications/admin-ui-design-system.md`。本文只规定流程；**交互与视觉内容的详则**见[原型产物规范](./interaction-benchmark-spec.md)，**开发复用和何时测试**见[原型→正式实现规则](./prototype-to-production-rules.md)，**网页存放与清理**见[产物目录](../../interaction-benchmarks/README.md)。

## 1. 目标、优先级与边界

- **交互第一（可按约 80% 评审精力）**：重点验证业务模块间的导航与数据上下文、任务是否顺畅闭环、表单联动/防误操作、异常/高风险分支如何恢复，用户是否知道下一步做什么。
- **视觉第二（可按约 20% 评审精力）**：信息层级、布局和密度、按钮与弹窗位置、桌面/窄屏可读性、候选样式与配色。比例是帮助集中精力的建议，不是强制评分；无障碍焦点、状态可辨识、风险告知不能省。
- **验证不等于实现**：HTML 使用已批准的字段与业务语义，状态与数据为本地模拟；不连接生产 Supabase，不暴露真实秘密，不通过模拟成功声称事务、权限、性能、安全、WCAG 或浏览器 E2E 已通过。
- **不做双套前端**：原型是暂时的交互实验，正式代码仍用 React-admin/MUI、全局主题和最少 Provider 胶水层。DOM/CSS 是参考，不保证像素级或「一秒无损换肤」转换。
- **只模拟不确定性**：按「一条任务旅程 + 必要相邻模块」组织，不为每一个数据库表/页面复制完整 Admin，也不开发原型框架、打包工具或模拟后端。

## 2. 先分流：不是每个任务都做 UI-G0A

| 当前任务 | 推荐处理 |
| --- | --- |
| 已确认交互的小型文案、普通字段、表格列/筛选、局部布局调整 | **直接正式实现 + 必要回归**，不再生成新原型 |
| 新的跨模块业务旅程、上下文切换、复杂表单及多状态联动 | **先做轻量交互原型**，验证任务是否顺手 |
| 不可逆/高危操作、`UNKNOWN`、401/403/409、授权与敏感明文恢复 | **先做关键正常与异常分支原型** |
| 业务字段、状态语义或不变量尚有冲突 | **先查现有权威并收敛契约**，不能让 HTML 假实现决定数据合同 |
| 正式 UI 已有、交互未改变 | **直接修改真实代码并运行测试**，不长期双轨维护原型 |

AisenCore 首次 UI-G0 审批还应满足既有代表性场景、宽度、组件状态和真实视觉签收要求；「简单改动跳过原型」**不表示跳过当前未完成的项目级 UI-G0 门槛和施工授权**。

## 3. 六节点最短闭环（按需跳过原型节点）

1. **识别风险与读取合同**：从已有需求/架构/D3-UI 找到真实字段、操作者、任务起止点、跨模块跳转、关键错误分支。只读相关章节，不复制一份新需求书。
2. **AI 快速模拟**：确有交互不确定性时，在 `docs/interaction-benchmarks/<scenario-slug>/index.html` 产出一份无需安装、双击可用的自包含 HTML；按[产物规范](./interaction-benchmark-spec.md)覆盖真实决策相关的状态、跨模块路径与必要视觉维度。点击、切换、输入必须产生可观察的状态/下一步，不能全部用「操作成功」Toast 代替。
3. **同时提供体验引导**：交付网页时**必须至少提供一个可执行的操作指引**，帮助用户知道从哪里开始、按什么顺序点、观察什么、如何反馈。默认放在当次对话；离线/多场景可放 HTML 的「怎么体验」页面，需转交才单独成文档；不强制三种载体全做，见第 4 节。
4. **人体验、AI 定向修改**：用户观察业务是否顺畅，直接说出问题；AI 按反馈迭代。**分别记录交互认可、视觉认可、正式施工授权**，三者不可互相推定；未明确决定就记 `PENDING`。
5. **AI 正式实现**：只有相关 UI-G0 与任务开发权限获明确批准后，复用 React-admin/MUI 组件和现有可信 API；不照搬原型手写 CSS/假数据，不发明新 RPC。
6. **分级验证与真实回归**：原型交付前执行 P0 轻量走查，交互复杂才做 P1 自动化；正式实现后按 P2/P3 做浏览器 E2E、RPC/权限负向与 UI-G3 检查（[分级规则](./prototype-to-production-rules.md)）。未运行则 `NOT RUN`；实际失败要修实现或重新讨论交互，而不是拿原型 PASS 当证据。

## 4. 引导、交接与审批边界

每次交付原型必须帮助用户知道**怎么开始、点击什么、每步观察什么、如何反馈**；默认当次对话提供，离线评审时可使用网页内「怎么体验」，确需交接才独立成文档。**具体要素和禁用假签收规则只在[产物规范第 4 节](./interaction-benchmark-spec.md)维护**。

认可后的行为、原型路径及 Git 版本、未决事项在**现有 Plans** 留最小增量记录；交互认可、视觉/Token 签收与正式施工许可彼此独立。可复用资产、禁止复制的模拟代码和 P0～P3 测试边界以[正式实现规则](./prototype-to-production-rules.md)为准，流程本身不建立新的审批系统或第二套交互代码。

## 6. 向 AisenFlow 迁移时的边界

可复用的是「识别交互风险 → 最小模拟 → 人类决策 → 正式实现 → 运行证据」的职责链，而非强制增加四个 Agent、新编排引擎、专用服务或通用设计平台。先通过 AisenCore 的发码 UNKNOWN / 用户与权益跨模块场景验证能否减少返工，再视收益推广。当前 `灵感/` 里的候选 HTML 不构成 UI-G0A 通过证据。
