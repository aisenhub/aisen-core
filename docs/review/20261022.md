### **三、详细的分支架构（Detailed Sub-Architectures）问题与修改建议**

* **修复 redeem\_code 的兑换码有效性探测侧信道漏洞（B-01，高危）**：  
  * **问题细节**：在 docs/architecture/database/entitlements-and-redemption-constraints.md:65 和 docs/Plans/aisencore-mvp/aisencore-mvp-d1-database-implementation-design.md:155-163 中，redeem\_code(code) 的执行顺序是：先通过 code\_hash 查找兑换码 → 若找不到码则记入 redemption\_rate\_limits 并返回 REDEEM\_CODE\_INVALID → 若找到码，再检查该用户在对应产品的成员状态，若为 left 或 suspended 则返回 MEMBERSHIP\_LEFT / MEMBERSHIP\_SUSPENDED。  
  * **安全后果**：由于未兑换过该码的新用户在猜测不存在的码时得到 REDEEM\_CODE\_INVALID，而在该产品处于 left（可由用户自己点击退出轻易构造！）的账号一旦猜中真实存在的兑换码，就会得到 MEMBERSHIP\_LEFT（且码不被消耗）！如果 MEMBERSHIP\_LEFT 分支不计入失败限流，攻击者只需主动退出产品（状态变为 left），即可**无视 15 分钟 10 次限流，无限暴力枚举全平台有效兑换码**；即便计入限流，返回不同的错误码也向已退出用户泄露了“该码真实存在且属于该产品”。  
  * **修改建议**：  
    1. 将接口签名改为 **redeem\_code(product\_key text, code text)**，要求兑换时指定目标产品；  
    2. 在查询 redemption\_codes **之前**，先校验用户在 product\_key 的成员状态：若为 left 或 suspended，无需查码即直接返回 MEMBERSHIP\_LEFT / MEMBERSHIP\_SUSPENDED；  
    3. 若成员状态合法，再去查 redemption\_codes，且当码不存在、已撤销、已过期、已用尽**或码所属 product\_id 与传入 product\_key 不一致**时，一律计入 redemption\_rate\_limits 并统一返回 REDEEM\_CODE\_INVALID。  
* **加固 redeem\_code 子事务隔离、细化 L0 锁粒度并定义 Advisory Lock 编码（B-02）**：  
  * **问题细节**：  
    1. redeem\_code 为了持久化 redemption\_rate\_limits 而规定“业务拒绝不抛异常，以 HTTP 200 ok=false 返回”，一旦未来维护者在拒绝分支前误加任何 DML，就会将半成品状态连同限流计数一并提交；  
    2. docs/Plans/aisencore-mvp/aisencore-f01-f04-security-convergence-design.md:42 要求**所有**管理写 RPC（包括发码、改套餐、改产品、授权益）都先抢同一个全平台排他锁 L0，导致无关的管理操作互相串行阻塞；  
    3. L0、L1(user\_id)、L7(user\_id, plan\_id) 均依赖 PostgreSQL 64-bit pg\_advisory\_xact\_lock，但未定义如何从 128-bit UUID 映射为 64-bit bigint 且保证 L0/L1/L7 之间不发生哈希碰撞。  
  * **修改建议**：  
    1. 在 private.redeem\_code\_core 中使用 PL/pgSQL 子事务块（BEGIN ... EXCEPTION WHEN ... END; 即内部隐式 SAVEPOINT）包裹核销写入逻辑，业务拒绝时显式回滚内部子事务块，再在外层更新 redemption\_rate\_limits 并返回 ok=false；  
    2. 将 L0 锁改为**读写锁分离**：仅修改管理员资格或封禁管理员的操作（admin\_revoke\_admin、admin\_block\_account、admin\_grant\_admin）获取排他锁 pg\_advisory\_xact\_lock(L0)，其余常规管理写 RPC 获取**共享锁 pg\_advisory\_xact\_lock\_shared(L0)** 后复核管理员资格，兼顾 M1 安全保底与并发吞吐；  
    3. 明确 Advisory Lock 键生成函数：使用双 int4 参数 pg\_advisory\_xact\_lock(class\_id int4, obj\_hash int4)，其中 class\_id 固定传入锁层级常量（1 代表 L1 账号锁，7 代表 L7 用户套餐锁），彻底消除跨层级锁碰撞。  
* **解耦 free 基础套餐冻结限制，补齐周期续期后的总有效期返回字段（B-03）**：  
  * **问题细节**：  
    1. docs/architecture/domains/billing-and-entitlements.md:38-40 规定保留 plan\_key='free' 作为无授权记录时的默认基础套餐，同时规定 UNIQUE(product\_id, plan\_key) 且套餐一旦被引用不可原地修改、需新建 v2 版本。若未来需要调整 Free 用户的默认额度，新建 free\_v2 会导致按 plan\_key='free' 查找的基础逻辑失效；  
    2. 同套餐周期续期生成的 grant 其 starts\_at 在未来，而 CheckAccess 只过滤 starts\_at \<= now()。用户剩余 3 天时充值 365 天，调用 CheckAccess 或 GetMyProducts 看到的 ends\_at 仍是 3 天后（前次审计 S2 提出后仍未在 api-contract-and-mvp-acceptance.md:37-43 和 D2 中落地）。  
  * **修改建议**：  
    1. 在 admin\_create\_codes 和 admin\_grant\_entitlement 中明确**禁止对 plan\_key='free' 发行兑换码或创建授权记录**，使 free 永远不被 grant/code 引用，允许管理员按运营需要调整 free 基础配额；  
    2. 在 CheckAccess 与 GetMyProducts 的 entitlement 返回结构中，将同产品下未撤销且连续衔接的周期授权合并计算最远到期时间（或同时返回 current\_period\_ends\_at 与 effective\_ends\_at），消除用户充值后到期日不变的困惑；  
    3. 将 docs/Plans/aisencore-mvp/aisencore-mvp-auth-entitlement-mfa-efficiency-design.md:70 候选快照中语义模糊的 "valid\_until": null 拆分为显式的 "is\_lifetime": boolean 与 "expires\_at": string | null。

### **四、MVP 架构与计划（及 MCP 专项评估）问题与修改建议**

* **统一 U01～U11 决策台账，消除 6 份计划文件的状态冲突（M-01）**：  
  * **问题细节**：docs/Plans/aisencore-mvp/aisencore-mvp-d3-admin-infrastructure-design.md:3：U01 Aisenlens 本地优先、U02 首批 R2 备份已确认；**U03～U11 仍未确认**。  
    docs/Plans/aisencore-mvp/aisencore-mvp-d3-admin-infrastructure-design.md:7：**U03 公众注册及 U04～U11 部分方向已确认**。  
    同样的问题出现在 F01-F04:11、F05-F08:5、D1:301-306、D2:357-365。  
  * **修改建议**：删除 D0、D1、D2、D3、F01、F05 各文档首尾重复维护的 U03～U11 状态表与叠加的日期补丁块，统一指向 docs/Plans/aisencore-mvp/aisencore-u03-u11-user-decisions-2026-10-22.md 和 docs/Plans/TODO.md。  
* **砍掉冗余的字节级请求哈希列，修复 entitlement\_grants 的列级授权隐患与 admin\_grant\_entitlement 时间契约冲突（M-02）**：  
  * **问题细节**：  
    1. F05 为 redemption\_code\_batches 设计了复杂的 config\_fingerprint bytea(32)（canonical v1 JSON 哈希），但该表本身已经持久化了 product\_id, plan\_id, quantity, grant\_duration\_days, max\_redemptions, expires\_at 全部 6 个强类型字段；  
    2. F05 在 public.entitlement\_grants 表上新增了 admin\_request\_fingerprint bytea(32)，并在 D1:96 规定**该列不可通过 Data API 对普通用户或管理员暴露 SELECT**。一旦对 public.entitlement\_grants 撤销表级 SELECT 改用列级 GRANT SELECT，所有未显式手写全部列名的客户端查询（如 select=\*）都会直接触发 PostgreSQL 42501 permission denied；  
    3. F05:24 要求 admin\_grant\_entitlement 必填非空 starts\_at 和 ends\_at，与 billing-and-entitlements.md:42 规定的“同套餐续期由服务端锁内按最晚未撤销 ends\_at 自动顺延”发生冲突。  
  * **修改建议**：  
    1. **彻底移除 config\_fingerprint 与 admin\_request\_fingerprint 两个哈希列**：当 (created\_by, request\_id) 或 (source\_type, source\_ref) 命中已有行时，直接在 SQL 内用 IS NOT DISTINCT FROM 比对已落库的强类型业务列（产品、套餐、数量、时长、过期时间、目标用户、原因），既无需维护 JSON Canonicalizer，又让 entitlement\_grants 和 redemption\_code\_batches 保持干净的表级 GRANT SELECT；  
    2. 将 admin\_grant\_entitlement 的时间参数改为 (..., duration\_days integer NULL, starts\_at timestamptz DEFAULT NULL, ...)：当管理员未指定具体 starts\_at 时，由数据库在 L7 锁内自动按 max(transaction\_timestamp(), latest\_unrevoked\_ends\_at) 计算顺延区间。  
* **简化 Aisenlens 配置备份链路并修复 reserved\_bytes 配额死锁（M-03）**：  
  * **问题细节**：  
    1. Aisenlens 仅备份“白名单非敏感平台配置与模板文本 JSON”（通常数 KB 至数十 KB），D2 与 F03 却设计了 intent → staging PUT → complete → HEAD ETag → Worker 条件 CopyObject → 下载解析 JSON 校验白名单 → 异步清理孤儿 的重型状态机；  
    2. 在配额计算 ready \+ reserved 时，若客户端调完 backup-intent 后崩溃或断网未调 backup-complete，而在 Supabase Free 环境下又未配置可靠的分钟级定时清理任务，pending 状态的 reserved\_bytes 将永久占用用户配额。  
  * **修改建议**：  
    1. **首选简化方案**：对纯文本配置备份（限制单次 ≤ 256KB），直接由客户端 POST JSON 至 aisenlens-backup Edge Function，在内存内一次完成白名单 JSON 校验、SHA-256 计算、服务端直写 R2 final\_key 与 DB ready 落账，砍掉 staging\_key、CopyObject、额外 Worker 和孤儿对账；  
    2. **若保留预签名直传**：在 SQL 计算用户已占配额时，将预留条件限定为 status \= 'ready' OR (status IN ('pending', 'verifying') AND expires\_at \> transaction\_timestamp())，使过期的 pending 记录在查询时自动失效，无需依赖外部定时任务即可避免配额锁死。  
* **补充评估：若您的“MCP 计划”确实指引入 Model Context Protocol（MCP）**：  
  * **架构定位边界**：切勿在 AisenCore 公共云端建设托管式多租户 MCP Server（否则会打破“不建公共 AI 网关、不代管用户 AI Key 与本地拉片数据”的铁律）。  
  * **推荐双端 MCP 方案**：  
    1. **Aisenlens 本地端 MCP Server（面向用户）**：在 Aisenlens 桌面客户端内置本地 stdio / localhost MCP Server，将用户的本地拉片项目、时间轴标记、切片与模板暴露为 MCP Resources / Tools，供用户本机的 Claude Desktop / Cursor 等 AI 客户端直接调用；在启动该高级功能时复用现有的 check\_access('aisenlens', 'ai.mcp\_server') 在线复核；  
    2. **AisenCore 运维端 MCP Server（面向单人管理员）**：既然全平台只有您一名运营者（U05），可编写一个仅在您本机运行的轻量 Admin MCP Server（封装 admin\_create\_codes、admin\_grant\_entitlement、admin\_lookup\_users 等受保护 RPC），让您在本地 IDE/AI 助手中用自然语言安全完成日常小批次发码与授权，作为 React-admin Web 后台的高效补充。

### **五、Admin 架构与计划（Admin Architecture & Plans）问题与修改建议**

* **解除 UI-G0 流程死锁，大幅瘦身前端设计规范（A-01，高优）**：  
  * **问题细节**：  
    1. docs/architecture/applications/admin-ui-design-system.md:129-185 要求在禁止写任何 apps/admin 代码的前提下，先产出 4 类代表页 × 5 种屏幕宽度（含 320px 手机屏）× 全部交互状态的高保真视觉稿并完成签收，否则 UI-G0 \= BLOCKED；而在没有专职 UI 设计师画 Figma 且不允许写代码渲染 MUI 组件的情况下，这一要求直接造成了**无法开工的死锁（Catch-22）**；  
    2. docs/development/frontend/ 从外部项目迁入了 2,123 行的 admin-design-rules.json（62 条规则）和 7 份规范文档，对于一个仅站长一人使用的内部 React-admin 管理台而言严重过度设计，且与 AGENTS.md 第一条“优先复用 React-admin 已有成熟能力”冲突。  
  * **修改建议**：  
    1. **将 UI-G0 改为“代码原型签收关口（Coded Theme Prototype Gate）”**：允许直接用 React-admin \+ MUI createTheme 编写最小可运行的 theme.ts、AdminLayout 和 4 个静态 Mock 页面，在浏览器中渲染出真实界面供您直接预览确认，确认即通过 UI-G0；  
    2. **裁剪响应式与规则负担**：明确 Admin 仅针对桌面端（≥1200px 与 768～1199px）做完整布局验收，窄屏（\<768px）仅保证登录/MFA 和紧急封禁可用；将 62 条 JSON 规则降级为可选参考指南，不再作为阻塞开发的逐屏门禁。  
* **用 private 受保护只读 RPC 替代 admin-user-lookup Edge Function，彻底解决成员页 N+1 查询瓶颈（A-02）**：  
  * **问题细节**：docs/architecture/applications/admin-console.md:26, 48 与 docs/architecture/database/database-access-and-transactions.md:21 认为“客户端不访问 auth.users，且 Auth Admin SDK 无批量按 ID 查邮箱接口，因此成员列表每页对有限 UUID 并发调用 Edge Function getUserById 补邮箱，邮箱搜索用 listUsers 分页扫描并返回 search\_incomplete”。这会导致 Admin 在查看成员、授权、兑换、限制、审计 5 个列表页时，每翻一页都要发起 25～50 次 Auth Admin API 请求，既缓慢又极易触发限流，且用户超过几百人后邮箱搜索就会失灵。  
  * **修改建议**：  
    1. **直接砍掉 admin-user-lookup Edge Function**！Supabase 的 auth.users 表本来就位于同一个 PostgreSQL 实例的 auth schema 中；  
    2. 在 PostgreSQL 中新增一个受保护只读 RPC：public.admin\_lookup\_users(p\_user\_ids uuid\[\] DEFAULT NULL, p\_email text DEFAULT NULL, p\_limit int DEFAULT 50, p\_offset int DEFAULT 0)（外壳 SECURITY INVOKER → 内核 private SECURITY DEFINER）；  
    3. 内核首行强制校验 private.is\_platform\_admin()（含 aal2、active、未 blocked），通过后直接在数据库内对 auth.users 执行 SELECT id, email, created\_at, email\_confirmed\_at, last\_sign\_in\_at（支持 id \= ANY(p\_user\_ids) 批量补全和 lower(email) \= lower(p\_email) 索引级精确查找）。**1 次 SQL RPC 请求即可在 2ms 内补全整页 50 个成员邮箱或完成全库精确邮箱搜索**，零 Edge Function 开销、零 service\_role 密钥暴露、零 search\_incomplete 缺陷。  
* **将管理写 RPC 收敛回 React-admin 标准 DataProvider 与安全只读视图（A-03）**：  
  * **问题细节**：  
    1. docs/Plans/aisencore-mvp/aisencore-mvp-d3-admin-infrastructure-design.md:45-59 设计了独立于 dataProvider 之外的 rpcAdapter.execute(operation, payload)，并禁止 dataProvider 的 create/update/delete。这会导致 React-admin 的 \<Create\>、\<Edit\>、\<SimpleForm\>、自动乐观/悲观缓存失效（TanStack Query 自动刷新列表）无法工作；  
    2. redemption\_codes 表因含 code\_hash 而采用列级 GRANT SELECT，React-admin 默认若未严格拼写列白名单会直接触发 PostgREST 报错。  
  * **修改建议**：  
    1. 为 redemption\_codes 创建一个不含 code\_hash 的安全只读视图 public.admin\_redemption\_codes\_view，让 DataProvider 直接对该视图做标准读取；  
    2. 在自定义 DataProvider 内部实现标准方法到受保护 RPC 的路由映射（例如 dataProvider.create('code-batches', { data }) 内部转调 supabase.rpc('admin\_create\_codes', ...) 并返回 { data: { id: res.batch\_id, ...res } }），从而 100% 复用 React-admin 原生的表单、通知、错误处理与自动缓存失效机制。  
* **补齐单人运营下的 Admin TOTP MFA 物理防锁死预案（A-04）**：  
  * **问题细节**：U05 确认只有您一名实际运营者，且强制开启 aal2 TOTP MFA。此时数据库的 M1（防止撤销/封禁最后一名管理员）只能防误点按钮，无法防止手机丢失或验证器损坏导致的后台锁死。  
  * **修改建议**：在 D3 迁移步驟 M04（首次管理员引导）中增加一条硬性操作要求：首次 enroll TOTP 时，必须将同一个 TOTP Secret 同时绑定至两台独立设备（或离线加密密码库），并在运维文档中写明当验证器遗失时通过 Supabase CLI / Dashboard SQL 重置 auth.mfa\_factors 对应记录的标准恢复 SQL。
