## 1. 项目定位与原则

1. **多 SaaS 公共底座**：AisenCore 为多个彼此独立的 SaaS 产品提供值得复用的轻量公共能力，而不是某个本地拉片产品专用后端，也不把所有产品业务合并成一个巨型应用。
2. **一套公共账号、权益按产品独立**：用户可用一个平台账号访问多个产品；每个产品的套餐、定价、会员和功能权限相互独立。购买产品 A 的 Pro 不会自动获得产品 B 的 Pro。
3. **统一必要能力，独立产品业务**：公共平台集中管理身份、产品、必要权益与轻量计费；各产品自己的项目、任务、业务内容、业务规则和数据尽量独立组织。业务职责独立**不等于**必须为每个产品立即建立独立数据库或 Supabase Project。
4. **适用三种产品模式**：
   - **本地优先**：主要业务数据和处理位于用户设备，按需要调用公共账号/权益/计费能力。
   - **云端业务**：产品可以主动接收、处理用户上传的数据和文件，使用其自身的业务服务与数据库。
   - **混合型**：本地和云端分别负责相应业务，公共身份/权益/计费仍可复用。
5. **成熟方案优先**：优先评估并复用合适、活跃、许可证适用的成熟开源方案，重点比较功能适配、二次开发、部署维护和整体复杂度。只有自研能显著降低整体复杂度时才优先自研，不重复造框架。
6. **明确排除**：不采用 Payload；AisenCore 是独立新项目，不默认引用或复用已舍弃的 Aisenhubplatform 的代码、设计、数据、配置或模块，除非用户明确指定并批准具体部分。

## 2. 首版公共平台范围

第一版采用**最小公共核心**，包括：

| 范围 | 首版必须具备的能力 |
| --- | --- |
| 统一用户身份 | 账号、登录与身份关联，服务多个 SaaS |
| 产品及成员管理 | 公共平台注册/识别 SaaS 产品，统一管理产品成员加入、退出、封禁及恢复，产品级权益独立 |
| 会员资格与授权 | AisenCore 只维护指定产品的身份/成员关系、当前 Pro 资格及起止时间、兑换码/直授/撤销和审计；各 SaaS 自己定义并执行 Free/Pro 具体功能与额度 |
| 兑换码及分阶段支付 | **先做平台自有兑换码开通权益**；初期暂定使用爱发电进行打赏/支付与回调，保留以后增加支付宝、Stripe 的能力，不要求首版同时完成所有支付通道 |
| 内部 Admin | 用一个必要的管理入口管理上述公共数据和流程 |
| 跨 SaaS 用户反馈 | 按产品收集文字和 0～2 张图片，Admin V3 按四队列轻量分诊/标记/私有备注处理（旧 V2 公开回复/五态只读保留），可受控 ZIP；结构化数据用公共 PostgreSQL、私有图片用 R2 |

首版**不追求**大型综合运营后台、复杂财务分析报表、多组织运营平台、复杂企业多租户计费或完整的高级统计体系；但不能因此省掉支付一致性、安全管理必需的少量事件记录与基本审计能力。具体操作清单和最小审计范围在实际接入时细化。

## 3. 统一账号、登录与授权

- **已选身份服务**：Supabase Auth；首版仅要求**邮箱 + 密码**登录，全平台统一身份。
- **首版明确面向公众开放邮箱注册并正常运营（U03 已确认）**，不是邀请制 Beta。正式开放前必须完成邮箱确认和密码找回，统一 Aisen 身份品牌并使用**自定义 SMTP（U06 方向已确认）**；真实域名、服务商、发件地址、回调域名、防刷与邮件送达仍待确定及验证。
- **未来可选**：手机号验证码、邮箱验证码、免密链接、Google 等第三方登录，以及需要另行验证适配方案的微信登录。不要求首版接入这些方式，也不把微信认定为 Supabase 的内置现成提供商。
- 全平台统一账号不自动等于跨不同站点的无感 SSO。跨域登录体验、身份绑定、多设备会话规则后续确定。
- 账号已认证不等于获得任何产品 Pro 权益，也不等于具备 Admin 管理权限。授权必须按用户、产品和具体操作核验。
- **产品成员 API 最小原则**：首次合法使用需登录的产品服务时按需幂等创建成员；可信 SaaS 后端用现有用户 JWT 代用户调用公共接口，纯本地客户端可直接以本人 JWT 调用。状态查询无副作用，云端受保护的关键操作由可信服务端复核，客户端状态缓存不作为最终授权证明；不预建独立授权 Token、通用 API 网关或复杂缓存。详见[公共 API MVP 与 SaaS 接入](../architecture/backend/public-api-and-saas-integration.md)。
- **统一用户 MVP 安全与会话**：必须避免普通用户读取/修改他人资料；成员变更和最小审计不可出现部分成功；管理员权限需可信、可及时撤销；产品级封禁与全局限制相互独立；邮箱确认和密码找回需可靠，跨 SaaS 不强求共享登录态。具体隔离与事务方案见[数据库权限](../architecture/database/database-access-and-transactions.md)，平台限制见[账号生命周期](../architecture/domains/platform-admin-and-account-lifecycle.md)，接口错误/验收见[API 契约](../architecture/backend/api-contract-and-mvp-acceptance.md)。
- **Admin 治理入口分工**：平台账号封禁与解封只从用户中心的账号状态卡操作；平台管理仅提供产品、审计和管理员权限，管理员资格授予/撤销使用独立专用弹窗与路由，不复用封禁弹窗。两类操作沿用受限身份查询、理由、确认、AAL2 实时权限及最小审计。
- **首版低请求量身份认证**：Supabase Auth SDK 统一维护登录/会话/必要的自动刷新；**不得每次页面/点击都联网 `getUser()`**，优先复用当前有效会话和经可信验证的 JWT。普通用户**不强制 TOTP MFA**；JWT 仅证明身份，不将缓存 Pro/管理员角色作为当前授权。实际 Auth/数据库/Edge 免费配额和令牌新鲜度需在真实环境取证，长期信任边界见[多 SaaS 会话架构](../architecture/applications/auth-and-multi-saas-sessions.md)及[管理员领域](../architecture/domains/platform-admin-and-account-lifecycle.md)；测试排程留在 Plans。
- **BaaS/计量 MVP 原则**：复用 Supabase 原生 Auth、PostgREST/RLS/可信 PostgreSQL RPC 和少量必要 Edge，**首版不新增 Redis、独立公共服务器、公共积分余额/通用消费 RPC 或 AisenCore AI 网关**。未来产品真有可扣减额度时，必须由产品可信服务**决定费用、验证请求主体及属主**，在受保护数据库事务内做正数/边界校验、并发扣减/预留、幂等与必要审计；绝不授权前端直写余额/权益。Supabase Free 的 Unlimited Data API Requests **并不等于数据库算力、流量和 Edge 用量无限**，真实性能和成本需按计划单独验收。长期约束见[权益领域](../architecture/domains/billing-and-entitlements.md)、[可信事务](../architecture/database/database-access-and-transactions.md)。

### 统一产品成员规则

- **公共平台统一管理产品成员**：首次实际使用某 SaaS 需要账号的服务时，在可信服务端验证后按 `user_id + product_id` 幂等创建 `active` 成员；公共账号注册不自动加入所有产品，匿名免费本地功能不触发加入。
- **成员状态**只包含 `active`（正常）、`left`（主动退出）、`suspended`（暂停/封禁）；从未加入由“无记录”表示。成员关系与平台账号、产品运行状态、会员权益及产品业务权限分别管理。
- 用户主动退出后不能因为登录自动恢复，只能主动确认重新加入；封禁后仅可信管理员能够解除，重复登录、兑换与支付不得绕过限制。产品停用不批量改变成员或会员记录。
- **退出与删除分离**：退出不自动删除业务数据或本地文件、不撤销历史权益、不取消自动续费、不退款；原授权有效期和试用期自然流逝，重新加入后根据原授权、现存数据和当前权限判断。
- 公共平台负责产品成员资格，各 SaaS 负责自身项目、任务、协作权限与业务数据。当前成员状态由公共成员关系记录保存，成功的关键状态变更以独立事件记录做最小审计，**不通过事件重放计算当前成员状态**。关键变更与审计需共同成功或共同失败；具体机制见[数据库约束](../architecture/database/database-constraints-and-audit.md)，状态规则见[成员生命周期](../architecture/domains/membership-lifecycle.md)。

### 已批准的兑换与管理员最小变更合同

- **兑换接口与错误隔离（DEC-01 已批准 A）**：正式公开接口为 `redeem_code(product_key, code)`；目标产品是用户声明而非权限依据。服务端先验证身份、全局限制、限流、声明产品和其成员 `left/suspended` 状态，再检查码；声明产品与真实码归属必须一致，无效/跨产品/撤销/过期/用尽统一返回 `REDEEM_CODE_INVALID`，不得向不可兑换成员泄露码有效性。历史单参数 `redeem_code(code)` **仅为迁移时需清点和关闭的旧入口**，不得继续对公众提供可探测旁路。真实锁序、错误响应见[API 契约](../architecture/backend/api-contract-and-mvp-acceptance.md)。
- **管理直授与幂等（DEC-05 已批准 A）**：管理员人工授权可选**互斥的固定 `duration_days` 同套餐顺延**或**显式 `starts_at/ends_at`（含明确永久）**，不以省略结束字段偷偷发永久权益。可信端锁内计算并持久化首次请求的规范语义和时段；同管理员 `request_id`、相同参数只返回原授权，异参稳定返回冲突。技术元数据与兑换码哈希不得暴露到普通读取。
- **批量身份查询（DEC-06 已批准 A）**：Admin 用户/成员的有限 UUID 本页邮箱补全及受控精确邮箱搜索优先使用经隔离测试证明安全的受限只读 PostgreSQL RPC；若 Auth 权限/性能不满足则按**已批准的技术回退**改为单次受保护 Edge 批量聚合，不使用高权限密钥下发客户端，不保证未经测量的延迟值。

## 4. 产品权益与 Pro 在线校验

首版公共权益系统**支持四类权益**，每个 SaaS 只启用业务真正需要的类型：

| 已确定权益类别 | 业务要求 | 待具体产品确定 |
| --- | --- | --- |
| SaaS 自有功能策略 | AisenLens、AisenNote 根据 Core 的会员状态自行决定导出规格、AI、业务使用额度，并在相应可信执行端校验；Core 不保存功能开关 |
| 数量/使用额度 | 能限制功能次数、对象数量或其它产品使用额度 | 计数来源、周期、重置方式、本地使用量可信度 |
| 云端文件/备份配额 | 能限制产品相关存储或备份容量/数量 | 按大小还是数量、超额处理、删除后回收 |
| 有效期与订阅到期 | 权益在有效时间内生效，能反映订阅到期/撤销 | 宽限期、退款/取消影响、刷新时效 |

**桌面离线会员授权不是首版必须实现的能力**，只保留未来由确有需要的产品单独提出后扩展的可能；首版不建通用离线许可证系统。

**本地 Pro 在线校验原则**：

1. 需要 Pro 的本地客户端在**启动时完成有效的联网权益校验**，运行中根据各产品实际关键操作、进入高级功能或其他合适时机**合理复核**。
2. 公共权益系统是权威依据；不要求所有产品使用固定轮询周期，也不要求每次点击都访问后端。每个产品自主确定具体复核点。
3. 临时断网、校验失败、已启动任务和权益撤销后的使用体验，在具体产品接入时确定；不能由“运行中复核”推导出长期离线 Pro 使用权。
4. 不应无故禁止用户在断网时使用与 Pro 无关、原本可离线运行的本地免费功能。
5. 在线校验可以提高正常客户端授权的可控性，但**不能承诺防止用户复制网页、本地运行或修改客户端绕过限制**；云端的受保护业务操作必须在可信服务端真正校验权限，不能只靠前端隐藏按钮。

**AisenLens 本地 Pro 策略**：事件驱动按需复核、同环境/账号/产品并发请求去重，不固定轮询、不每次点击查询。已确认短时断网可在最近成功核验暂按最多 **15 分钟**测试的窗口内开始新的纯本地 Pro 操作，但不超过权益自然到期、不绕过已知撤权；新 AI 请求及云端创建/确认/下载等操作必须在线核验。15 分钟是已采纳的待实测参数，不是已验收的离线许可证；Free 启动不等待联网判断。具体时序见[本地优先架构](../architecture/applications/local-first.md)。

**Free / Pro 职责边界**：公共 AisenCore 不再保存 `products.free_features/free_limits`、`plans.features/limits`、套餐功能版本，不运行 capability 业务开关/额度 max 计算。Free 是没有有效 Pro 的派生结果，不是可兑换/直授套餐；AisenLens 匿名本地 Free 仍离线可用。各 SaaS 负责 Free/Pro 功能和额度，Core 仅认证产品成员、Pro 资格、开始/截止/永久、Grant 来源和撤销；30/365 天和永久是**授予时间参数**。以[轻量会员认证职责边界](../architecture/domains/membership-qualification-boundary.md)为唯一权威。

**Free / Pro 授权原则**：每个 SaaS 的 Free 业务能力由产品自己配置，不是可兑换或直授的 `plans`/Grant；**首期兑换码与人工直授只授予 Pro**。成功时记录该用户、该产品、对应 Pro 授权的来源明确、可到期/可撤销的 `entitlement_grants`，绝不通过写 `users.is_pro` 或成员状态来“升级”。当最后一份当前有效 Pro 授权到期或撤销，用户的 Pro 状态自然消失，重新按该产品默认 Free 能力评估，**保留授权历史，不另发 Free Grant，也无“降级”写操作**；若还有其他有效 Pro 授权则保持对应权益。在线访问仍取决于认证、全局限制、产品状态和成员准入；AisenLens 无账号离线 Free 不受影响。将来的试用/赠品/分群不自动复用 Free 授权，需单独决策。

## 5. 兑换码优先、分阶段支付与轻量统一计费

- 多产品**共享必要的订单、支付、订阅生命周期与权益同步逻辑**；各产品分别定义套餐、价格和会员范围，绝不自动跨产品共享 Pro。
- **业务优先级**：自有兑换码先于外部支付；当前有效的渠道顺序、不同阶段边界以[计费与权益专项](../architecture/domains/billing-and-entitlements.md#2-权益来源与支付接入顺序当前有效唯一权威)为唯一权威，此处不重复渠道表。
- **兑换码是平台独立能力**，不依赖爱发电或未来其它支付渠道的兑换码功能。由可信服务端核验兑换条件并为指定用户、指定产品**创建 Pro Grant**，不能单凭前端状态开通，也不改变会员身份布尔值。首期兑换码仅面向 Pro，支持按产品、Pro 授予时长、次数、有效期和撤销进行安全授权，防止重复与超量；**首版默认规则**见[计费专项](../architecture/domains/billing-and-entitlements.md#4-自有兑换码-mvp-规则)，更复杂的用户绑定和分发机制延后。
- 目标业务/授权模式保持 **月付订阅、年付订阅、一次性永久购买、免费试用** 四类；这描述平台**应支持的权益/商业模式**，并**不要求第一阶段的兑换码或爱发电立即具备所有支付渠道的自动扣费、自动退款等完整能力**。具体模式能否由爱发电直接承载应按其实际功能核实。
- 一次性永久购买应形成有明确权益范围的**非周期续费授权**，不伪装成“永不到期的周期订阅”。免费试用是否绑卡、是否自动转付费、试用时长和额度仍待定。
- **首发 Aisenlens 的 Pro 已确定支持 30 天、365 天、永久三种非自动续费的初始权益时长；首版不自动赠送试用。** 永久授权由 `ends_at IS NULL` 的产品级有效权益表示，不是永久会话 Token；适用产品功能、购买/升级/服务承诺等仍需明确。首批人工兑换码优先一次使用和固定时长，**不是自动发行永久码**。
- **所有渠道最终汇入同一套平台产品级会员权益**：兑换成功、有效的爱发电订单以及未来其它支付渠道的可信结果，可以分别成为开通或延长对应产品权益的来源，不能把会员逻辑绑定在某个支付平台里。
- **支付回调可靠性**：未来接入任何外部支付渠道时，必须基于可信的已核验交易状态授予对应产品权益，防止漏单、重复或伪造回调；具体适配细节见[计费专项](../architecture/domains/billing-and-entitlements.md)。
- **不把额度限制等同于按用量收费**：首版不自动引入复杂按量结算、充值点数或大型多支付插件系统。
- **不引入庞大的通用支付插件框架**；只保留少量必要的渠道边界，未来实际接入支付宝或 Stripe 时再扩展。爱发电的正式账户关联与交易匹配、后续支付宝/Stripe 的商户资质、收款币种/地区、永久权益细则、退款策略，以及交易/订阅权威数据物理位置均需按阶段决定。计费逻辑统一**不代表**未来所有外部订单表必须同库；但 **MVP 公共 Pro 授权、兑换码和核销记录同库**是已确定约束，见[数据专项](../architecture/database/entitlements-and-redemption-constraints.md)。

## 6. Admin 管理前端

- **已选框架**：[React-admin](https://github.com/marmelab/react-admin)（Marmelab 开源核心）。只为**本人或少数可信管理员**提供平台公共管理能力；不预先设计各 SaaS 分别运营的复杂后台和权限体系。
- **首要明确的管理操作**：管理员**创建 AisenCore 自有兑换码**，由平台所有者人工分发；具体批量生成、状态查看、撤销权限与操作记录根据实施需要明确，不提前设计复杂运营权限。
- **运营方式已确认**：项目只有一名实际运营者，日常 Admin 和人工发码均由其本人承担；首批以小批次、单次兑换、固定时长码为主，**100 个/批仅为待实测及批准的候选上限**。希望保留主管理员和备用恢复能力，但备用身份/负责主体未定。
- **MVP 已明确纳入管理员 TOTP MFA**：必须实现首次因素注册、必要的登录 challenge/verify、取得 `aal2` JWT、真实管理员资格检查，以及设备遗失/会话失效时的受控恢复和拒绝路径。**不要求每次管理页面切换或业务查询重新输入 TOTP 或额外访问 Auth MFA 服务器**：管理 Data API/RPC 在原请求中从经验证的 JWT 检查 `aal2` 和当前管理员名册、blocked；UI 短期资格缓存仅供导航，不构成授权。会话降级、过期或新登录时再执行必要 MFA 流程。单人运营的备用恢复真实人选仍待定；必须在隔离环境按 AUTH-P01～P12 真实验证，不能以此降低高权限服务端鉴权。
- **完全遵循 React-admin 默认技术栈**：React、TypeScript/TSX、`ra-core` / `ra-ui-materialui`、Material UI、Emotion/MUI Theme、React Router、TanStack Query、React Hook Form、React-admin i18n；优先采用官方推荐的 Vite 构建方式。避免再叠加平行完整 UI、路由、表单、缓存或状态管理框架。
- **已选网站部署**：Cloudflare Pages；源代码采用 GitHub / Git 管理。版本、主题裁剪、域名、Pages 仓库接入和构建发布设置以后实施时决定。
- Admin 是前端管理界面，**不是** Supabase、轻量计费服务或各产品业务后端的替代品；React-admin 的选择也**不强制**其它 SaaS 产品使用 React。
- Admin 列表读取采用 PostgreSQL RLS 保护的 PostgREST Data API，写操作经受保护管理 RPC；可评估 `ra-supabase` 的兼容性但不提前锁定包版本，详见[Admin 专项](../architecture/applications/admin-console.md)。
- Supabase Auth 用户管理、人工改动别人的会员权益、退款等**高权限操作必须经过可信服务端授权接口**；不能因为登录成功就允许管理所有用户，也不能在浏览器使用 Supabase `service_role` / secret key。
- **Admin 页面与交互要求**：基于[Admin 应用与安全合同](../architecture/applications/admin-console.md)和[通用 UI 质量规范](../architecture/applications/admin-ui-design-system.md)实现 MFA、Pro 资格和期限、一次性明文、UNKNOWN、成员操作及高风险确认。具体菜单、栅格、对话框和视觉形态按本次任务设计；不增加公共 Free/Pro 功能/额度编辑或旧 Pro 功能版本克隆。
- **Admin 视觉评审与正式开发授权**：正式前端基于 React-admin/MUI 单一全局 Theme，重要交互可以先原型验证，视觉方案由用户明确评审并留可追溯版本，发布前进行浏览器、无障碍和安全实测。正式 Admin 视觉与交互须按当前实际页面由所有者评审；独立的数据库/后端开发不以过时的原型数量或像素规范作为前置条件。离线模拟不替代正式代码、安全和上线验收。

### 用户反馈 V4：三队列、五分类、批量移动与永久删除 / 私有图片 / ZIP

2026-10-29 联系邮箱合同：新反馈必填独立contact_email，默认注册邮箱且允许提交前修改；可信JWT仍决定user_id，不修改认证邮箱。去首尾空白后最多254个ASCII字符，单一local@domain格式，拒绝空白/控制字符/多地址及无域名点，保留大小写。字段与正文/分类/原图纳入同号不变性，变更409。授权Admin详情可查看/复制，默认identity=false的ZIP/JSONL/Markdown不得包含。没有邮件发送API。直接替换唯一提交签名及所有调用者，不做数据转换、旧调用兜底或清库；已保存记录保持原事实，无联系方式时不推测或回填。

- 各 SaaS 已登录、邮箱已确认且未被全局 blocked 的本人可按产品提交文字及最多 2 张图片；不要求 Pro 或既有产品成员，不自动创建成员或变更权益。AisenLens 匿名离线 Free 必须保持可用，匿名反馈本期不实现。
- **当前 Admin V4 合同**：仅保留收件箱（优先级/星标/内部备注）→处理工作台→已归档，归档可重新处理；支持当前页 1–20 条合法批量移动与单项/批量永久删除。后者必须真实删除反馈、内部事件、附件元数据、R2 原图及缩略图，失败保留可重试任务且不得伪称成功。不提供回收站或管理员自定义标签；使用用户提交时五个固定类别筛选并显示类别。只有全平台视角显示所属产品，单产品视角依顶部选择器。维持 AAL2/版本锁/无内容审计，不恢复旧五态/指派/回复。见 [V4 实施计划](../Plans/aisencore-mvp/2026-10-29-feedback-admin-ux-bulk-delete-remediation-plan.md) 与 [反馈领域合同](../architecture/domains/user-feedback.md)。
- Admin 可按产品或有权限的全平台范围读取、使用受控 ZIP 选择记录或筛选结果；内部评论与直接身份默认关闭，敏感导出需再次确认，任何筛选/产品范围漂移必须阻断旧确认。PostgreSQL 保存正文、队列/标记、审计与附件元数据；R2 保存私有图片，必须独立授权与错误/孤儿恢复。AisenCore 不接管视频、项目或 AI 数据。

- 首版不建客服系统、AI 分诊、自动派单或邮件通知；图片数量 2 已定，正文/字节/TTL/留存/反刷候选参数须另获验证或决定。

## 8. 数据归属、对象存储与安全边界

- **公共结构化数据**：统一用户身份关联、产品、套餐、授权、兑换码与核销记录归公共 Supabase PostgreSQL；未来外部渠道订单/订阅的物理归属待接入时决定。
- **产品结构化业务数据**：项目、任务、文档、生成历史、聊天记录、运行状态等由相应 SaaS 产品负责；可以采用适当的逻辑隔离或真正的物理隔离，**不预先强制单一数据库或一产品一库**。
- **Cloudflare R2 保存文件字节**（上传资源、附件、图片/音频/视频、PDF、生成文件、配置备份等按产品需要采用）；用户、产品、业务关联、R2 对象 Key、大小、状态等**文件元数据存于对应的结构化数据库**。
- 私有文件必须经用户/产品权限校验后方可操作；R2 对象 Key 不能当作公开读取他人文件的授权。R2 Bucket 数量、路径、生命周期、配额和删除处理规则后续确定。
- Supabase Data API 暴露的数据应有合适的数据库授权与 RLS；敏感管理操作和支付事实必须由可信流程处理。**Supabase 服务端高权限密钥、R2 长期访问凭据和支付密钥不得下发浏览器或客户端。**
- 数据归属、标识和文件引用关系需要足够清晰，支持未来按产品管理、审计和迁移。

**单独的反馈图片小文件例外**：上述 AisenLens JSON 备份方案不涵盖反馈图片。跨 SaaS 反馈首版另外允许最多两张经可信校验的小图通过专用受保护 Edge 写入 R2，独立授权、元数据/失败补偿规则见[反馈领域](../architecture/domains/user-feedback.md)；不得扩大为视频或普通产品业务文件代理。

## 9. 本地优先拉片产品专项需求

该产品只是公共平台支持的一个实例，下列本地优先要求**不强制套用到所有 SaaS**：

1. **原始视频、拉片项目、切片/关键帧、AI 分析结果、用户的 AI API Key 及其它本地业务数据留在用户设备**，不由 AisenCore 公共服务器默认接收、存储或转发。
2. 使用第三方大模型时，**客户端使用用户自行配置的密钥直接请求其选择的 AI 提供方**；分析所需输入发送到**第三方模型服务**、模型输出直接返回客户端，不通过平台 AI 代理。不得误称任何分析输入都不曾发送给外部服务。
3. 备份只包含**当前上下文一套完整已生效分析模板**及必要包元信息；字段库、规则/示例、自定义模板集合和启用关系必须完整。项目库读取个人模板，工作台读取当前项目已保存模板快照；不探索其他项目，不读取界面/应用/AI 设置、结果参数、答案、媒体、凭据或 Token。
4. 配置备份**不要求客户端端到端加密**，运营方可按授权访问明文配置；但数据必须**私有、受访问控制并经加密传输**，不是公开文件。
5. **私有文件通常由客户端与 R2 直接传输字节**；**仅 Aisenlens 用户主动选择的、小体积、服务端白名单验证的非敏感配置/模板 JSON 备份（DEC-02 已批准 A）**例外：客户端经 JWT 授权将受限 JSON 发送给 Supabase Edge Function，Edge 校验 schema、字节数/摘要、属主和当前权益，经可信 R2 凭据条件创建不可覆盖的 final 对象，数据库原子预留/ready 与跨 R2 失败补偿分别处理。原始视频、项目数据、AI 结果、API Key/Token 等严禁通过此例外上传；其他大文件/普通私有文件仍按直接 R2 传输规则。此例外不意味着 Supabase 与 R2 可以提供跨系统 ACID。
6. **私人备份与任何未来分享能力完全分离**。分享链接、配置广场、模板广场尚未确认开发；若未来实现，只能由用户主动发布另一个可分享的副本，不能公开完整私人备份。
7. 本地 Pro 时序遵循 §4 和[本地优先架构](../architecture/applications/local-first.md)。恢复须手动选择版本、预览完整模板差异、确认后整体替换本机个人分析模板；不选择类别、不自动合并、不写任何项目快照。

### 首发 Aisenlens 已确认的产品功能与备份范围

- **Free**：提供真正可用的**本地基础工作流**，不要求先登录或联网，不因为 Pro/云端功能不可用而无故失效。
**AisenLens Pro 产品功能**：AI 分析（用户自备 API Key）、无水印导出、私有配置备份等功能由 **AisenLens 自己定义/配置/执行**，不属于 AisenCore 会员认证数据；Pro 资格和有效期由 Core 认证。是否付费、具体产品额度与上限仍按对应 SaaS 的后续产品实施确定。
- **私有备份**：每账号、每产品 **20 份**（AisenLens 多设备合计，各 Pro 期限一致）；单份 **5 MiB（5,242,880 字节）为已采纳、待完整载荷/接口实测的上限**。ready 与有效 pending 原子占用份数，满额拒绝新增，不自动覆盖/删除旧文件；新建需有效 Pro，到期仍可查看/下载/删除本人旧备份，但仍执行身份、属主及 Core 产品/成员准入。服务正常期间不按年龄或会员到期自动删除；注销/停服的保留及通知政策上线前确定。模型与一致性见[文件架构](../architecture/database/product-data-and-files.md)。
- **账号注销**：人工受理、身份核验及受控清理；专门支持邮箱为渠道方向，**具体渠道留待上线前确定**。未确定前不提供可成功提交的申请按钮、不假报已受理；不建自动删号 RPC，不删除本机项目/配置。合法留存例外、期限及通知责任另行确定。

### 当前本地对接范围

- Core 是主优化对象，后端相关页面/数据/API 统一以 Core 当前合同为准；不兼容 Lens 测试实现。首轮只做 WebApp 的 Auth、成员、资格显示/安全历史、兑换、反馈及分析模板云备份；不接支付、桌面/移动壳或 SSO。
- **本次不启用或改造 AI Pro 限制、去水印、第二项目登录门槛**；这些仍是产品目标，后续须另列最小业务改动范围。后端/账号界面通过不能冒称所有 Pro 功能已落地。
- **允许的最小生命周期接线**：登出/切号锁定保险库、释放未持久保存的会话 Key，保留加密凭据；在途账号任务先完成或由用户明确取消，旧请求结果不得写入新账号。不得改 AI 算法、Provider 管理或项目存储。
- **统一昵称**：保留可选昵称，存于 Supabase Auth 用户可编辑资料，仅作跨产品显示，不新增资料表/头像/个人主页，不参与身份或权限判断。
- 同产品已有当前有效永久 Pro 时拒绝继续兑换周期码或不同永久码，**不耗码、不新增 Grant**；同码成功重试仍按已兑换处理，不恢复已撤销权益；普通周期续期继续顺延，管理员直授独立受控。此规则已确认，服务端实现与并发负例仍待完成，见[计费规则](../architecture/domains/billing-and-entitlements.md)。
- 第一阶段可独立完成的 Core/Admin 缺陷先修验并取得正式签收；同时可做静态合同及隔离环境准备，之后才正式双端联调。**当前仅授权同步文档，不改代码/数据库，不将决定确认当作阶段签收或云端许可。**

**Admin 视觉与实施边界**：正式 React-admin 使用统一 MUI Theme，具体视觉与关键交互由所有者评审；当前 [V6 离线 Demo](../interaction-benchmarks/README.md)仅是合成参考，不等于生产视觉签收。Admin、TOTP MFA、受保护 RPC 和多项本地真实 AAL2 Chrome 验证已实施；仍欠第一阶段全场景、人工 WCAG/视觉、代表性性能与所有者正式签收。AisenLens 本地双端联调尚未运行。质量规范见 [Admin UI 规范](../architecture/applications/admin-ui-design-system.md)。

## 10. 数据迁移与长期演进

- 现阶段优先使用 Supabase 托管能力；**未来随着规模、成本、维护需求变化，再评估自托管或其它部署形态**，现在不预定迁移时点或唯一迁移目标。
- 未来迁移需要考虑 PostgreSQL 结构化数据、身份与 Auth 关系、服务端函数、订单和权益一致性、R2 文件与元数据引用等；按具体范围决定。
- 要求迁移过程可靠：可备份、校验完整性和一致性、恢复/回滚，并考虑中断窗口。具体可接受的数据丢失、停机时长、工具和演练计划以后再确定。
- 不因当前采用托管 Supabase 而把所有产品业务绑定在同一物理部署，也不预先为假设需求做复杂框架。

## 11. 仍待具体业务或实施阶段决定

1. **兑换码与爱发电接入**：首批本人 Admin 人工发放的小批次单次固定时长码已定；`100/批` 仍是候选上限，码自身失效期、运营约束和爱发电订单关联/回调核验仍待定。
2. **后续支付**：自动试用首版不启用；今后是否增加手动试用、支付宝个体商户/Stripe、退款、永久购买具体服务/升级承诺与公共计费事实数据库落点仍待定。
3. **权益计量**：其他产品具体能力/计量规则待定；AisenLens 的 20 份、满额拒绝新增、到期取回/删除及不按年龄自动删除已确认，5 MiB 仍需实测验证，不能再把这些业务决定列为未决。
4. **登录体验及成员接口**：公众可注册及统一品牌/自定义 SMTP 已定；生产域名、供应商、回调、反滥用措施、真实注销申请通道及具体数据保留/删除期限待定。
5. **本地 Pro**：短时断网新纯本地 Pro 可在有效快照内启动已确认；最多 15 分钟为已采纳待实测参数。剩余为时效/撤权窗口与请求量实测，相关 AI/导出业务入口实施不属于本轮范围。
6. **Admin 接入**：一名实际运营者已确认，**Admin TOTP MFA 为 MVP 必做，管理读取和写入必须要求当前 `aal2` 与管理员资格**；有效会话不因导航或日常操作重复挑战 TOTP。备用恢复责任主体、独立备用因素及生产丢设备演练尚待落实；Provider/Pages 部署细节亦待确认。普通用户不强制 TOTP。
7. **数据与文件拓扑**：Aisenlens 小型非敏感 JSON 经受保护 Supabase Edge 校验并写 R2 的路径**已批准**；单个或多个 Supabase Project、产品库隔离、R2 Bucket/对象组织、允许配置字段与上限、对象删除/恢复策略仍待实施验证或具体产品确认。
8. **分析模板备份**：唯一完整模板、个人整体恢复、数量/到期/正常服务留存规则已确认；仍需冻结当前格式的全层字段/类型/长度校验及运行证据，5 MiB 接口实测、元数据/R2 对账尚未完成。分享链接/模板广场未批准。
9. **可靠迁移**：自托管目标、迁移范围、数据一致性验证、备份恢复与验收指标。

以上按条目区分已确认规则、待实施/实测和真正未决事项；已确认业务不再重复审批，未决项在对应阶段收口。任何文档确认都不能自动当作代码已实现、运行已通过或云端变更许可。
