## 1. 项目定位与原则

1. **多 SaaS 公共底座**：AisenCore 为多个彼此独立的 SaaS 产品提供值得复用的轻量公共能力，而不是某个本地拉片产品专用后端，也不把所有产品业务合并成一个巨型应用。
2. **一套公共账号、权益按产品独立**：用户可用一个平台账号访问多个产品；每个产品的套餐、定价、会员和功能权限相互独立。购买产品 A 的 Pro 不会自动获得产品 B 的 Pro。
3. **统一必要能力，独立产品业务**：公共平台集中管理身份、产品、必要权益与轻量计费；各产品自己的项目、任务、业务内容、业务规则和数据尽量独立组织。业务职责独立**不等于**必须为每个产品立即建立独立数据库或 Supabase Project。
4. **适用三种产品模式**：
   - **本地优先**：主要业务数据和处理位于用户设备，按需要调用公共账号/权益/计费能力。
   - **云端业务**：产品可以主动接收、处理用户上传的数据和文件，使用其自身的业务服务与数据库。
   - **混合型**：本地和云端分别负责相应业务，公共身份/权益/计费仍可复用。
5. **成熟方案优先**：优先评估并复用合适、活跃、许可证适用的成熟开源方案，重点比较功能适配、二次开发、部署维护和整体复杂度。只有自研能显著降低整体复杂度时才优先自研，不重复造框架。
6. **明确排除**：不采用 Payload；AisenCore 是独立新项目，不默认引用或复用已舍弃的 Aisenhubplatform 的代码、设计、数据、配置或模块，除非用户明确指定并批准具体部分。

## 2. 首版公共平台范围

第一版采用**最小公共核心**，包括：

| 范围 | 首版必须具备的能力 |
| --- | --- |
| 统一用户身份 | 账号、登录与身份关联，服务多个 SaaS |
| 产品及成员管理 | 公共平台注册/识别 SaaS 产品，统一管理产品成员加入、退出、封禁及恢复，产品级权益独立 |
| 套餐与会员权益 | 每个产品分别配置套餐、有效期、功能开关和所需配额，并判断用户当前是否有权使用 |
| 兑换码及分阶段支付 | **先做平台自有兑换码开通权益**；初期暂定使用爱发电进行打赏/支付与回调，保留以后增加支付宝、Stripe 的能力，不要求首版同时完成所有支付通道 |
| 内部 Admin | 用一个必要的管理入口管理上述公共数据和流程 |

首版**不追求**大型综合运营后台、复杂财务分析报表、多组织运营平台、复杂企业多租户计费或完整的高级统计体系；但不能因此省掉支付一致性、安全管理必需的少量事件记录与基本审计能力。具体操作清单和最小审计范围在实际接入时细化。

## 3. 统一账号、登录与授权

- **已选身份服务**：Supabase Auth；首版仅要求**邮箱 + 密码**登录，全平台统一身份。
- **正式开放注册前**必须能合理完成邮箱确认（按项目实际策略）和密码找回流程，落实稳定的邮件发送能力；具体邮件提供商及相关验证服务尚未选定。
- **未来可选**：手机号验证码、邮箱验证码、免密链接、Google 等第三方登录，以及需要另行验证适配方案的微信登录。不要求首版接入这些方式，也不把微信认定为 Supabase 的内置现成提供商。
- 全平台统一账号不自动等于跨不同站点的无感 SSO。跨域登录体验、身份绑定、多设备会话规则后续确定。
- 账号已认证不等于获得任何产品 Pro 权益，也不等于具备 Admin 管理权限。授权必须按用户、产品和具体操作核验。
- **产品成员 API 最小原则**：首次合法使用需登录的产品服务时按需幂等创建成员；可信 SaaS 后端用现有用户 JWT 代用户调用公共接口，纯本地客户端可直接以本人 JWT 调用。状态查询无副作用，云端受保护的关键操作由可信服务端复核，客户端状态缓存不作为最终授权证明；不预建独立授权 Token、通用 API 网关或复杂缓存。详见[公共 API MVP 与 SaaS 接入](../architecture/backend/public-api-and-saas-integration.md)。
- **统一用户 MVP 安全与会话**：必要公共数据使用 PostgreSQL 最小 GRANT/RLS，成员状态变更与最小审计必须同事务提交；平台管理员使用可信资格记录，产品级封禁与全局账号限制分离，若提供跨产品封禁需在公共准入中检查当前限制；统一 Supabase Auth 邮箱密码身份但不强制跨 SaaS 共享登录态，正式注册前确保邮箱验证与密码找回；按标准 HTTP/业务错误码及 MVP 验收用例验证。详见[统一用户专项目录](../architecture/README.md)。

### 统一产品成员规则

- **公共平台统一管理产品成员**：首次实际使用某 SaaS 需要账号的服务时，在可信服务端验证后按 `user_id + product_id` 幂等创建 `active` 成员；公共账号注册不自动加入所有产品，匿名免费本地功能不触发加入。
- **成员状态**只包含 `active`（正常）、`left`（主动退出）、`suspended`（暂停/封禁）；从未加入由“无记录”表示。成员关系与平台账号、产品运行状态、会员权益及产品业务权限分别管理。
- 用户主动退出后不能因为登录自动恢复，只能主动确认重新加入；封禁后仅可信管理员能够解除，重复登录、兑换与支付不得绕过限制。产品停用不批量改变成员或会员记录。
- **退出与删除分离**：退出不自动删除业务数据或本地文件、不撤销历史权益、不取消自动续费、不退款；原授权有效期和试用期自然流逝，重新加入后根据原授权、现存数据和当前权限判断。
- 公共平台负责产品成员资格，各 SaaS 负责自身项目、任务、协作权限与业务数据。当前成员状态由公共成员关系记录保存，成功的关键状态变更以独立事件记录做最小审计，**不通过事件重放计算当前成员状态**。关键变更与审计应由可信服务端在同一数据库事务内完成；数据库逻辑约束见[最小审计与约束专项](../architecture/database/database-constraints-and-audit.md)。详见[统一身份与产品成员专项](../architecture/README.md)。

## 4. 产品权益与 Pro 在线校验

首版公共权益系统**支持四类权益**，每个 SaaS 只启用业务真正需要的类型：

| 已确定权益类别 | 业务要求 | 待具体产品确定 |
| --- | --- | --- |
| 功能开关 | Free / Pro 功能可用性，按产品和用户独立 | 功能清单、其它会员档位 |
| 数量/使用额度 | 能限制功能次数、对象数量或其它产品使用额度 | 计数来源、周期、重置方式、本地使用量可信度 |
| 云端文件/备份配额 | 能限制产品相关存储或备份容量/数量 | 按大小还是数量、超额处理、删除后回收 |
| 有效期与订阅到期 | 权益在有效时间内生效，能反映订阅到期/撤销 | 宽限期、退款/取消影响、刷新时效 |

**桌面离线会员授权不是首版必须实现的能力**，只保留未来由确有需要的产品单独提出后扩展的可能；首版不建通用离线许可证系统。

**本地 Pro 在线校验原则**：

1. 需要 Pro 的本地客户端在**启动时完成有效的联网权益校验**，运行中根据各产品实际关键操作、进入高级功能或其他合适时机**合理复核**。
2. 公共权益系统是权威依据；不要求所有产品使用固定轮询周期，也不要求每次点击都访问后端。每个产品自主确定具体复核点。
3. 临时断网、校验失败、已启动任务和权益撤销后的使用体验，在具体产品接入时确定；不能由“运行中复核”推导出长期离线 Pro 使用权。
4. 不应无故禁止用户在断网时使用与 Pro 无关、原本可离线运行的本地免费功能。
5. 在线校验可以提高正常客户端授权的可控性，但**不能承诺防止用户复制网页、本地运行或修改客户端绕过限制**；云端的受保护业务操作必须在可信服务端真正校验权限，不能只靠前端隐藏按钮。

## 5. 兑换码优先、分阶段支付与轻量统一计费

- 多产品**共享必要的订单、支付、订阅生命周期与权益同步逻辑**；各产品分别定义套餐、价格和会员范围，绝不自动跨产品共享 Pro。
- **当前明确的实现优先顺序**：

  | 顺序 | 方式 | 当前决定 |
  | --- | --- | --- |
  | **1** | **AisenCore 自有兑换码** | **最基础、优先建设**。管理员在 React-admin 创建兑换码，由**平台所有者人工分发**，领取兑换码的用户兑换后取得**对应 SaaS 产品的会员权益**；不依赖任何支付提供商 |
  | **2** | **爱发电（Afdian）** | **初期暂定的外部打赏/支付渠道**。用户已在以前的项目里简单验证打赏、回调的基本流程可通；是否符合当前平台使用规则、具体订单与账户关联、生产可靠性仍需新项目接入前确认 |
  | **3** | **支付宝个体工商户支付** | 等个体工商户注册、商户准入条件具备后再评估和开发；本阶段**不接入** |
  | **4** | **Stripe** | 更后期根据商户资格与海外收款需要再对接；本阶段**不接入** |

- **兑换码是平台独立能力**，不依赖爱发电或未来其它支付渠道的兑换码功能。由可信服务端核验兑换条件并更新指定用户、指定产品的权益，不能单凭前端状态开通。兑换码的批量创建、码类型、使用次数、有效期、权益期限、绑定方式与作废规则**尚未确定**，不能默认全部设计成单次码或永久码。
- 目标业务/授权模式保持 **月付订阅、年付订阅、一次性永久购买、免费试用** 四类；这描述平台**应支持的权益/商业模式**，并**不要求第一阶段的兑换码或爱发电立即具备所有支付渠道的自动扣费、自动退款等完整能力**。具体模式能否由爱发电直接承载应按其实际功能核实。
- 一次性永久购买应形成有明确权益范围的**非周期续费授权**，不伪装成“永不到期的周期订阅”。免费试用是否绑卡、是否自动转付费、试用时长和额度仍待定。
- **所有渠道最终汇入同一套平台产品级会员权益**：兑换成功、有效的爱发电订单以及未来其它支付渠道的可信结果，可以分别成为开通或延长对应产品权益的来源，不能把会员逻辑绑定在某个支付平台里。
- **支付回调可靠性**：爱发电 Webhook 与 API 订单查询均已有官方接口说明，且官方提示 Webhook 可能漏推、重复；以后真正接入时必须经可信服务端核对订单真实性、产品/套餐和目标账号，处理幂等、漏通知和异常，不允许仅因浏览器显示打赏成功就授予 Pro。
- **不把额度限制等同于按用量收费**：首版不自动引入复杂按量结算、充值点数或大型多支付插件系统。
- **不引入庞大的通用支付插件框架**；只保留少量必要的渠道边界，未来实际接入支付宝或 Stripe 时再扩展。爱发电的正式账户关联与交易匹配、后续支付宝/Stripe 的商户资质、收款币种/地区、永久权益细则、退款策略，以及交易/订阅权威数据物理位置均需按阶段决定。计费逻辑统一**不代表**全部计费表必须与身份数据同库。

## 6. Admin 管理前端

- **已选框架**：[React-admin](https://github.com/marmelab/react-admin)（Marmelab 开源核心）。只为**本人或少数可信管理员**提供平台公共管理能力；不预先设计各 SaaS 分别运营的复杂后台和权限体系。
- **首要明确的管理操作**：管理员**创建 AisenCore 自有兑换码**，由平台所有者人工分发；具体批量生成、状态查看、撤销权限与操作记录根据实施需要明确，不提前设计复杂运营权限。
- **完全遵循 React-admin 默认技术栈**：React、TypeScript/TSX、`ra-core` / `ra-ui-materialui`、Material UI、Emotion/MUI Theme、React Router、TanStack Query、React Hook Form、React-admin i18n；优先采用官方推荐的 Vite 构建方式。避免再叠加平行完整 UI、路由、表单、缓存或状态管理框架。
- **已选网站部署**：Cloudflare Pages；源代码采用 GitHub / Git 管理。版本、主题裁剪、域名、Pages 仓库接入和构建发布设置以后实施时决定。
- Admin 是前端管理界面，**不是** Supabase、轻量计费服务或各产品业务后端的替代品；React-admin 的选择也**不强制**其它 SaaS 产品使用 React。
- 一般数据的访问可评估 React-admin Data Provider 与有正确权限控制的 Supabase 接口；`ra-supabase` 只是待评估选项，**尚未选定为必须使用的依赖**。
- Supabase Auth 用户管理、人工改动别人的会员权益、退款等**高权限操作必须经过可信服务端授权接口**；不能因为登录成功就允许管理所有用户，也不能在浏览器使用 Supabase `service_role` / secret key。
- 具体页面列表、所有者与少数管理员是否细分角色、操作审计和每个管理按钮的权限细节**推迟到选定框架后的实际对接阶段**，不在目前过度设计。

## 7. 公共后端、数据库与云端部署技术

| 层级 | 已确认选择 | 职责与边界 |
| --- | --- | --- |
| 公共后端 | Supabase | 统一身份和产品权益等必要公共服务；未来保留可靠迁移能力 |
| 公共关系数据库 | **Supabase 托管 PostgreSQL** | 公共用户关联、产品、权益与必要的结构化公共记录 |
| 用户认证 | Supabase Auth | 首版邮箱密码，未来按需添加其他方式 |
| 可信公共服务端逻辑 | **Supabase Edge Functions**（TypeScript / Deno 兼容） | 优先承载敏感 Admin 接口、支付回调/权益同步、需要保管秘密的授权处理；具体接口后续确定 |
| Admin 托管 | Cloudflare Pages | 部署 React-admin + Vite 构建出的管理前端 |
| 对象文件 | Cloudflare R2 | 保存各产品按需要上传的文件本体及可选配置备份 |
| 代码管理 | GitHub + Git | 代码与版本，未来可连接 Pages 自动部署 |

这些属于**已确认的技术选型，不表示服务已开通或运行**。公共数据库选为 PostgreSQL，不意味着每个独立 SaaS 的业务数据库也必须用同一数据库/同一个 Supabase Project。**具体技术栈与关系图**见[技术栈专项架构](../architecture/infrastructure/tech-stack.md)。

## 8. 数据归属、对象存储与安全边界

- **公共结构化数据**：统一用户身份关联、产品注册、权益信息和必要公共记录由公共平台维护；计费权威事实的准确物理归属仍可根据业务与安全需求决定。
- **产品结构化业务数据**：项目、任务、文档、生成历史、聊天记录、运行状态等由相应 SaaS 产品负责；可以采用适当的逻辑隔离或真正的物理隔离，**不预先强制单一数据库或一产品一库**。
- **Cloudflare R2 保存文件字节**（上传资源、附件、图片/音频/视频、PDF、生成文件、配置备份等按产品需要采用）；用户、产品、业务关联、R2 对象 Key、大小、状态等**文件元数据存于对应的结构化数据库**。
- 私有文件必须经用户/产品权限校验后方可操作；R2 对象 Key 不能当作公开读取他人文件的授权。R2 Bucket 数量、路径、生命周期、配额和删除处理规则后续确定。
- Supabase Data API 暴露的数据应有合适的数据库授权与 RLS；敏感管理操作和支付事实必须由可信流程处理。**Supabase 服务端高权限密钥、R2 长期访问凭据和支付密钥不得下发浏览器或客户端。**
- 数据归属、标识和文件引用关系需要足够清晰，支持未来按产品管理、审计和迁移。

## 9. 本地优先拉片产品专项需求

该产品只是公共平台支持的一个实例，下列本地优先要求**不强制套用到所有 SaaS**：

1. **原始视频、拉片项目、切片/关键帧、AI 分析结果、用户的 AI API Key 及其它本地业务数据留在用户设备**，不由 AisenCore 公共服务器默认接收、存储或转发。
2. 使用第三方大模型时，**客户端使用用户自行配置的密钥直接请求其选择的 AI 提供方**；分析所需输入发送到**第三方模型服务**、模型输出直接返回客户端，不通过平台 AI 代理。不得误称任何分析输入都不曾发送给外部服务。
3. 本地设置及拉片模板的**部分文本内容**可按用户明确操作备份到 R2，并供用户在其他设备恢复。**视频、项目数据、AI 结果、API Key、Token 等秘密不进入备份**；实际可备份字段以后按客户端明确划定。
4. 配置备份**不要求客户端端到端加密**，运营方可按授权访问明文配置；但数据必须**私有、受访问控制并经加密传输**，不是公开文件。
5. 备份和恢复时，客户端在取得必要的受限授权后**直接与 R2 传输文件字节，不由 Supabase 或公共后端中转**。服务端可负责必要授权和最小备份索引/对象元数据。
6. **私人备份与任何未来分享能力完全分离**。分享链接、配置广场、模板广场尚未确认开发；若未来实现，只能由用户主动发布另一个可分享的副本，不能公开完整私人备份。
7. 本地拉片的 Pro 使用已确定采用**启动在线校验 + 运行期间按关键操作等适当时机复核**；断网或授权撤销后的交互、备份恢复时覆盖/合并、版本与配额、文件本地目录布局等后续确定。

## 10. 数据迁移与长期演进

- 现阶段优先使用 Supabase 托管能力；**未来随着规模、成本、维护需求变化，再评估自托管或其它部署形态**，现在不预定迁移时点或唯一迁移目标。
- 未来迁移需要考虑 PostgreSQL 结构化数据、身份与 Auth 关系、服务端函数、订单和权益一致性、R2 文件与元数据引用等；按具体范围决定。
- 要求迁移过程可靠：可备份、校验完整性和一致性、恢复/回滚，并考虑中断窗口。具体可接受的数据丢失、停机时长、工具和演练计划以后再确定。
- 不因当前采用托管 Supabase 而把所有产品业务绑定在同一物理部署，也不预先为假设需求做复杂框架。

## 11. 仍待具体业务或实施阶段决定

1. **兑换码与爱发电接入**：码的授权内容/期限/使用次数/有效期、批量创建与失效方式、用户兑换入口；爱发电订单与 Supabase 用户及具体产品的可信关联、平台规则、回调防伪、漏推补查和可适用的订阅模式。
2. **后续支付与试用**：支付宝个体工商户注册/商户资质、Stripe 资格与对接时机，商户/地区/币种、退款、升级降级、免费试用规则、永久授权范围；公共计费事实数据库落点。
3. **权益计量**：功能列表、数量与配额统计周期、超限处理、存储容量/对象数计量、到期宽限期。
4. **登录体验及成员接口**：确定生产邮件发送服务、回调域名与各产品页面；未来手机/邮件 OTP、第三方登录或无感跨域 SSO 按实际需求再评估；已确定的成员 API 逻辑仍需最终 HTTP/SQL 实现、状态生效时效、注销流程与具体数据保留/删除期限。
5. **本地 Pro**：各产品运行期复核时机、临时断网后的 Pro 处理、任务中断与退款撤权同步。
6. **Admin 接入**：兑换码管理的实际操作和其它管理页面、最小权限、审计、`ra-supabase` 或自定义 Provider、Pages 仓库/域名/部署配置。
7. **数据与文件拓扑**：单个或多个 Supabase Project、各产品业务数据逻辑/物理隔离、R2 Bucket/对象组织、文件访问与删除/恢复规则。
8. **拉片配置**：备份字段、版本、恢复时覆盖或合并、R2 备份元数据与配额；分享链接/模板广场是否开展。
9. **可靠迁移**：自托管目标、迁移范围、数据一致性验证、备份恢复与验收指标。

以上内容都是**待决定问题**，不能自动当作已批准的技术实现。

## 12. 协作与文档维护规则

- 目前阶段仅做需求、架构及已授权的开源技术选型；**选择技术或编写文档不表示授权开始代码开发、下载安装、创建 Supabase/R2/Pages 资源、连接 GitHub 或部署**。
- **`docs/spec/requirements.md` 是唯一现行需求文档**。需求变化时直接更新当前有效条目，**不保留历史轮次记录、变更日志、被新结论覆盖的旧要求**。
- **`docs/architecture/` 存放已确定的总体架构和按需拆分的专项架构**：主架构只概述总体关系、边界和专项入口；复杂专项必要时可在架构目录下再建子文件夹。架构文档不保留历史方案或修改历史。
- **`docs/development/` 存放开发指南、规范及外部参考**：按前端、测试、付费订阅等主题划分文件夹；某主题分别维护参考文档（链接与成熟项目）、开发对接规范，以及按需的 `templates/` 模板/资产目录。它不代替 `spec/` 的需求或 `architecture/` 的架构设计。未确定的接口、SDK、测试工具不得在指南里写成已批准实现。
- 对于实际尚未确认的产品要求或冲突，应先澄清，不能把推测写成正式决定。架构与需求索引维护在 [文档总索引](../README.md)。
- 与具体产品或第三方集成时优先复用成熟开源方案；尚未选择的插件/服务不自动成为项目依赖。
