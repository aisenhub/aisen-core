## 1. 用户已明确的设计目标

1. **指定产品视角**新增 Pro：自动使用顶部已选的唯一产品，不让管理员重复选一次；**全平台视角**才要求选择目标产品。
2. 授予模式只在普通界面提供 **固定天数 / 永久**。删除常规“指定开始/结束时间”编辑，不要求人工填写生效日期。
3. 固定天数默认 30 天，快捷选项 **7 / 30 / 90 / 365 天**，保留在服务端允许范围内的自定义正整数天数。
4. **权益成功入账即立即生效于用户的会员汇总**：已有 Pro 的剩余期限不能被覆盖，新增天数应立即增加到综合到期日；原为 Free 且具备使用资格则立即升级 Pro。
5. **人工授权与兑换码兑换采用同一续期规则**；发放兑换码本身不增加任何用户权益，**成功兑换时**才入账。
6. 每笔权益来源、原始授权数量、操作人、发放/兑换时刻、撤销及审计历史**独立保存**；不能简单把旧记录改成新记录、抹除来源或合并删除。
7. Lens “我的权益”、Core 授权列表和 Core 用户综合中心须统一展示：当前实际 Pro 状态 + **已承诺的综合到期日** + 独立授权历史。

**本计划不把“每笔新授权的覆盖片段 starts_at 都必须等于当前时刻”误解为“权益立刻可用”。** 已有 Pro 时，为防同一天被重复计算，新增信用天数可以排在现有片段之后；但用户的**综合到期日必须立即增加**，记录显示为“已入账／续期已计入”，而非让用户误认为尚未获得权益。

## 3. 业务词汇与权威合同

| 名称 | 精确定义 | 是否为单笔事实 |
| --- | --- | --- |
| 授权入账时间 `credited_at` | 管理员成功提交/用户成功核销的服务端事务时刻 | 是 |
| 授权面值 `duration_days` | 授予的有限日数（推荐 1 日 = 24 小时） | 是 |
| 授权来源 | `admin` / `redeem_code`，带不可重复的源引用 | 是 |
| 片段覆盖时间 `starts_at/ends_at` | 目前数据表中为消费该时长安排的覆盖时段；新规则下是可变化的**分配投影**而非入账时间 | 否，不能拿它代替原始事实 |
| 当前能否使用 Pro `pro_active` | 同一用户/产品、此刻已确认的成员与账号条件和有效信用/永久资格 | 否，权威派生状态 |
| 综合到期时间 `effective_ends_at` | 当前时刻起**连续可用**的有限权益终点（计入所有已入账、未撤销的续期信用） | 否，权威派生状态 |
| 永久 `is_lifetime` | 存在仍有效、未撤销的永久授权，此产品永久覆盖（但成员/账号限制仍可能禁止使用） | 授权事实有对应来源，状态是汇总 |
| 历史记录状态 | 已入账、已撤销、已消耗；与“当前是否轮到该片段覆盖”不同 | 按事实 + 派生视图区分 |

### 3.1 建议的统一读取合同

现有 `check_access(product_key)` 保持原有 `allowed/reason/tier/pro_active/is_lifetime/effective_ends_at/evaluated_at` 等字段兼容语义，**更正 `effective_ends_at` 为连贯的综合到期日**。建议受保护地追加或提供清晰独立字段：

- `entitlement_credited_at`（最近一次成功入账时刻，可选）；
- `queued_duration_days` 或 `remaining_credit_seconds`（只在必要时显示；不要无契约地舍入）；
- `entitlement_projection_version`（用于缓存、审计和新旧迁移比对，可选）；
- `state_reason`（区分账号/产品/成员不可用和权益不足）。

用户侧 `check_access` 继续以本人 JWT 判定；管理员查看目标用户的综合权益应走**独立受限 Admin 读取服务/RPC**，不能把用户自查函数改成可任意传用户 ID 的公开接口。Lens、Admin 必须消费**同一服务端权益计算逻辑**，不各自求和。

## 4. 推荐的目标规则（统一人工授予与兑换）

### 4.1 有限天数入账

已具备可用产品成员资格、无平台账号限制时：

1. 没有任何有效剩余 Pro：成功授权时立即开始 Pro，综合到期为 `server_now + N 天`。
2. 已有有限 Pro：成功授权时立即记入 **N 天信用**，综合到期立即从原连续到期日增加 N 天，且不浪费已有时间。
3. 此次授权始终创建一笔**独立、不可重复**的记录，来源是人工或某次兑换；读取历史时清晰展示其入账时刻及对应时长。
4. 发行/生成兑换码不产生用户授权；仅`redeem_code` 校验成功并提交时入账。
5. 暂停/退出/被封禁不因人工授权而自动解除；**先处理资格再决定是否允许授予**，见第 7 节。

例如：10 月 28 日 Pro 原定 11 月 27 日到期，再授予 30 天后，用户当前仍立即可用，综合到期立即显示 **12 月 27 日**；新增记录状态显示“已入账 · 排队覆盖/已计入续期”，不是含混的“未获得权益”。

### 4.2 永久授权

- 永久 Pro 成功入账后，同产品 `is_lifetime=true`，综合到期为 `null`；UI 显示“永久有效”。
- **建议**当仍有效永久权益存在时，阻止继续人工授予有限/永久 Pro；兑换码已有有效永久保护，需统一人工作业的预检与服务端保护。
- 任何“永久”只指权益本身**无时限**，不是免于平台封禁、成员暂停或管理员撤销。
- 若后续撤销永久 Grant，原有限权益余额是否恢复、是否曾消费、如何审计，必须按第 6 节的明确政策处理；不得恢复一个无依据的“无限期”状态。

### 4.3 历史来源和有效期

- 保留每条 Grant 的原始来源、原始获授日数、业务引用、入账时间、操作理由、撤销信息。
- 管理后台单笔可以显示“已入账/已撤销/已消耗”与“当前覆盖/后续覆盖/已结束”两种不同维度；不把未来片段 `starts_at` 直接翻译成“权益尚未到账”。
- Lens 当前“我的权益”首屏以汇总综合时间为准；独立历史保留原始天数/来源，不能拿某条 Grant 的 `ends_at` 假装用户综合到期。

## 5. 数据设计：**独立事实流水 + 可核验权威汇总**（推荐）

### 5.1 为什么不建议简单把所有新 Grant 的 `starts_at` 改成 `now`

如果用户已有 30 天 Pro，再来一笔 30 天，两笔都以今天开始、30 天后结束，基于“存在任何未过期片段”的读取规则，到期并不会延长。若只把后一条的 `ends_at` 直接推后而没有状态重算，撤销旧记录也会留下隐含的重叠/空档和审核问题。

**推荐保留独立 Grant 作为业务事实，新增或明确定义权威的时长信用及消费投影；不让 UI 或散落的 SQL 各自计算余额。**

### 5.2 推荐状态结构（实施前须经建模评审；名字暂定）

1. **事实层**：继续以 `entitlement_grants` 为核心，逐笔保存 `id, user_id, product_id, source_type, source_ref, requested_duration_days, created_at, revoked_at, revoke_reason`；永久 Grant 用明确 `is_lifetime` 语义。旧的 `starts_at/ends_at` 作为**历史分配事实或兼容投影**保留，新逻辑不得依赖它充当入账时间。
2. **信用/消费层（建议增加）**：按 `(user_id, product_id)` 跟踪每笔可用有限授权的信用额、已消耗额、可撤销的剩余额、最近结算时刻，并为账本变动记录**不可改写的事件和原 Grant 引用**。可以采用独立明细表 + 汇总快照，或事务内纯计算账本；不要把当前到期时间当成唯一数据真相。
3. **读投影层**：一个有版本和 `evaluated_at` 的服务端计算器，在授予/兑换/撤销/成员状态变更后给出当前可用状态、永久标志和从现在起连续到期日；`check_access` 和 Admin 受限查询共享相同定义。
4. **审计层**：每次写入、撤销、回放/冲突都保留现有业务 `request_id` 与审计，不复制用户私密数据到无关日志。

选型分支：**方案 A（较小改动）**：保持现有 Grant 时间段，修正读取为“从当前活跃片段开始可连续衔接的未来片段”并在撤销时重排尚未消费的片段；优点是迁移较少，缺点是历史时间段变更、复杂撤销和旧 `explicit_window` 并存难证明。**方案 B（推荐长期合同）**：不可变时长信用流水 + 统一消费/投影；改动更大，但“立即入账、连续续期、撤销不留洞”含义清晰。必须先用黄金场景和迁移演练决定是否分两期交付；不能把 A 当成完整的 B。

### 5.3 推荐的时间计算不变量

- **一次时间只消耗一次有限信用**：两个各 30 天权益在同一产品下组成 60 天可用时间，不能因为重叠/时间戳错误变 30 天或 90 天。
- **入账事务单一时点**：以数据库事务时刻为准，不使用管理员浏览器时间计算发放/到期；时区转换只用于展示，天数算术需一致（推荐 1 天 = 24 小时，需单独测试 DST）。
- **来源事实不变**：授权面值、真实来源和已消耗的历史不得在撤销旧 Grant 后被回填伪造或删除。
- **撤销只取消未消耗信用**：已实际使用的时长不能被倒扣到过去；剩余额从当前起重排，不形成由旧分配段留下的假空档。
- **一次入账只发生一次**：同一可信来源和请求号多次递交不得增加两次余额；参数变更必须拒绝 `409`。
- **跨产品绝不共享余额**：`aisenlens` 和其他产品的 Grant 不能互相顺延。
- **永久优先**：永久生效时 Pro 到期日为空；不得将“无限期”当成有限信用的锚点，不能让有限余额数值溢出。
- **成员资格与权益额度独立**：平台/成员状态不可用时 `allowed=false`；不能把持有信用误写成正在被允许使用。

### 5.4 建议的逐事件处理顺序（伪规则，不是可直接上线 SQL）

```text
为每个 (user_id, product_id) 提供同一受保护事务锁。
每次授权/兑换/撤销：
  1. 验证真实用户、目标产品、管理员或兑换资格、单次来源/请求 ID。
  2. 以数据库当前时刻结算截至 now 已消耗的连续 Pro 时长。
  3. 按来源引用持久写入新的有限信用 / 永久信用 / 撤销事件。
  4. 对尚未消耗的有限信用依确定顺序（建议 credited_at, grant_id）
     计算从 now 起的剩余额及未来连续覆盖终点。
  5. 写入/核对版本化结果和审计。
  6. 同一事务提交后对外返回权威汇总；响应丢失时按同号读证据恢复。

读取时：
  若账号/产品/成员不可用 -> allowed=false，reason 为具体原因；
  否则若存在有效永久信用 -> pro_active=true，effective_ends_at=null；
  否则若剩余有限信用>0 -> pro_active=true，
      effective_ends_at=server_now+remaining_credit；
  否则 -> Free（限于成功取得权威状态）；网络未知不得伪装 Free。
```

注意：如果采用“余额快照”，**时间流逝也会消费信用**，不能仅在写操作时递减一次后永久静止；读路径需按快照基准时间安全结算、版本化，并验证并发下不会重复扣减。

## 6. 撤销、永久、历史与特殊情形的政策（P0，不得遗漏）

### 6.1 撤销旧授权的反例及推荐处理

假设 10 月 28 日 A 授权 30 天，后来 B 又授权 30 天。到了第 20 天，A 已使用 20 天，A 尚有 10 天、B 尚有 30 天。

**若此时撤销 A**，建议行为是：从此刻取消 A **剩余的 10 天**，B 的 30 天立即接上，用户综合到期重新计算为 **从撤销时刻起再过 30 天**，而不是在 A 原定到期日前禁用 Pro、到期后再恢复，也不是回收 A 已用的 20 天。

要实现此合同，不能只 `UPDATE A.revoked_at` 后继续信赖 B 旧 `starts_at`；读投影或分配段必须重算，事件历史中保留撤销发生时间、操作者、原因和原 A 的消费事实。

### 6.2 撤销排队中尚未消耗的 Grant

若 B 的 30 天尚未被消耗，撤销 B 应把综合到期日立即缩短 30 天；不得因为 B 的旧 `ends_at` 已排在未来而无视撤销结果。撤销后旧 Grant 与其来源仍可查询，禁止用软删除把它从审计中抹掉。

### 6.3 永久信用与有限信用叠加（推荐政策，待产品方冻结）

| 场景 | 推荐政策 | 需单独确认 |
| --- | --- | --- |
| 已有有限 Pro → 授予永久 | 永久立即生效，有限信用保留为独立余额，但不继续被消费 | 是：保留/冻结 |
| 已有永久 → 新增有限/永久 | 普通 Admin 和兑换流程均禁止重复入账，返回明确原因（不消耗兑换码） | 是：拒绝策略 |
| 永久 Grant 被撤销 | 解除永久覆盖；先前**尚未消费的有限余额**恢复可用，按剩余时间从撤销时刻重新起算；已消耗历史不变 | 是：恢复策略 |
| 多份旧永久 Grant 并存 | 只要任意一个合法未撤销的永久 Grant 仍生效，继续永久；必须逐条撤销才可能降级 | 是：旧数据兼容 |

这项不能仅修改 `check_access`。如现有历史期间有永久 + 有限重叠，必须先定义旧有限额度在该期间是否视为“已消费”；**不得用一句“所有天数立即叠加”代替永久权益规则**。

### 6.4 产品成员资格、封禁与暂停

现有 `check_access` 在综合 Grant 前仍要求用户产品成员 `active` 且平台未受限。当前兑换码 RPC 可在允许场景下创建缺失成员关系，人工授权 RPC 则**不等价于自动入会**。

推荐产品原则：

- **正常成员**：直接按规则授权/兑换；
- **从未加入产品**：人工授权界面需先说明用户尚未加入。推荐明确的“先加入并授权”管理动作（如果后来批准）或要求完成既有加入流程；不能悄悄给出“可用 Pro”成功提示；
- **已退出/暂停成员**：不凭新 Grant 自动恢复，需单独授权的恢复流程；兑换继续按当前拒绝规则；
- **平台账号封禁**：一律不将“入账成功”显示成“当前允许访问”；是否禁止写入应在 Core 契约层明确；
- **暂停期间时长是否停止流逝**：**不在本轮擅自改变**。现有 Grant 按日历时间走；是否“暂停计时”是另一项待确认产品政策，必须独立评审并回归历史数据。

### 6.5 旧版指定时间窗与未来授权

用户要求新界面只保留固定天数/永久，**不代表可以直接删除旧 `explicit_window` 的历史记录或迁移时把预约时间统一改为现在**。

旧的固定时间窗可能包括：过去已结束、当前生效中、将来才开始、永久。推荐：

- 历史数据原样保留并在 Admin 历史详情可辨认；
- 新版普通授权禁用新建“指定未来时间窗”，不得影响旧记录读取、撤销或审计；
- 做迁移时区分“明确的预约 Grant”与“顺延排队产生的未来片段”，**不能把两者都当成已入账待覆盖信用**；
- 对无法无损转换的旧窗口保持 Legacy 投影/只读规则，先出具差异报告，未经审批不自动重排或清理；
- 若未来确有预约授权场景，另外建立受控高级功能，不反向污染普通“立即续期”合同。

## 7. CORE-ADMIN-UI-002｜新增 Pro 授权交互规格

### 7.1 作用域决定产品

`apps/admin/src/App.tsx` 顶部当前以 `aisencore.current.product` 保存范围；`IssueCodes.tsx` 已有类似“产品选中时锁定产品”的参考实现。新 `GrantCreate` 应按下表处理：

| 操作上下文 | 产品栏 | 服务端目标 |
| --- | --- | --- |
| 顶部选定 `aisenlens` | 显示只读“授权产品：aisenlens · 当前产品已锁定”，**不出现选择下拉** | 使用真实已确认的 `products.id` |

产品来源优先级推荐**显式已核实的用户中心产品操作 → 顶部当前作用域 → 全局手选**；任何冲突应阻止提交并要求管理员确认，绝不悄悄改写目标。

### 7.2 目标用户选择与确认

按 CORE-ADMIN-UI-001 统一：管理员输入**完整邮箱精确查找**或从用户详情进入，查到唯一真实用户后展示账号邮箱和相邻可复制的“用户编号”；写入 RPC 仍只传 UUID，不接受邮箱作为授权主键。切换用户时必须清除过时的到期预览和操作复核。

### 7.3 表单内容与排列

```text
新增 Pro 授权
目标用户：user@example.com  （已核对用户编号） [更换]
授权产品：aisenlens · 当前产品已锁定        [全局视角才允许选择]
授予类型：[● 固定天数] [○ 永久]

                                       [取消] [确认授予 Pro]
```

- 类型默认“固定天数”，天数默认 30；永久类型隐藏天数和日期输入，仅显示“永久有效（可被有权管理员撤销）”。
- 所有常规开始/结束日期输入从弹窗移除。**数据层仍允许 Legacy 合同按兼容策略存在**，新请求须由可信 RPC 自动决定入账时刻。
- 自定义整数天数在当前服务端安全范围内（现有 Admin UI `1..36500`，最终边界由 Core 冻结），非法值明确报错。
- “授予理由”仍必填，保留 200 字以内的服务端约束与管理员审计；不因 UI 简化省略。
- 对产品未加入、用户受限、已永久、网络未知等给出不同状态；**非可靠快照不得给出看似确定的预计到期日**。
- 提交前显示受益邮箱、用户编号、产品、模式、天数/永久、原因与当前权益摘要；最终提交以服务端重算/复核为准，防止预览到提交间其他管理员已续期。
- 保留 AAL2、真正管理员及产品状态检查；“锁定产品”是交互减少错误，不是后端授权证明。

### 7.4 UNKNOWN 与浏览器刷新/切页

已有 `GrantCreate.tsx` 与 `grantPending.ts` 使用浏览器会话级 pending 快照，`admin_find_grant_request` 只读核查原请求；保留并加强：

1. 发送前持久化 `actor_id, target_user_id, product_id, mode, duration/lifetime, reason, request_id` 的**原始完整参数**；
2. 未明确收到结果时，页面重新打开必须先显示原请求核查，不把未知当成功或失败；
3. 原管理员同一身份重新核查；只有权威明确不存在时才允许**同号、同参**重试；
4. 当提交后网络返回丢失或状态未知时，不得生成新 ID 追加第二份天数；
5. 只读结果发现同 ID 不同参数时拒绝；其他管理员、其他产品作用域不得夺取 pending；
6. UI 上“重新选用户/产品/模式”不能影响已经发送的 pending 快照。

## 8. 兑换码与 Admin 授予的共用核心

**推荐把两条路径收敛到受保护的“按用户+产品结算权益信用”的内部逻辑**，但保留各自的入口认证、发行/兑换约束、审计和来源关联。现有公开入口 `admin_grant_entitlement` 与 `redeem_code` 保持各自独立的身份验证和权限边界，内部才共用可信结算逻辑。

| 行为 | Admin 授予 | 用户兑换 |
| --- | --- | --- |
| 身份来源 | AAL2 管理员已核对用户 UUID | 已确认邮箱的真实用户 JWT |
| 产品选择 | 顶部范围或明确手选 | 对应当前 Lens 产品及兑换码锁定产品 |
| 来源 | `source_type='admin'`，actor+request ID | `source_type='redeem_code'`，代码核销唯一关系 |
| 何时新增信用 | 管理员 RPC 成功提交 | **用户成功兑换提交**，不是发码时 |
| 有限信用规则 | 入账立即计入综合到期 | 同一算法 |
| 永久规则 | 生效立即永久、重复拒绝策略待冻结 | 保留已实现的有效永久拒兑保护，并统一规则 |
| 写入幂等 | actor + `request_id` | 同码使用次数、用户/码唯一性及相应事务恢复 |
| 限流 / 安全 | 管理员资格、理由、审计、写锁 | 码校验/哈希、限流、码库存、成员/账号门禁、原子消费 |

**新业务抽象不能绕过 `redeem_code` 的原有锁序、核销计数、速率限制、失败不消耗码、已兑换拒绝和永久拒兑，也不能绕过管理员授权的 AAL2、`409` 冲突、审计与只读恢复。**

## 9. Lens 与 Core Admin 的显示合同

### 9.1 AisenLens（LENS-ENTITLEMENT-001）

在 `我的权益` 的顶部：

- Free 且权威查询成功 → Free；

### 9.2 Core Admin（与 CORE-USER-ARCH-001 协同）

- 授权记录列表展示“来源 / 授予时长 / 入账时间 / 覆盖状态 / 撤销状态”，不再用单个“待生效”涵盖所有维度；

- 给用户授予时读取目标用户的权威当前状态，预览追加后日期；提交返回后重新读取确认；
- `check_access` 与 Admin 不得出现“Lens 到期 11/27，Admin 到期 12/27”的持续分歧；
- 有效期日期展示需用统一时区/时刻格式，避免“同一绝对时间因 GMT+8 与浏览器本地时区看上去差一天”。

| GE-21 | 非 AAL2/被撤权管理员调用授权与用户权益查询 | 403/拒绝，高权限审计和私有账户隔离维持现状 |
| GE-22 | 旧数据、读投影、迁移/回滚演练 | 数据行数、来源、独立 Grant、核销计数、真实历史均一致；无误授或丢失 |
| GE-23 | 账户仅部分可用，旧排队记录的 `starts_at` 未来 | 顶部到期可正确包括已入账的连续续期，但列表明确区分入账和覆盖 |
| GE-24 | 同一授权引用重复读取/缓存前台重载 | 权威状态可重复计算得到同一结果，缓存按版本/时效失效，无重复扣减 |

### 11.1 技术测试层次

1. **纯规则模型**：先实现与生产 SQL 无关的参考计算器（测试样例与预计结果一一对照），覆盖永久、续期、撤销、过去/未来分段、非法时间、同秒事件稳定排序；将它作为数据库实现的对照 oracle。
2. **真实 PostgreSQL / RLS / SQL 回滚测试**：覆盖原子写、锁顺序、权限、唯一来源、账户状态、产品边界、迁移、撤销时重排、累计信用守恒。
3. **多进程并发**：人工+兑换、双兑换、双人工、撤销+续期、永久+续期、同号重试，验证不会产生负余额、双计时长、死锁或未解释时间洞。
4. **真实 Admin Chrome**：产品锁定/全球手选、邮箱精确匹配、先确认用户、7/30/90/365、自定义天数/永久、原因、加载、禁用、UNKNOWN 核查及响应式。
5. **真实 Lens Chrome + Core**：同一认证用户先兑换后人工授予，及反向顺序；页面上当前 Pro 到期立即变化，历史单条不被覆盖。
6. **故障注入**：DB 提交但 HTTP 回执丢失、服务读取失败、旧 Admin JWT 被撤销、切号、短时网络断开；错误状态不得造成额外入账。
7. **数据清洁**：每次数据库写入测试前后运行 `scripts/check-local-admin-qa-cleanliness.py`，仅可清理自己创建的 QA 用户/授权/码/事件；保持原管理员与原两款真实产品、其他既有数据不变。

**验收记账方式**：每个 GE 记录真实命令、退出码、关联 PR、数据库行与信用余额断言、截图与清理结果。没有真实执行证据一律 NOT RUN / OPEN，不以此计划作为验收通过证明。

## 12. 迁移策略、数据安全和回滚门禁

### 12.1 不在旧数据上盲目覆写

1. 先对**可安全读取的本地备份/隔离副本**清点 Grant 的 `grant_mode`、未来 `starts_at`、永久/撤销、已消耗/历史来源分布；不从已知两个真实产品或真实管理员上直接制造测试授权。
2. 明确 Legacy 预约窗与排队信用的识别规则，输出逐类转换方案及**无法无损转换清单**；不能仅按 `starts_at>now` 判定“可迁移余额”。
3. 新表/新读模型必须采用**追加迁移、先读影子校验**；旧业务操作原有表和来源引用在未获得迁移验收之前不能删除。
4. 双读/影子阶段记录新旧计算差异的类别与数量，不输出不必要的邮箱/个人资料；**任何无法解释的金额/天数差异必须阻断切换**。
5. 提供切换点的写入冻结窗口或事务一致性策略，防止切换时兑换/人工授予两套计算器各追加一次；**不可在不知道读写版本的情况下混用新旧写逻辑**。
6. 生产切换前要有按数据库恢复点验证的回滚方案；**若已按新规则产生授予/撤销事件，不能仅把代码回滚到旧 SQL**，必须有对应的数据兼容或暂停写入恢复程序。
7. 现实 R2、SMTP、外部备份和云部署不属于本次改版授权；不触发真实生产租户变更。

### 12.2 版本和兼容建议

- 用户端：保留 `check_access` 已用字段及 `allowed/reason` 的原含义，只调整合同范围内的综合到期语义；更改语义时补协议版本/变更记录和真实 Lens 回归。
- 管理端：新增受保护的“目标用户当前权益摘要”只读入口，如现有数据访问已安全足够，则不额外暴露 `auth.users`；权限必须服务端复核。
- 历史数据：新旧 `grant_mode` 允许共存读；普通新增只发“固定天数/永久”，不得把旧预约授权无提示当作新入账额度。
- 读缓存：授予/兑换/撤销后失效，跨标签页/账号须重新核验；必要时带版本号和读取时刻，绝不通过前端本地加天数替代 Core。
- 国际化/时间：以 UTC/数据库时刻作为计算源，以明确时区格式显示给 Lens、Admin；日期文本一致性必须以绝对时刻和测试基线核对。
