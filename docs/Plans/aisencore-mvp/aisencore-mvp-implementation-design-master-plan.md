## 1. 目标与方法

**总目标**：将已经确定的 MVP 逻辑架构细化为可以直接实现、明确测试、独立评审的技术设计；所有核心契约明确后再单独授权正式开发。当前无需重构五层架构，不以扩大公共平台职责代替各 SaaS 自身业务实现。

**总体原则**
1. 复用 Supabase Auth、PostgREST/RLS、受保护 PostgreSQL RPC、React-admin、Cloudflare Pages；只自行实现 AisenCore 特有的产品成员、授权与兑换逻辑。
2. 公共底座负责跨 SaaS 必需的身份/产品关系、成员、权益、兑换、管理和最小审计；产品项目、文件、业务资源权限和用量计数仍属各 SaaS。
3. **需求唯一权威**为 spec，**既定逻辑架构权威**为 architecture；本计划仅维护阶段、依赖、工作包、产物和验收门槛。新增方案与现行规则冲突时，先提交对应权威文档确认，不在计划中偷偷变更需求。
4. 先确定物理数据、安全与事务，再固定公共 API/接入契约，最后落实管理 UI 与部署细节。可并行做资料收集，但不能越过未决的关键依赖。
5. 文档中的“拟定、待验证、已评审”与实际“已实现、测试通过、生产部署”须分开记录；不预建空专题和重复的进度文档。

## 2. MVP 范围

| 工作域 | 本轮实施设计必须涵盖的能力及边界 |
| --- | --- |
| 统一身份 | Supabase Auth 邮箱密码、确认邮件、密码恢复、JWT、各应用会话；**平台管理员 TOTP MFA/`aal2` 为明确 MVP 必交付功能**（必要 enroll/challenge/verify/受控恢复与真实 E2E），普通用户不强制 MFA，正常后台业务查询不每次新发 MFA 网络请求 |
| 产品与成员 | 产品状态、首次合法使用时按需加入、退出、明确重加、产品成员封禁/恢复、事件审计；仅登录不自动入会 |
| 平台管理员与账号 | 平台 `blocked`、管理员资格、最后合格管理员保护、管理审计、账号注销的 MVP 人工流程 |
| 套餐与权益 | 产品级 Free/Pro、布尔能力、数值上限、周期/永久授权、续期/撤销、不可变套餐版本 |
| 自有兑换码 | 高熵发码、仅存哈希、明文首次响应、幂等批次、限流、核销锁序、兑换和授权事务 |
| 公共读写 | PostgREST + RLS 读取；受保护 RPC 完成状态+审计原子写入；`CheckAccess` 无副作用 |
| React-admin | 产品、用户查询、成员、套餐/授权、兑换码最小管理页面；可信管理权限，不默认访问 SaaS 私有内容 |
| 独立 SaaS 接入 | 一条可实施的“登录 → 真实业务触发按需加入 → 公共准入 → SaaS 业务资源鉴权/计量”链路 |

**非本轮公共底座 MVP 前置项**：爱发电全量回调与结算、支付宝/Stripe、自动续订、组织 RBAC、跨站 SSO/OAuth/机器身份平台、统一用量账本、通用离线 Pro 凭证、Redis 撤权总线、跨库事务/复杂事件平台、跨 SaaS 自动数据删除编排、BI/统一 AI 网关。

**首发当前已确认方向**：首发本地优先 Aisenlens、首批私有 R2 备份必需，**对公众开放注册和正常运营**；Free 保有本地可用工作流，Pro 增加 AI 分析/无水印导出/云备份，30 天/365 天/永久，无自动试用；本人 Admin 小批次单次固定时长发码；配置白名单与手动版本恢复、Pro 关键操作复核；详见 [2026-10-22 用户决策记录](./aisencore-u03-u11-user-decisions-2026-10-22.md)。AI 输入/输出、项目、视频与密钥仍不通过平台或进入备份。**真实上线需要邮件、注销、管理员安全和所有运行验收，产品细节、MFA 评估未全部结束**。

## 4. 八项实施设计工作包

### 4.1 工作 1 — MVP 范围、技术基线、依赖（D0）

- [x] 将需求与当前主架构映射为首版公共模块、外部依赖、必要管理员功能和首个 SaaS 接入目标（U01 已确认 Aisenlens 本地优先，U02 已确认首批必须支持 R2 文件/配置备份）。
- [x] 标记已确认与待实施核验的技术版本、邮箱及域名、初始管理员、MFA 恢复、必要运维条件；不臆造配置值。
- [x] 确认每个职责属于公共核心还是 SaaS，写明明确非目标、阶段依赖和会阻断后续设计的决策。

**产物**：范围/依赖基线、技术假设和待确认问题清单。**通过判据**：范围明确，无阻塞 D1 的业务定义歧义。

### 4.2 工作 2 — PostgreSQL 物理数据库（D1）

- [x] 定义各公共实体实际 Schema/表名、字段类型、默认值、PK/FK、UNIQUE、CHECK、必要索引及引用删除策略（D1 设计文档 §1～2，**候选规格，未经 SQL 编译/执行**）。
- [x] D1 设计现已按 2026-10-23 最新决定修订，包含产品、成员/事件、管理员/限制、`entitlement_grants`、兑换码/批次/核销、限流和审计；**不包含公共 plans/plan_id 或 SaaS 功能/额度表**，不重复建 Auth 用户主档。真实迁移尚未执行。
- [x] 定义不可变字段、可信时间、授权时间区间、码次数上限、`request_id` 幂等唯一性和状态组合约束。
- [x] 设计空库迁移顺序、初始所有者种子、安全升级与备份/回退原则；**仅编制 SQL/DDL 设计，不执行迁移**。

**产物**：物理模型、DDL 规格、约束/索引清单、迁移顺序。**通过判据**：合法/非法数据可据此判定，设计可以直接转为数据库迁移。

### 4.3 工作 3 — 数据权限、RLS 与事务并发（D1）

- [x] 按表列出 `anon`、`authenticated` 与平台管理员可读/可写范围，具体 GRANT、RLS Policy、EXECUTE 及受限列投影（D1 §3；SQL 实际有效性待测试）。
- [x] 确定 `private.is_platform_admin()`、管理员 `aal2`、`SECURITY DEFINER`、固定 `search_path`、最小函数所有者及暴露/私有 Schema 的界限。
- [x] 定义成员加入/退出/重加、封禁/恢复、发码、兑换、续期、授予/撤销及管理操作的事务锁顺序、审计原子性、重试和竞争处理。
- [x] 专项检查 **M1**：`BlockAccount`/`RevokeAdmin` 必须共享串行化保护，变更后仍至少有一名 active 且未 blocked 的管理员；不能经 Auth Admin 直接封禁绕过。
- [x] 专项检查 **M2–M4**：任何 grant 或已发行 code 引用的套餐权益冻结；码只存哈希且明文不可恢复；本人重复兑换优先于后续过期/用尽/撤销且不重复授权。
- [x] 设计拒绝未授权直接写入、跨用户查询、审计写入失败的反向及并发测试。

**产物**：RLS/GRANT 矩阵、可信 RPC 安全与锁序设计、事务不变量表。**通过判据**：关键不变量能被数据库正反向/竞争测试表达。

### 4.4 工作 4 — 公共 API 详细契约（D2）

- [x] 固定自助、只读及管理员 RPC 的**候选实施签名**、身份来源、参数与 JSON 响应字段，包括 `ensure_membership`、`leave_product`、`rejoin_product`、`get_my_products`、`check_access`、`redeem_code`、发码/撤码、授权操作（正式 SQL/客户端生成仍待实施验证）。
- [x] 明确 PostgREST HTTP 映射、业务错误码、查询/写入差异、版本兼容**核验门槛**与 SaaS 调用示例。
- [x] 专项检查 **M5**：`CheckAccess` 已认证且可信计算出的拒绝返回 **HTTP 200 + `allowed=false/reason`**；缺失/无效身份用 401，可信验证失败用 503/5xx，不能误放行。
- [x] 规定 `RedeemCode` 预期业务拒绝为 HTTP 200 + `ok=false/code` 以保留限流统计；技术故障则回滚。
- [x] 确定超时后的状态确认、幂等键、重复请求、竞态、码首次明文响应丢失与撤销重发行为。

**产物**：RPC/API 详细接口契约与成功/拒绝响应示例。**通过判据**：SaaS、Admin 无需自行推断数据格式与失败语义。

### 4.5 工作 5 — Auth/MFA 与多 SaaS 接入（D2）

- [x] 确定邮箱确认、密码恢复、**回调安全约束（域名待 U06）**、会话/刷新、管理员 TOTP MFA/`aal2` 和受控恢复责任归属（U05 待定）。
- [x] 明确各 SaaS 如何验证共享用户 JWT、保留真实操作者上下文、调用公共 RPC；不把 `product_key` 当作机器身份。
- [x] 设计首发 **Aisenlens 本地优先** 完整流程：匿名 Free → 本人登录/按需加入 → 在线权益 → 私有 R2 签发/上传确认/恢复 → 资源/配额与故障处置；通用云端 SaaS 后端接入继续作为既有架构参考。

## 7. 执行与变更控制

- **顺序**：原设计流程 D0 → D1 → D2 → D3 → D4 已执行文档层评审；**Admin 前端的新阶段顺序为 D3 → D3-UI（文本页面规范）→ UI-G0（真实高保真+用户批准，强制 BLOCKING GATE）→ 正式 UI 编码 → 浏览器视觉及安全验收**；D3-UI 和 UI-G0 的测试追踪追加到历史 D4 后续执行，而不是伪称原 D4 已评审后来追加的视觉画面。允许不冲突的非 Admin UI 工作按另行授权推进。
- **停止条件**：若新方案触及未确认需求或与现行架构矛盾，先在 spec 或相应 architecture 专项确认，再继续依赖它的工作包；不必停止完全独立的设计。
- **技术细节留给专题确认**：SQL 字段/索引/锁具体选型、RPC 最终签名、Supabase/Edge 版本、`ra-supabase` 兼容、邮箱/回调配置、发码批次上限、部署命令和测试工具，不在此计划凭空规定。
- **过程记录**：每轮设计结束回填本计划中对应勾选项、实际产物链接、评审结果和未完成阻塞；不为每次会议生成新版本总计划。
- **实现独立授权**：实际编码、SQL 执行、云配置、部署与 Git 提交都必须按后续具体授权进行。
