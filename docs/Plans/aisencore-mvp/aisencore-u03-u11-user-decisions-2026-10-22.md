## 2. Pro 的可信期限与明确永久（2026-10-23 最终修订）

**公共核心仅有产品 Pro 资格、来源和时段**。每条 `entitlement_grants` 以 `user_id + product_id + tier='pro'`、可信 `starts_at`、`ends_at` 和撤销信息表达。Pro 永久是明确的 `ends_at IS NULL`，不是永久 JWT、免于封禁，也不是循环发行 365 天授权。无当前有效 Pro 时派生 Free；不会发行 Free 授权或编辑公共功能/额度。

| 产品运营显示 | 公开资格 | 原始授权时段 | 说明 |
| --- | --- | --- | --- |
| Free（默认） | 无有效 Pro | 无 Free Grant | AisenLens 离线免费功能由 SaaS 实现，Core 不控制功能矩阵 |
| Pro 30 天 | `pro` | `ends_at=starts_at+30 days` | 固定 30 天并不等于自动月订阅 |
| Pro 365 天 | `pro` | `ends_at=starts_at+365 days` | 固定天数，并非每年相同日扣费 |
| Pro 永久 | `pro` | `ends_at=NULL`（显式确认） | 无自然截止日，仍可撤销/被成员或账号限制 |

30、365、永久只是**发行时长参数或 UI 快捷预设**，不是三个 `plans.plan_key`、不同功能版本，也不要求 Pro 套餐引用冻结。改变 AI、视频导出、私有配置备份、次数/容量只应改 AisenLens 自己的策略与可信执行端。

**首批发码**：已确认仅固定正整数天数、通常单次兑付，优先 30 或 365 天；每个 Code 要保存首次 Pro 授予天数，`expires_at` 表示码可兑换的截止时间，不是 Grant 期末。永久 Pro 先由受控人工直授在 `explicit_window` 模式明确传 `ends_at=NULL`；若以后决定发行永久 Pro 码，应单独批准其运营和不可缺省的输入语义，不能把漏传天数误当永久码。后续价格、退款、永久购买承诺依然待产品决议。

## 3. Admin MFA：已纳入 MVP，解决重复验证的体验诉求

**后续 2026-10-22 用户确认覆盖本文件最初记录的“暂缓 MFA”提议**：当前 [管理员领域权威](../../architecture/domains/platform-admin-and-account-lifecycle.md#1-平台管理员最小可信机制) 要求 Admin TOTP MFA/`aal2`，用户现已明确**加入 MVP**。因此不再存在“是否取消生产 MFA”的政策冲突，实际还需要评测**如何不增加重复网络认证与操作延迟**；保持管理 RLS/RPC 的每请求真实 `aal2` 与数据库当前资格授权。

**MVP 已确认的低打扰方案**：Supabase Auth 官方 TOTP 登录第一因素后 challenge/verify 取得 `aal2`；已验证会话里的普通 Admin 数据读取与管理 RPC **在当前业务请求中核验 JWT `aal2` + 实时资格**，**不应每次单独发 `getUser`、MFA challenge/verify、`admin_check_access` 远程请求**。需要重新登录、会话 `aal` 降级、因素失效时才重新执行必要挑战。新设备/刷新/浏览器重开与恢复仍需在 SDK 版本和会话策略下实测，详见 [MVP Auth/Pro/Admin 优化](./aisencore-mvp-auth-entitlement-mfa-efficiency-design.md)。

**当前状态**：`ADMIN TOTP MFA REQUIRED IN MVP; LOW-FRICTION UX TO BE TESTED`；不仅设计 UI gate，还必须完整实现首次因素注册、登录挑战、受保护服务端权限门禁、会话/因素失效和受控丢设备恢复；所有真实验收仍 NOT RUN，**没有批准 `aal1` 访问 Admin**。普通用户 MFA 不在本次 MVP 强制范围。

**个人单人运营与“备用管理员”**：可拥有主管理员和一条备用恢复方案，但“第二账号由同一个人同一设备登录”不能构成独立的人力灾备，也未提供一个真实可信的第二人员。当前建议记录**单实际运营者**，不要捏造另一名管理员身份；所有者应规划离线保管的账号/MFA 恢复材料（不进仓库）、必要时受控数据库恢复入口。M1 的“至少一名合格管理员”数据库不变量继续有效，不等于真实 Auth/MFA 设备可恢复。
