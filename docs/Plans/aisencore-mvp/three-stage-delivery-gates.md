# AisenCore × AisenLens｜三阶段开发与交付验收总则

> **项目所有者于 2026-10-24 确定的执行阶段与准入规则。** 本文说明开发顺序、验收标准及跨阶段边界，纳入 [MVP 唯一总计划](./00-mvp-master-plan.md) 并由 [TODO](../TODO.md) 跟踪。既有 D1/D2/D3/S1/D4 是**技术工作流和历史任务编号，不是五个独立交付阶段**。业务与安全规则仍以 `docs/spec/` 和 `docs/architecture/` 为准。
>
> **当前状态（2026-10-27）：所有者宣布第一阶段基本结束，进行第二阶段准备；第一阶段完整签收及其未通过/未运行门禁仍在跟踪，第二阶段真实双端联调尚未执行，第三阶段未获部署授权。** 曾通过的本地测试不代表第一阶段的完整 UI、无障碍及交付标准已经达成。

## 一、三阶段一览

| 交付阶段 | 明确终点 | 测试环境和数据 | 核心交付物 | 准入下一阶段条件 |
| --- | --- | --- | --- | --- |

**阶段原则：每阶段必须完成该阶段可完成的全部内容，不能把本可在前一阶段独立完成的问题推迟到后一阶段。** 阶段进度由证据和明确签收决定，而不是源码是否存在、构建是否通过或测试数量。三阶段连续衔接，但不得跳过验收门禁。

## 二、第一阶段：对接前完成真正可交付的 Admin

### 1. 功能与业务流程

- **全部 Admin 模块可交付**：管理概览、产品、成员与用户、Pro 授权、兑换码批次与安全码、核销记录、成员事件、账号查找、管理员、账号限制、管理审计，以及必要的认证/恢复辅助页面。
- **每个模块逐状态验收**：真实列表与详情、可用的搜索/筛选/排序/分页、准确的计数与状态展示、适用的导出/复制、列表到详情再到操作结果的导航；加载、无数据、部分数据、权限不足、网络错误、超时、并发冲突、成功/失败反馈都须被设计和测试。不得强行给不适用的业务表增加危险导出或任意修改能力。
- **全业务闭环**：产品创建/启停、成员生命周期、Pro 授予/撤销及期限模式、批量发码/首响明文/CSV-TXT、UNKNOWN/429/503/断网恢复、兑换/核销只读、用户精确查询、账号封禁/解封、管理员授予/撤权、审计与错误恢复。后端依赖但尚未接入 AisenLens 的事项，以本地可信 RPC/临时真实 Auth 会话验证。
- **演示数据驱动的高标准业务验收**：保留可重复初始化、可隔离、不会污染普通本地数据的合成 fixture；覆盖正常、临界、异常、空态、失败重试与安全拒绝。脚本与手工验收均需提供可复核记录，不把静态 Demo、假点击或仅 DOM 渲染算为功能 PASS。
- **实现质量**：必要代码抽象、清晰类型边界、模块拆分、无重复/废弃的正式页面、统一 UI 组件/设计规范、错误日志安全与回归测试；既有 Core 身份/RPC/管理操作的本地安全、并发、幂等和审计缺口在此阶段内尽可能关闭。

- **新增反馈领域第一阶段独立交付**：完成反馈三表、RLS/受保护 RPC、本地受限上传测试替身、Admin 当前 V3 四队列列表/详情、标签/星标/优先级/内部备注及原位恢复（旧 V2 五态和公开回复保留历史只读）、无权限/并发/网络异常、安全负例与全量视觉/WCAG/响应式测试；不能拖到 AisenLens 联调才补做。权威为[用户反馈架构](../../architecture/domains/user-feedback.md)。

### 2. 强制视觉与无障碍标准

- **八维完整视觉评审**：`Typography`、`Whitespace`、`Visual hierarchy`、`Color`、`Motion`、`Micro-interaction`、`Responsive`、`Originality`；参考 Awwwards / Webby / FWA 的优秀设计品质，但适应高频 B2B 管理场景，拒绝未加工的默认组件拼装。需要进行整站逐页、跨状态对比和反复修正。
- **无障碍是第一阶段准出项**：目标 WCAG 2.2 AA，覆盖键盘全流程、焦点与弹窗焦点管理、读屏名称/语义、输入校验提示、颜色对比、`prefers-reduced-motion`、表格语义、复杂交互与中文输入。以自动化 + 人工检查共同提供证据，不能用少量 Tab/Escape 烟测冒充全量验收。
- **响应式和可操作性**：桌面/平板/手机、常见最窄视口、200%/400% 缩放与不同业务密度，不允许关键按钮不可达、长 UUID 撑破页面、表格不能操作或弹窗无法关闭。完整列表、表单、详情、异常页都必须覆盖，而不只是管理概览。

### 3. 第一时间完成的前端性能工程

- **优先优化首次访问和页面交互**：按资源/路由懒加载、业务与第三方代码拆包、公共模块去重、避免重量级依赖一次性打包，控制首屏加载、字体/样式及图表资源，减少不必要的重新渲染和请求。
- **性能不以单一 bundle size 作为终点**：在生产构建预览中，量测冷/热启动、主要页面首屏加载、切换资源、较大数据量表格筛选/分页/滚动、交互响应、内存与网络请求；维护每项可复现的基准和与回归结果，并在阶段签收前确认适合本项目的数值预算。
- **代码与质量门禁**：`pnpm install --frozen-lockfile`、`typecheck`、`lint`、`build`、依赖审计、关键前端/数据库安全测试、真实浏览器 E2E、构建产物密钥检查；消除影响交付的 P0/P1 缺陷与已确认的性能退化。

### 第一阶段退出判据

- [ ] 全部 Admin 资源、必要流程和状态清单逐项 PASS；任何已知 P0/P1 业务阻塞不得带入第二阶段。
- [ ] 真实本地 Auth/MFA 与可信 RPC 的安全正反例、操作/数据/审计闭环可重复；合成数据与临时 QA 对象有安全清理机制。
- [ ] 前端懒加载/分包、可复现性能基准及优化、无严重性能回归，生产构建验收通过。
- [ ] 各模块全表格/业务状态的响应式、完整键盘与无障碍验证通过；高标准八维视觉已逐页修订。
- [ ] **项目所有者明确完成 Admin 最终视觉和第一阶段交付签收**，才允许把主工作流切到 AisenLens 本地对接。

## 三、第二阶段：真实 AisenLens 本地数据和双端开发

- **数据规则变化**：以在 AisenLens 本地客户端真实操作、注册、登录、创建项目/设置、兑换或使用 Pro 等生成的**实际业务数据**为验收依据；不得用第一阶段 `seed:admin-demo`、演示批次、假网络响应替代双端真实通信。允许专用于隔离测试的实名义测试账号/测试请求，但必须通过真实业务路径产生、可追踪且可清理；不要将“真实数据”理解为要导入生产用户隐私数据。
- **双端同步开发**：AisenCore 后端/可信 RPC/必要 Edge 与 AisenLens 对应前端、登录界面、产品成员、Pro 资格展示与复核、兑换码输入、异常提示、Free 离线行为等同时推进；不得只交付 Core API 而留下客户端未实现。
- **剩余业务按批准范围实现**：真实 AisenLens 会员/授权端到端、状态/到期/撤权感知、按需核验和并发去重；若首发包含私有配置备份，还必须完成元数据/配额预留、受保护 Edge/存储适配、白名单、版本选择/差异预览/恢复、跨系统幂等和故障对账。
- **各模块通信验收**：真实客户端 ↔ Auth ↔ Core API/PostgREST/RPC ↔ AisenLens 业务与（适用时）Edge/备份存储的请求和响应、身份/产品归属、业务边界、重试/超时、离线重连、跨产品隔离和安全失败；逐项复核适用 `I-01～I-28`、`R-01～R-15`、`REV-*`，形成可重放日志。
- **同步完善视觉和交互**：AisenLens 新增/修改的注册、登录、权益、备份与恢复 UI 达到自身约定质量；仅因真实业务数据暴露的新问题应同步修复，但**不能把第一阶段欠下的 Admin 设计任务当作正常的第二阶段工作**。
- **上线参数准备但不部署**：冻结真实产品业务白名单/备份额度/保留规则与断网 Pro 行为；本地对接可以以协议兼容存储进行故障注入，真实云 R2/SMTP/域名端到端验证属于第三阶段。若第二阶段本地必须访问外部服务，仍需单独获授权。

- **新增反馈真实双端联调**：从 AisenLens 客户端实际填写文字与最多 2 张图片，完成本地 Core/测试存储提交、本人查看当前 V3 允许的状态、Admin 四队列处理与再次核对；覆盖断网/幂等/跨产品拒绝，绝不使用合成 seed 代替。

### 第二阶段退出判据

- [ ] 双端功能均已完成，无代替真实业务流程的演示 fixture 依赖。
- [ ] AisenLens 的注册/权益/兑换/必要备份恢复及各模块跨端通讯，在本地真实操作数据下正反向验证通过。
- [ ] 所有跨端数据、身份、权限、幂等、故障补偿与离线行为有真实证据；对应后端与 AisenLens 前端均完成质量验收。
- [ ] 项目所有者确认第二阶段通过，才进入线上环境配置与跨部署测试。

## 四、第三阶段：实际部署与三端跨环境验收

- **部署对象**：线上 Supabase 数据库/Auth/API/必要 Edge，已构建的 Admin（按既定 Cloudflare Pages 方案），AisenLens 正式部署端或发布候选包，以及适用的 R2 私有桶/受限凭据和邮件发送服务。
- **环境与安全**：环境隔离、HTTPS、域名/回调白名单、真实 SMTP 发信与确认/恢复、生产管理员与备用 MFA、最小权限密钥、RLS、日志告警、CSP/安全头、反滥用、备份恢复与迁移/回滚演练。**禁用第一阶段公知开发管理员口令、开发 Auth 密钥及测试 fixture，不能把本地配置直接复制到生产**。
- **部署端完整业务测试**：在真实部署链路上重复注册/确认、登录/MFA、AisenLens 会员与 Pro、兑换码、Admin 管理、数据权限、R2 私有上传/下载/恢复和跨服务异常回滚；实际验证各服务通信、邮件投递、会话生命周期、备份与账号删除。
- **反馈云端专门验收**：在已单独授权的线上/预发环境验证私有 R2 图像上传、短期按权限下载、孤儿清理、秘钥最小权限和账号注销清理。Mock PASS 不等于 REAL R2 PASS。
- **生产级非功能验收**：有代表性的并发/数据规模、关键 RPC P50/P95、客户端启动和网络请求量、页面性能、可靠性、可观测性、安全扫描、生产配置隔离、事故应急与灾备。
- **先预发布后正式上线**：可以先在受控线上测试或预发环境验证，出现问题须修复重测；**生产云变更、Git push、对公网公开发布均要求项目所有者另行明确批准**。第三阶段计划本身不是部署命令或上线授权。

### 第三阶段退出判据

- [ ] Admin、Supabase、AisenLens 的真实部署端具备同一版本范围的全链路 PASS 证据。
- [ ] 邮件/Auth/RLS/MFA/支付（若首发承诺）/R2（若首发承诺）以及容错、监控、备份恢复与回滚完成真实环境验收。
- [ ] 完成生产安全、性能、数据保护和合规运营清单，关闭上线阻塞项。
- [ ] 所有者独立签署正式上线批准，才可对公众开放。

## 六、验收记录约定

所有任务记录**阶段归属、验收环境、数据类型、页面/业务状态、测试方法、证据位置、结果（PASS / PARTIAL / FAIL / NOT RUN）、已知缺陷和验收人**。严禁把第一阶段 mock 数据的 PASS 写成第二阶段真实双端 PASS，也不得把第二阶段本地通过写成第三阶段部署通过。阶段交接必须有未完成事项清单且 P0/P1 门槛已关闭；任何签收需要项目所有者明确确认。

> **本文件写入并更新索引只调整计划与验收规则，不意味着已完成任何阶段或获得真实 SaaS 对接、云端连接、Git 推送、线上部署批准。**
