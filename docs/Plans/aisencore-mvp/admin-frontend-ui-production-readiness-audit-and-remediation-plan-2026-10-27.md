## 0. 一页结论与使用方式

**判断**：Admin 已有完整的 React-admin/MUI 应用骨架、多资源列表/详情、登录 TOTP、运营命令、反馈工作台、安全确认及响应式加载状态；**尚不满足可宣布的生产级 UI 验收**。既有工程完成度曾被定性估计为约 75%–80%，该估计**不是经加权清单逐项验证的完成率，也不能当作发布准入率**。本次以逐项验收状态取代单一百分比。

**最关键的剩余工作**：（1）生产环境文案/身份/操作影响范围；（2）全业务成功与失败交互闭环；（3）非空数据的 SPA/移动端任务；（4）全站 WCAG 2.2 AA、八维视觉与真实所有者签收；（5）网络、数据规模、异常与完整证据。前端不能代替后端补出尚不存在的管理员角色、注销或实际业务权限；涉及这些能力先由领域合同批准后再实施 UI。

**验收纪律**：
- `CODED` 仅代表源代码存在；`PASS` 必须注明环境、数据、业务场景、测试命令与证据；`PARTIAL` 表示已验证但覆盖不完整；`FAIL` 是已复现问题；`NOT RUN` 表示未运行，不得写为故障已发生，也不得写为 PASS。
- **P0**：阻止生产/第一阶段准出，涉及信息泄漏、错误授权、操作结果不明、不可恢复的敏感损失或关键操作不可达；**P1**：关键业务、准确性、无障碍、端到端体验和完整生产质量缺口；**P2**：体验一致性、效率与可维护性改进。优先级是整改顺序，不等于已复现严重漏洞。
- 第一阶段使用**隔离本地环境、合成但代表性的产品/用户/成员/授权/反馈记录**做完整 Admin/Core 真实路径验收，需所有者视觉签收；第二阶段由 AisenLens 实际本地操作数据验收双端；第三阶段才是已单独授权的部署环境、真实 R2/SMTP/生产配置及正式发布。任何本地成功不得宣称已上线。

### UI-G5｜统一业务状态与异常恢复（P1）

建立并逐模块落地以下最小状态合同（复用 MUI/RA；没有现实需求不开发“通用状态机框架”）：

| 状态 | 用户可见行为 | 不允许的结果 |
| --- | --- | --- |
| 首次等待 | 固定结构先出现，动态表体/值局部反馈 | 长白屏、全页跳变、无障碍静默 |
| 空数据 | 明确说明无记录 vs 等待查询条件 | 请求失败时假装空数据 |
| 后台刷新 | 保留仍有效的旧数据显示更新标志 | 旧产品内容误套入新产品、无限 spinner |
| 401/403、MFA | 及时阻断受保护操作，提示登录/再认证/权限失效 | 自动回退为普通空列表或持续可点击危险操作 |
| 409 并发冲突 | 提示最新状态，安全刷新与人工重试 | 偷偷覆盖、覆盖未提交输入 |
| 429/503/断网 | 显示可操作重试或稍后处理 | 假报成功、把网络错误解释为封禁 |
| UNKNOWN 写入 | 使用原请求号只读核验、谨慎恢复 | 立即生成新的高风险请求 |
| 成功反馈 | 对象、范围、结果可核对；相关列表刷新 | 成功 Toast 但目标数据未更新且无说明 |

**准出**：关键模块至少覆盖 8 类中适用状态的可重放自动化与重点人工验证；所有失败场景中无敏感数据泄露与错误成功状态。**当前：IN PROGRESS（UI-04 列表 GET 429/503 真实 Chrome 注入/恢复 PASS；其余模块与人工异常矩阵尚未关闭）**。

## 5. 每页必须执行的共同验收清单

对 `3` 中每个页面/弹窗，都按下面的核验序列记录 PASS / FAIL / NOT RUN：

- [ ] **数据语义**：真实受保护 API 返回、字段含义准确、账号/产品/权益状态不混淆；关联数据丢失或 403 不假装正常。
- [ ] **正常任务**：进入、找到、搜索/筛选/排序/翻页、查看/操作、回退到来源，关键上下文正确。
- [ ] **边界任务**：0 / 1 / 20 / 21+ 行、多页、长文本、特殊字符、日期/时区、空引用及异步切换。
- [ ] **等待与刷新**：首屏结构立即可见、无长期空白、局部 busy/更新态与真实数据稳定。
- [ ] **权限与故障**：匿名、AAL1、AAL2、撤权、401/403/409/429/503、断网/超时，安全拒绝和准确提示。
- [ ] **安全操作**：确认范围/后果、阻止重复提交、失败保留输入、UNKNOWN 可核查、敏感状态离开前保护。
- [ ] **响应式**：320/390/768/900/1440、200%/400% 和适用的真机交互，重要控件不遮挡。
- [ ] **无障碍**：键盘、读屏、焦点、状态提示、表单错误和对比度；记录工具版本、incomplete 人工判定。
- [ ] **八维视觉**：层级/字体/留白/色彩/组件/微交互/响应式/无障碍；所有者有可复核截图与意见。
- [ ] **性能**：响应/交互预算和真实 SPA 数据作用域，不因性能调优降低权限或业务语义。
- [ ] **回归与留痕**：自动化命令、退出码、截图/视频/JSON 证据、异常日志、合成数据清理及评审人。

不适用（N/A）需注明理由；只存在代码却未测，必须标 `NOT RUN`，不得默认为 PASS。

#### UI-01 / P1 — 部署标识与配置失败文案

- **复核事实与根因**：`App.tsx` 原导航尾部无条件显示“本地开发环境”，点状标识为 `success.main`，但标签既不检查构建模式，也不核实健康状态；`main.tsx` 会将公开配置异常或动态 App 导入失败统一交给 `SetupScreen`，后者原来始终显示仓库路径、本地服务端口和开发命令。没有证据表明此处直接输出 Secret Key，但错误分支确有不恰当的生产文案和误导性正常绿色语义。
- **决策与边界**：遵循 Vite 受控构建变量 `import.meta.env.DEV` / `MODE`：开发服务器显示本地开发、显式 `staging` 模式显示预发，其余正式构建显示生产；点状标记采用中性 Theme Token，不假装检查服务在线。仅 DEV 分支提供本地排障步骤；非开发构建一律提供通用不可用状态和重新载入动作，不回显配置问题。构建模式只标识构建目标，**不是部署环境的真实健康证明**；正式部署还需第三阶段核验构建参数。
- **施工细节**：只改 `App.tsx` 与 `SetupScreen.tsx`，不改变配置判定、Supabase/Auth 加载条件、密码与公开密钥路径；生产的模块加载失败与配置失配均安全降级。本地 QA 正式构建可能包含 `127.0.0.1` 的公开 Supabase URL，这是第一阶段预览环境的连接参数，不可误判为可见开发配置说明或允许用于实际部署。
- **验收计划**：A. TypeScript/Lint/正式构建；B. production 与 `--mode staging` 分别检查产物中环境标识及排障指令不可见；C. 用真正开发服务器以及预发/生产构建模拟缺失配置、无效 URL、模块加载失败，记录屏幕、刷新行为、焦点、320/390/1440 视口；D. 第三阶段在真实部署配置下复测。本轮 **A、B PASS；C 中开发服务器缺配置 Chrome 烟测 PASS，其余 C 和 D NOT RUN**，所以整体 **PARTIAL / NOT ACCEPTED**。

#### UI-03 / P1 — 账号状态读错时的绿色 Chip

- **复核事实与根因**：`UserShow.tsx` 的状态文案已区分 `restrictions.isPending`、`isError`、`blocked`；原来 Chip 的背景和前景色却只判断 `blocked`。读取失败时 `restrictions.data ?? []` 可能得到空数组、`blocked=false`，从而出现“账号状态不可用”搭配绿色正常态，属于确定的视觉语义错误；不据此推断后端已越权或封禁事实错误。
- **决策与边界**：只派生 `pending / unknown / blocked / normal` 四态；未确定时绝不以旧/空数据染绿，分别复用 MUI `default / warning / error / success` Theme 色和 outlined Chip；加入状态语义 `role=status`。不改受保护 RLS 查询、不将页面状态作为敏感 RPC 的权限证明，不新增状态机。
- **施工细节**：修改 `UserShow.tsx` 的状态导出分支与 Chip 展示，不动 Grant、成员关系、用户检索及关联加载。保留查询错误时明确的“账号状态不可用”文案，而非伪装成正常。
- **验收计划**：A. TypeScript/Lint/正式构建；B. 在真实只读 `restrictions` 请求上注入 pending、403/503/断网、正常、已封禁四态，截图和读屏确认 Chip 语义；C. 再检查用户切换和旧请求迟到时不会混用状态。本轮 **A PASS；B、C NOT RUN**，所以整体 **PARTIAL / NOT ACCEPTED**。

#### UI-02 / P1 — 平台级危险操作对象、范围与状态确认（已实施，真实主路径 PASS）

- **复核事实与因果**：`AccountActions.tsx` 已通过受限 `users` 身份查询核对精确 UUID + 邮箱，理由必填且两步确认；原末次确认却只重复 UUID、动作，不展示当前或预计状态。服务端 `private.admin_change_account_core` 把 block/unblock 作用于 `platform_account_restrictions.kind=blocked`，把 grant/revoke 作用于 `platform_admins.active`，在单事务里执行资格、MFA、M1 最后管理员保护；返回值仅 `changed/action`。它不提供前端猜测角色和产品权限的授权能力。当前 `dataProvider` 对 `admins`、`restrictions` 均存在受限、支持 `user_id` 精确筛选的只读列表路径，可用于 UI 当前状态核查，无需增加后端合同。
- **最小实施方案**：① 仅在已核实目标身份后发起目标 UUID 的两项只读查询；错误/等待时明确展示无法核查并禁用“核对目标与操作”和提交，不能把零数据与查询失败混同；② review 说明必须同时包含可信邮箱/UUID、**全平台**范围、所选状态“当前→目标”、实际后果及反向恢复命令；③ 身份、动作、理由、被查询状态变化时必须重新核对；④ 复用既有受保护 RPC、二步核对、busy 锁和刷新，继续由服务端决定最后管理员冲突和实际授权，不从侧栏产品范围派生权限；⑤ 完成后刷新目标状态，服务端错误不得显示成功。
- **实施事实与验证**：`AccountActions.tsx` 已实现身份先验 → 两项受保护只读状态核查 → 全平台/当前→目标/恢复方式确认；失败/等待时不许提交，输入/状态变化使确认失效，在途锁定输入，后端仍是权限权威。`scripts/test-d3-authenticated-pages.mjs` 在隔离真实 Auth/AAL2 Chrome 中新增四动作的目标身份、全平台范围及状态转换断言；原受保护 RPC、审计、撤权后旧 AAL2 访问被拒绝路径本轮 **PASS**；测试 QA 产品/Auth 账号清理与复查 **PASS**。第一次全量运行因旧反馈页标题断言不符 FAIL，已按当前真实页面修正并重跑 PASS，不能隐去此过程。尚缺目标查询 403/503、无身份证据、单独 409/幂等、并发点击及人工读屏/真机/所有者评审，整体 **PARTIAL / NOT ACCEPTED**。

#### UI-04 / P1 — 列表错误语义与恢复（首批源码/合同复核，尚未施工）

- **核实事实**：`WorkspaceLists.tsx` 原将所有 GET 错误统一展示为“记录读取失败，请检查管理员身份、网络及权限”，虽有 `query.refetch()`，但把 401/403 与 429/503/断网混为一谈。进一步沿 `dataProvider.ts` 发现：`asError` 支持可信响应 status 且 RPC 路径会传递；**普通 getList/getOne/getMany 原来解构响应时遗漏 HTTP status**，仅依赖有限的 `PT*` code 映射，导致真实限流/服务异常的状态无法保真。网络传输错误可能没有状态。读取失败未调用 `setSearch` 或清空 `draft`，已有代码在 `query.isError` 时也不渲染空态。既有缺陷属于错误语义和状态传递，不是已确认的“把失败当成空数据”。
- **最小修复设计**：第一小步只在 `WorkspaceLists` 既有 Alert 分支按可信 HTTP 状态区分会话/管理员-MFA失效、409 已变化、429 限流、503 暂不可用、无响应网络故障与其余未知错误；仍复用一次已有的 `refetch` 和原筛选/排序/页码；不可直接输出不受控 SQL/服务端错误原文。不预建全站错误框架。权限错误提示重新认证，普通临时错误提示重试；确保失败不再显示“暂无匹配记录”。第二小步独立审阅 `Feedback`、`IssueCodes`、`GrantCreate` 等写入模块的 UNKNOWN/409 既有约束，绝不能用通用 GET 重试策略错误重发写入请求。
- **本次实施与新增实测根因**：`dataProvider.ts` 的 getList/getOne/getMany 将实际响应 `status` 交给原 `asError`，保持 401/403 清空资格缓存；`WorkspaceLists.tsx` 在既有 Alert 区分 401/403、409、429、503、断网/超时、未知并保留重新认证/原查询重试，不另造抽象。首轮单次 HTTP 注入只拿到正常列表，无法作为负例证据；第二轮改为显式刷新与持续注入后，**429 已通过并进入下一步**，而 503 在约 30 秒内被 Chrome 实际拦截 15 次，页面仍显示“正在更新记录”，没有及时提示故障，证明仅依赖最终 `isError` 的设计仍不足。已进一步使用 `useGetList` 的在途 `failureCount/failureReason` 在首次失败时提示错误，并隐藏不可确认的缓存行，保持原筛选和安全只读重试。增强后的真实 Chrome 注入 **429/503 均 PASS**：错误与空数据分离、UUID 搜索条件保持，恢复后原筛选重试成功；第一次增强版全量回归在表格排序读数时遇到旧等待竞态 FAIL，已将测试改为等待真实升序记录最终到达，**最终完整本地 AAL2 Chrome 回归 PASS（退出码 0）且 QA 产品/Auth 清理 PASS**。TypeScript/生产构建、Lint、脚本语法/差异检查、静态秘密扫描、认证并发回归均 PASS。仍缺只读 401/403、断网/超时、人工读屏及跨反馈/Grant/发码的完整异常矩阵，整体 **PARTIAL / NOT ACCEPTED**。

**后续 UI-05～UI-14** 仍按既有矩阵逐一执行相同“源码/合同/证据复核 → 独立方案 → 修改 → 真实验证”过程，不能把未复核的问题批量结案。

### 7.2 剩余问题逐项复核与施工前方案（2026-10-27 续批）

#### UI-05 / P1 — 非空多页数据与迟到响应
- **已核事实**：`WorkspaceLists` 的 GET 包含产品 scope、page、sort、filter 等独立 React Query 键，跨产品 scope 由 `pagination.scope===scopeKey` 即时回落首页；`UserShow` 按用户 UUID 保存两个独立的分页游标。既有本地 AAL2 Chrome 的多页成员排序、User360 21+ Grant 页码和跨范围空→全平台恢复 PASS。**尚无证据证明旧请求真的污染新 scope**。
- **计划**：新增同会话“有数据→空 scope→有数据”快速切换及跨页查询前后关联检查，包含 20/21+ 行；使用已有合成数据，不重写 RA Query。只有出现错误混用或迟到结果再实施针对性修正。没有 1k/10k 合成规模就不得宣称容量验收。

#### UI-06 / P1 — 认证与恢复 UI 全态
- **已核事实**：`LoginPage` 已包括密码/TOTP/绑定，`AuthActionPage` 有邮件重置/确认入口；AuthProvider 在每次资格检查验证 AAL2，旧 AAL2 撤权拒绝已真实通过。恢复页面若只凭普通既有 Session 判定“恢复已就绪”需专门审查：一般已登录会话与 `PASSWORD_RECOVERY` 事件语义不同。
- **计划**：隔离验证无效/过期回调、常规已登录但非 recovery Session、错误 TOTP/取消/多标签状态，审查 `PASSWORD_RECOVERY` 判定和焦点/报错；没有可靠授权语义前，不造 MFA 或密码恢复后门。真实邮件链路/遗失设备的人工作业保留待签收。

#### UI-07 / P1 — 高风险操作弹窗与一次性明文
- **已核事实**：`OperationDialogs` 对 busy/pending/plaintext 有不同退出策略；`IssueCodes` 明文保存在组件本地，只有无敏感值的 pending metadata 写入 sessionStorage；真实 AAL2 Chrome 已通过下载、安全关闭、503 UNKNOWN/429 分支和明文不进入日志检查。
- **计划**：逐一增补 Escape/背景/忙碌/未保存与剪贴板失败/重复点击负例；保持首次明文与 UNKNOWN 恢复逻辑，不引入持久化明文。按截图、临时文件清理、权限拒绝核对；第三阶段仍须重验真实外部依赖。

#### UI-08 / P1 — 反馈附件与导出范围绑定
- **已核根因**：`FeedbackExport` 只有打开时重置敏感选项；`go()` 执行时从**实时** `product/filterValues/selectedIds` 组合 payload，用户若在弹窗打开、特别是二次敏感确认之后变更顶部产品范围，可能出现确认时看见的范围与实际请求范围不一致。其 20 条 UI 限制也应当在提交入口再守一次。服务端需继续独立验证实际访问范围。反馈详情图片元数据读取失败分支只写“请重试”却没有重试控件。
- **最小方案**：打开导出框冻结 selected/filtered 的记录范围、队列、产品、标签、优先级、星标等安全非秘密元数据；计算当前范围签名，发生改变立即阻断旧确认和下载，明确要求关闭并重新核对，绝不静默复用敏感批准；服务器仍作为权限权威。图片列表失败保留只读重试按钮（`refetch`），签名链接过期/私有对象仍按原权限错误处理，不冒充成功含图 ZIP。补冻结快照/改变范围/20 限制/敏感二次确认测试。

#### UI-09 / P1 — WCAG 2.2 AA / 人工核查
- **现有证据范围**：受控 axe 基线与部分 Tab/Escape、尺寸检查 PASS，但 `incomplete` 和 NVDA/VoiceOver、中文 IME、200/400% 缩放、焦点返回等未全面人工核查。**这不是已复现的 WCAG 全站失败**。
- **计划**：按第 5 节路由矩阵补充自动可执行测试及截图；人工读屏与所有者签收需明确记录 `NOT RUN`，不得自动判 `ACCEPTED`。

#### UI-10 / P1 — 性能与可交互
- **边界**：复用 S1～S6 权威性能计划，现有慢网 LCP 与目标差距未证明通过。新增测试必须包含真实非空点击→查询→可操作事件、1k/10k 数据范围与同条件对照；本 UI 专项不另建第二套性能指标，不靠静态拆包宣称通过。

#### UI-11 / P2 — 状态 token 与重复样式
- **已核事实**：`UserShow.memberState` 和 `WorkspaceLists.State` 对正常/未知/警告写局部 HEX，而统一 MUI Theme 已有 `success/warning/error/default` token；不需要整站换肤。

#### UI-12 / P2 — 用户为中心的闭环
- **已核事实**：受限用户精确邮箱查询、User360 两类关联分页、成员详情和治理弹窗已有；User360 缺直接查看此账号完整授权历史的显式入口（虽然可手工进入 Grant 列表）。
- **最小方案**：增加目标 UUID 精确过滤的授权列表深链，复用现有 query filter 和 server ACL；确保 URL 只有 UUID 不含邮箱/兑换码，不增加模糊用户搜索；验证直接进入后筛选与返回。

#### UI-13 / P2 — 权益与审计时间语义
- **已核根因**：`WorkspaceLists` 一种 `date` 格式覆盖授权起止、撤销、审计与成员时间，只输出本地日历日期；例如 10 月 27 日 00:01 与 23:59 会被显示成相同日期，忽略实际授权时限/审计时刻。`WorkspaceDetails`、User360、反馈时间又各自调用 `toLocaleString`，无明确时区标示，跨时区容易误解。
- **最小方案**：集中使用同一 zh-CN 时刻格式（精确到分钟、显式 GMT 偏移、按操作者浏览器时区）显示授权起止、到期/撤销、核销/审计、详情与反馈时间；真正只需日历的成员加入日期可用单独日期格式。仅显示层修改，不改变后端 UTC/幂等、ISO 日期输入语义。使用带显式 Z/偏移的夏令时前后样本在不同时区测试同一瞬间，不把时区格式化当业务 UTC 转换。

#### UI-14 / P1 — 产品运营 RBAC 架构依赖
- **定论**：目前后端仅允许平台管理员全局资格及 AAL2 服务端判定。没有获批角色模型、矩阵、迁移及数据合同时不允许在前端创建伪产品级管理员权限。**标记 BLOCKED ON ARCHITECTURE APPROVAL**；本轮继续保证顶栏产品范围仅过滤数据，不授予能力。

**施工门禁**：以上只列已实际检查的事实与测试设计。UI-05/06/07/09/10/14 的新增完整正反例，及 UI-08 真正私有图片/外部 ZIP，未运行前不得标 PASS。代码变更前后依旧保留当前工作区其余已生成的测试证据。
