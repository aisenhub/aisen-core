## 一、用户提出的问题和目标

### 实测现象

1. 管理员给用户主动授予权益时，被要求输入“目标用户 UUID/UID”；业务操作人员通常只知道**用户邮箱**，不清楚 UID 是什么、去哪找。
2. 成员详情页把顶部很长的“记录编号”和远离它的右上角复制图标拆开；不知道该复制按钮复制的是什么。
3. 查找账号结果表里的“用户编号”缩略显示，复制图标却放在表格最右侧“查看”列，与该编号隔开。
4. 查到用户进入详情后，有“用户编号”文本却**没有直接贴着该编号的复制按钮**。
5. 成员关系列表仍要求“精确成员 UUID”，管理员希望直接通过邮箱找用户/成员；以人工操作为中心的查找不应强迫记忆技术 ID。

### 用户明确要求

- 后台涉及真实用户的名称**统一叫“用户编号”**，不要对普通管理员混用“用户 UID”“用户 UUID”“用户 ID”。
- 用户编号和复制按钮**紧挨着同一个字段**，鼠标和键盘用户能知道复制的是哪串内容；点完有“已复制用户编号”反馈。
- 以**完整注册邮箱作为常用查找输入**，解决“先知道用户编号才能找用户”的死循环。
- “授予权益”也应从邮箱找人，不能把原始 UUID 粘贴当成默认操作路径。

| `apps/admin/src/data/dataProvider.ts` | `users` 通过 `admin_lookup_users` RPC 按完整邮箱或 UUID 查询；业务成员/授权表通过 `user_id` 过滤 | 可组合现有只读查找与记录查询，**数据库关联键仍是 UUID** |
| `supabase/migrations/20261024045105_admin_user_lookup.sql` | 限权 `admin_lookup_users` 已支持大小写不敏感的**完整邮箱精确匹配**和单个/批量 UUID 查找；强制 `private.require_admin()`，限制参数和页数 | 必须复用安全边界；不能改成前端直接遍历 `auth.users` 或模糊搜索枚举用户 |

## 三、编号词汇规范：统一用户字段，同时区分不同业务实体

**用户编号**是用户的唯一、长期不变的 `auth.users.id`（技术表示为 UUID）。它属于账号，而**非**某个产品成员关系、授权、反馈或请求。

| 真实数据 | 面向管理员显示的名称 | 复制行为 |
| --- | --- | --- |
| `auth.users.id` / `user_id` / `p_target_user_id` | **用户编号** | 复制完整用户 UUID |
| `product_memberships.id` | **成员关系编号** | 复制完整成员关系 UUID |
| `entitlement_grants.id` | **授权编号** | 复制完整授权 UUID |
| `request_id` | **请求编号** | 复制完整请求 UUID |
| `products.id` | **产品编号** | 复制完整产品 UUID |
| 审计记录、其他内部实体 `id` | 对应实体的记录编号 | 复制相应记录 UUID，不能笼统称为用户编号 |

**禁止**把成员关系页顶部的 `item.id` 改名为“用户编号”却仍复制 `item.id`。如果用户需要复制真实的用户编号，必须在“关联账号”旁独立显示 `user_id` 并提供对应复制按钮。

界面默认使用中文业务名称，不在操作标签上暴露“UUID”术语；在可展开的技术详情、接口文档或高级工具提示中可解释“用户编号（UUID）”。

## 四、推荐的页面改版方案

### 4.1 用户 / 查找账号列表（最先修复）

已具备完整邮箱搜索，只需改善可发现性与复制归属：

```text
查找账号                                  [完整注册邮箱________] [查询]

账号邮箱              用户编号                              注册时间     查看
user@example.com      c8010c8c-...  [复制用户编号]            2026/10/28   [详情]
```

- 将通用“查看”列的复制按钮**移到“用户编号”字段右侧**；不要同时保留两个语义不清的复制图标。
- 标题统一为“用户编号”，有空间优先允许完整值折行/可选中；狭窄表格可中间省略，但 Tooltip、展开或复制必须获得完整 UUID。
- 图标的可访问名称与提示均为“复制用户编号”；成功提示“已复制用户编号”，失败提示“复制失败，请手动选择编号”，不露出无关账户信息。
- 点击编号、复制、详情三者的命中区要分开，不因点复制误跳详情；移动端把按钮和编号放在同一个信息单元格。
- 当前“查找账号”的完整邮箱精确查询及默认不列出所有用户的隐私机制**保持不变**。

### 4.2 用户详情（消除“看得到但复制不了”）

```text
账号：user@example.com
用户编号：c8010c8c-....-....      [复制用户编号]

[为此用户授予 Pro]  [查看成员关系]  [查看授权记录]
```

- 在已有“用户编号”文本**同行右侧**放复制按钮，而不是放到页面角落。
- 账号邮箱为主标题，用户编号为次级技术信息；可以自动换行，复制始终可见。
- 维持已有成员、授权、账号状态读取；异常时不把“查不到用户资料”当作已核实身份。
- 点击“为此用户授予 Pro”直接把当前**已经核实的真实用户 UUID**传入授权对话框，并在那里显示对应邮箱，避免管理员再次查找或复制。

### 4.3 成员详情（解决“记录编号”到底是什么）

推荐拆成两块且精准标注：

```text
成员详情
成员关系编号：<member.id>       [复制成员关系编号]

业务信息
关联账号：user@example.com
用户编号：<user_id>            [复制用户编号]
所属产品：aisenlens             成员状态：正常
```

- 顶部复制只复制**成员关系编号**，其按钮必须移到编号旁、提示正确。
- “关联账号”区显示注册邮箱；对应真实用户编号可展开/二行展示并就近复制。
- 需区分“成员关系编号”“用户编号”“授权编号”，不全称“记录编号”。
- 现有“暂停成员”等产品作用域操作保持独立，不能把成员详情复制的 ID 错拿去授予另一个用户。

### 4.4 成员关系与授权记录列表：以邮箱为首要查找方式

```text
成员关系                         当前产品：aisenlens
成员状态 [全部]      [完整用户邮箱________________] [查询] [刷新]
```

- “精确成员 UUID”“精确授权用户 UUID”改成**“完整用户邮箱”**作为默认查询方式；输入完整邮箱、点击查询后，仅返回对应用户的成员关系/授权历史。
- 推荐逻辑：**经授权精确查找邮箱 → 得到唯一用户编号 → 用 `user_id` 与当前产品 `product_id` 过滤业务记录**；不要求用户填写 UUID，不直接允许按 LIKE 搜邮箱遍历 Auth 表。
- 原有的 UUID **深链接**（如用户详情的 `/memberships?user_id=...`、`/grants?user_id=...`）保留，支持受控内部精准定位，但不作为普通用户必须看到的输入框。
- 若高级审计场景确实需要直接输入用户编号，可在**高级筛选**中提供“按用户编号查询”，但默认只见邮箱；不要强行取消技术维护能力。
- 对“不存在该邮箱”“该用户存在但不属于当前产品”“权限不足/查询失败/超时”分别显示准确状态。**查询失败绝不能回退为未筛选的全员数据**。
- 在切换产品作用域、输入新邮箱、撤权或退出管理员账号时清理旧结果；避免缓存的 A 用户结果被误当作 B 用户。
- 目前成员关系/授权记录列表本来允许浏览当前作用域的记录，**不因新增邮箱筛选而删除正常的管理列表**；只是在查找时采用邮箱而非 UUID。

### 4.5 新增 Pro 授权：默认用邮箱选择用户，不再手输 UUID

**推荐关键流程**：

```text
授予 Pro 权益

目标用户
[输入完整注册邮箱________________] [查找账号]

查询结果（仅在查到并通过身份核验后出现）
账号邮箱：user@example.com
用户编号：c801...abcd             [复制用户编号]
[确认选择此用户]

所属产品：[aisenlens ▼]
授予模式：[固定天数 / 指定时间窗]
授权天数 / 生效时间 / 结束时间
授予理由：[__________________]

最终核对：将 Pro 授予 user@example.com（用户编号 c801...）
         产品：aisenlens ｜ 时长：30 天 ｜ 理由：...
                                   [取消] [确认授予]
```

- 入口 A：从“查找账号”按邮箱命中 → 进入用户详情 → 点击“为此用户新建 Pro 授权”。该路径应**自动选中该用户、展示邮箱**，无需再查一次。
- 入口 B：从“授权记录”或快捷入口直接点“新增 Pro 授权”。先完整邮箱精确查找，再明确选定用户，未查到或存在歧义则**禁止授权**。
- 无需重新发明一套用户表：用现有受保护的 `admin_lookup_users` 做只读映射；如将来有同邮箱多身份或冲突，必须拒绝直接操作并核查。
- 不允许把输入框里的邮箱原样作为授权 RPC 目标。**真正写入仍只传 `admin_grant_entitlement.p_target_user_id`（已核实的用户 UUID）**，以及现有产品、时长、理由、幂等请求编号；Core 仍须服务端验证管理员/目标状态/产品。
- 在用户选定后如果**再次改写邮箱或产品**，需要清除或重新完成对应的核对，防止显示邮箱 A 却实际授权 B。
- 最终提交按钮前可见**邮箱、用户编号、产品、Pro 模式/期限、理由**；确认的是一个确定用户而非一段 UUID。
- 维持已有对丢响应/UNKNOWN 的原始请求安全核查：锁定目标 UUID 和其他原始参数，不能因邮箱更名/重新查找而静默换目标、生成新请求或重复授权。
- AAL2 管理权限及敏感授权审计不放松；用户不知道 UUID 不是授权安全的理由。

### 4.6 历史交互提案：原平台账号混合操作（已被专用弹窗拆分取代）

> 2026-10-29 生效：`/account-actions` 只封禁/解封，`/admin-actions` 独立授予/撤销管理员资格，详情见 [Admin 当前架构](../../architecture/applications/admin-console.md)。后续段落是旧提案过程，不再指导当前实现。

- `AccountActions.tsx` 目前仍是“目标用户 UUID”；为保持用户管理体验一致，建议在后续同一批 UI 工作中复用**邮箱精确查找 + 已核实目标展示**。
- 此类操作影响平台账号或管理员资格，比 Pro 授权更敏感，**必须保留其现有状态核验、影响范围、二次核对、理由与操作审计**。
- 不得因为改成邮箱输入就对未确认身份授予管理员资格，也不得绕过最后一名有效管理员保护。

## 五、安全、兼容和错误边界

1. **不改变身份主键**：`auth.users.id` 仍然是成员、Grant、审计和权限 RPC 的正式身份关联；邮箱只用于人类查找，**不能当数据库外键**。
2. **精确邮箱而不是模糊枚举**：复用 `admin_lookup_users` 的 AAL2/真实管理员门禁、非空完整邮箱、大小写不敏感精确匹配、限制页数与查询数量；不新增通配符、模糊邮箱搜索或未授权列表。
3. **变更邮箱**：一旦账户注册邮箱发生变更，新邮箱可用来查找同一 UUID；旧邮箱不应作为身份别名偷偷指向不同账号。保存授权时按已核实的 UUID 执行，展示值也须避免过期缓存混用。
4. **产品作用域**：查账号是平台身份，成员/授权是特定产品业务事实；查询结果与操作表单必须清楚展示作用域，不能从一个产品页面静默授予另一个产品。
5. **错误区分**：空邮箱、格式不合法、未找到、已找到但无成员、权限 401/403、写入或状态冲突 409、限流 429、网络 503、结果未知分开提示。不能把 403/503 当成没有用户，更不能 fallback 全量数据。
6. **权限与审计**：剪贴板只在管理员主动点击时复制目标 ID；复制/查找操作不改变权限，授权与封禁仍由受保护 RPC 与审计决定。
7. **响应式与可访问性**：320/390/768/1280/1440px；200%/400% 缩放下编号与复制图标关联仍明确；按钮可用键盘触达、提示可朗读、成功有非干扰状态反馈。
8. **对齐术语**：凡真实用户 `user_id`，显示“用户编号”；成员关系、授权、工单、产品各有对应业务编号，防止复制错对象。

- `apps/admin/src/data/dataProvider.ts`：复用受限身份精确查询与业务表 `user_id` 过滤，避免创建无权限的原始 Auth 数据读取。

### 不应未经评审修改的后端边界

- `supabase/migrations/20261024045105_admin_user_lookup.sql`：当前 `admin_lookup_users` 已支持精确邮箱和 UUID。**优先无需新增后端查询接口或数据库迁移**。
- 仅当真实 UI 流程证明既有 RPC 不能安全地实现“邮箱→身份→业务记录”时，才提出独立的最小受保护只读 RPC；严禁因此开放 Auth 全量扫描或削弱 AAL2。
- `admin_grant_entitlement` 继续要求真实 UUID，不改为“直接用邮箱授权”，不在 DB 存储“邮箱是身份主键”的错误模型。

## 八、决策边界与执行状态

### 用户已明确

- 用户管理体验应以邮箱作为默认查找方式；称呼统一使用“用户编号”，编号旁就近放复制按钮。
